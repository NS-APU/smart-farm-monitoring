# コーディング規約

目的: 実装時に守るコーディング規約を定める。

> **ステータス: 草案**。技術スタック（TypeScript・Node.js・Hono・React・DynamoDB・Vitest。[architecture.md](../10_design/architecture/architecture.md) 13章、[ADR-0005](../10_design/adr/0005-tech-stack.md)）に合わせた規約を含む。項目ごとに関係者のレビューを受けて確定する。「推奨」とあるライブラリは、採用時に、依存パッケージの追加として事前確認を取る（AGENTS.md）。

## 基本方針

- 読みやすさを優先する。コードは書く時間より読まれる時間のほうが長い
- 既存のコードのスタイル・構成に合わせる
- フォーマットなど機械的に判定できるルールは、Formatter / Linter に任せる（人手のレビューでは扱わない）
- 変更は依頼・Issue の範囲に限定し、無関係なリファクタリングを混ぜない
- ルールに例外が必要な場合は、理由をコメントまたはPR本文に残す

## ツール

| 項目 | 内容 |
|------|------|
| Formatter | Prettier。設定は最小限（既定値を基本とし、変えるものは設定ファイルに理由を書く） |
| Linter | ESLint（flat config）+ typescript-eslint（型情報を使う `strict` 系のルール）。React には `eslint-plugin-react-hooks`。アクセシビリティ（jsx-a11y）のルールは、oxlint（`.oxlintrc.json`）で検査する（`eslint-plugin-jsx-a11y` は、MPL-2.0 の axe-core に依存するため使わない）。`pnpm lint` が、ESLint と oxlint の両方を実行する |
| 型チェック | TypeScript の `strict` を有効にする。加えて `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`、`noImplicitOverride`、`noFallthroughCasesInSwitch` を有効にする |
| 設定ファイルの場所 | リポジトリ直下（`eslint.config.js`、`.oxlintrc.json`、`.prettierrc`、`tsconfig.json`）。パッケージごとの設定は、直下の設定を継承する |
| 実行 | `pnpm` のスクリプトとして `lint`、`format`、`typecheck` を用意し、CI で実行する（コマンドは [commands.md](../00_project/commands.md)） |

- Formatter / Linter の違反がない状態でコミットする。コミット前の自動実行（pre-commit フック）を導入してよい
- CI で同じチェックを実行し、違反があればマージしない（[git-workflow.md](../40_operations/git-workflow.md)を参照）
- Linter の警告を無効化する場合は、対象を最小限にし、理由を併記する
- Prettier と ESLint のルールが競合しないようにする（書式のルールは Prettier のみで扱う）

## 命名規則

- 名前は「何であるか／何をするか」が読み取れるものにする。意味の薄い名前（`data`、`tmp`、`x` など）や独自の省略語は避ける
- 英語で命名する。ドメイン用語は [glossary.md](../00_project/glossary.md) の表記に合わせる
- TypeScript の表記:
  - 変数・関数・プロパティ・引数: `camelCase`
  - 型・インターフェース・クラス・React のコンポーネント: `PascalCase`
  - 定数（モジュールの定数で、変わらない値）: `UPPER_SNAKE_CASE`
  - ファイル名・ディレクトリ名: `kebab-case`（例: `sensor-alert.ts`。React のコンポーネントのファイルも同じ）。テストは `.test.ts` / `.test.tsx`
  - 型のパラメータは、意味のある名前にする（`T` だけにしない）。インターフェースに `I` の接頭辞を付けない
  - `enum` は使わず、文字列リテラルのユニオン型、または `as const` のオブジェクトを使う
- 真偽値は状態が読み取れる名前にする（例: `isActive`、`hasError`）
- 単位を持つ値は、名前または型で単位がわかるようにする（例: `temperatureCelsius`、`intervalSeconds`、`humidityPercent`）
- ブランチ名・コミットメッセージは [git-workflow.md](../40_operations/git-workflow.md)に従う

## コードの構成

- 1つの関数・クラスには1つの責務を持たせる。長くなったら分割する（目安: 関数は画面1つ分に収まる程度）
- ネストを深くしない。早期リターンで異常系を先に処理する
- 同じ処理を複数箇所に書かない。ただし、偶然似ているだけの処理を無理に共通化しない
- マジックナンバー・文字列リテラルは定数に名前を付ける。特に閾値は、設定または定数として一箇所に定義する
- 健全性の判断基準（閾値・区分）は、[viewpoint](../10_design/viewpoint/) の設計と対応させ、コード中に直接書かない
- 時間の単位の換算（分・時間・日のミリ秒など）と、タイムゾーンは、`src/shared/time.ts` の定数を使う。値の集合（期間・取得間隔・並べ替えの項目・設定の選択肢など）は、定数の配列を1か所に定義し、スキーマと型をそこから導出する（同じ値を、別の場所に書き写さない）
- `exactOptionalPropertyTypes` のもとで、「値があるときだけキーを足す」場合は、`...(x === undefined ? {} : { x })` と書かず、`omitUndefined`（`src/shared/omit-undefined.ts`）を使う
- 提示層の本番の経路（ハンドラなど）は、インフラ層に依存しない（ESLint で検査する。開発用 API の `dev-routes.ts`・`api-deps.ts` のみ例外）
- 依存の向きは [architecture.md](../10_design/architecture/architecture.md) の設計（提示・インフラ → アプリケーション → ドメイン）に従う。ドメインのコードは、AWS SDK・Hono・React に依存させない（ポートを介して使う）
- `export` は、必要なものだけにする。ディレクトリごとの `index.ts` で何でも再公開しない（循環参照を避ける）
- ESM（`import` / `export`）を使う。循環参照を作らない
- `shared/` には、バックエンドとフロントエンドの双方で使うコードのみを置く

## 型とデータ

- 型を明示する。`any` は使わない。型が不明な外部の値は `unknown` として受け、検証して絞り込む。型アサーション（`as`）と非 null アサーション（`!`）は、原則使わない（使う場合は、理由をコメントに残す）
- 外部入力（API、画面、取り込むファイル、環境変数）は、境界でスキーマ検証する。スキーマと型は、1つの定義から導出する（推奨: Zod）。バックエンドとフロントエンドで共有するスキーマは `src/shared/` に置く
- 関数の引数が多い場合や、同じ型の値が並ぶ場合は、オブジェクトで受ける。戻り値の型は、公開する関数では明示する
- データ項目の名前・型・単位は [data-dictionary.md](../10_design/data/data-dictionary.md) の定義に合わせる
- 識別子（設備ID、ステータスコードなど）は、型で区別する（ブランド型など）。異なる種類の ID を取り違えない
- 時刻は UTC で保存・受け渡しし（ISO 8601、末尾 `Z`）、画面に表示するときにのみ、日本時間（`Asia/Tokyo`）に変換する。内部では、`Date` または専用の型に変換して扱い、文字列の比較・加算をしない。日付ライブラリは、必要になるまで追加しない
- 数値は単位を統一して扱い、単位変換は境界（入出力）でのみ行う。金額や回数は、整数で扱う。小数の比較は、許容誤差を明示する
- センサー値の欠損は、`0` などの値で代用せず、欠損（`null` または専用の型）として区別して扱う。`undefined`（未取得）と `null`（欠損）の意味を決め、混在させない
- 不変（`readonly`、`const`）を基本とする。引数のオブジェクトを書き換えない
- 判定のロジック（閾値判定、評価）は、副作用のない純粋な関数として実装する（[architecture.md](../10_design/architecture/architecture.md) 7章）

## エラーハンドリング

- エラーを握りつぶさない。捕捉する場合は、回復する・変換して伝える・ログを残すのいずれかを行う
- 想定できるエラー（入力不正、通信失敗、センサー欠損など）と、想定外のエラー（バグ）を区別する。想定できるエラーは、種類が分かる独自のエラー型（`Error` を継承し、`cause` に原因を持つ）にする
- `throw` するのは `Error` のインスタンスのみにする。`catch` した値は `unknown` として扱う
- 非同期処理は、`async` / `await` を使う。`await` し忘れた Promise（floating promise）を作らない（Linter で検出する）。並列に実行できるものは `Promise.all` / `Promise.allSettled` を使い、失敗の扱いを明示する
- 外部との通信（API・センサー・ロボット）には、タイムアウトとリトライ方針を設ける
- 外部入力（API・画面・センサーのデータ）は境界で検証し、検証済みのデータだけを内部に渡す
- ユーザー向けのエラーメッセージに、内部情報（スタックトレース、パス、SQL、設定値）を含めない
- 異常を検知した場合は、農作業者が対応を判断できるよう、何が起きたかと取るべき対応を伝える（HITL の設計に従う）

## ログ

- ログレベル（エラー・警告・情報・デバッグ）を使い分ける
- 構造化ログ（JSON）で出力する（推奨: AWS Lambda Powertools の Logger）。原因調査に必要な情報（対象のロボット・ハウスの識別子、時刻、処理の種類、リクエストの識別子）を、項目として残す
- 秘密情報・個人情報・リクエスト本文の全体をログに出力しない。必要な場合はマスキングする（[security.md](./security.md)を参照）
- 正常時に大量のログを出さない。センサー値の逐次出力などはデバッグレベルにする（ログの量は、費用に直結する。[architecture.md](../10_design/architecture/architecture.md) 11章）
- `console.log` を直接使わない。共通のロガーを使う

## コメント・ドキュメント

- コメントは日本語で書く
- コードを読めばわかること（何をしているか）は書かない。**なぜそうしたか**（判断の理由・制約・注意点）を書く
- 公開される関数・クラス・API には、用途・引数・戻り値・例外を説明するドキュメントコメントを付ける（形式: TSDoc の `/** ... */`）
- 未対応事項には `TODO:` を付け、可能なら Issue 番号を併記する
- 使わなくなったコードをコメントアウトして残さない（履歴は Git にある）
- 仕様・設計の説明はコメントではなく `docs/` に書く（[documentation-guidelines.md](../00_project/documentation-guidelines.md) 参照）

## セキュリティ

- 秘密情報（APIキー・パスワード・トークンなど）をコードに直接書かない。環境変数から読み込む
- DB へのクエリは、SDK のパラメータ（式の属性値・属性名のプレースホルダ）を使い、文字列結合で組み立てない
- 出力時に適切にエスケープし、XSS などを防ぐ。React では、`dangerouslySetInnerHTML` を使わない
- 認証・認可を必要とする処理（特に、ロボットやハウス設備の遠隔操作・設定変更）は、サーバ側で権限を確認する。画面の表示制御だけに頼らない
- 暗号・認証などの仕組みは自作せず、実績のあるライブラリを使う
- 詳細は [security.md](./security.md)に従う

## 依存パッケージ

- 追加・更新・削除は、目的と選定理由をPRに記載し、事前に確認を取る（AGENTS.md の「必ず事前確認が必要なこと」）
- メンテナンスされており、ライセンスが問題ないものを選ぶ。**コピーレフトのライセンス（GPL・AGPL・LGPL・MPL・EPL・CDDL・CC-BY-SA など）の依存は、追加しない**（推移的な依存を含む。確認の方法と結果は [.license-check/license-report.md](../../.license-check/license-report.md)）。依存を追加・更新したら、ライセンスの一覧を再確認する
- 標準ライブラリや既存の依存で足りる場合は、新しい依存を追加しない
- バージョンは固定し（`pnpm-lock.yaml` を管理する）、脆弱性診断（`pnpm audit`、Dependabot）を定期的に実行する
- 依存は、必要な範囲だけを import する（Lambda のバンドルサイズ・起動時間への影響を抑える）。AWS SDK は v3 のモジュール単位のパッケージを使う

## バックエンド（Hono・Lambda）

- ハンドラは薄く保つ。入力の検証 → ユースケースの呼び出し → 応答の変換、のみを行い、業務のロジックは、アプリケーション層・ドメイン層に置く（ADR-0001）
- AWS SDK のクライアントなど、重い初期化は、ハンドラの外（モジュールの読み込み時）で1度だけ行い、再利用する。ハンドラの中で毎回生成しない
- Lambda の実行時間・メモリに合わせて、処理を、時間内に終わる単位に分ける。外部との通信には、タイムアウトと再試行（回数・間隔の上限）を設ける
- スケジューラやストリームから起動される関数は、同じイベントが重複して届いても、結果が変わらない（冪等）ように実装する（推奨: Powertools の Idempotency）
- 認証・認可は、ミドルウェアで全ルートに適用し、例外（公開ルート）を明示する。トークンの検証をクライアントの申告だけに頼らない
- 設定値・秘密情報は、環境変数から読み、起動時にスキーマで検証する。ハンドラの中で直接 `process.env` を参照しない
- API の応答は、一貫した形式にし、エラーの応答に内部情報を含めない

## DynamoDB

- アクセスパターン（[data-model.md](../10_design/data/data-model.md)）から、キーを設計する。`Scan` を使わない（設定の少量のデータを除く。使う場合は理由を残す）
- 観測値は、（設備・項目）をパーティションキー、日時をソートキーに引く設計を基本とする（TODO: データモデルの設計で確定する）。ホットパーティションを避ける
- 項目の読み書きは、Repository のポートを介して行い、ドメインのコードに SDK の型を出さない（ADR-0001）
- 複数項目を同時に更新する必要がある処理（連携キューへの追加など）は、トランザクション書き込みを使う。条件付き書き込み（条件式）で、競合・重複を防ぐ
- 期限のあるデータ（ログ、連携キュー）には、TTL を設定し、費用の増加を防ぐ（[architecture.md](../10_design/architecture/architecture.md) 11章）
- 読み取りは、必要な属性だけを取得する（射影）。ページングを必ず処理する

## フロントエンド（React）

- 関数コンポーネントとフックを使う。クラスコンポーネントは使わない
- フックのルールを守る（Linter で検出する）。`useEffect` は、外部との同期にのみ使い、データの導出・イベント処理に使わない。依存配列を省略・無効化しない
- 状態は、必要な最小の範囲に置く。サーバーの状態（取得したデータ）と、画面の状態を分ける（サーバーの状態は、取得・キャッシュ・再取得を扱うライブラリで管理する。TODO: ライブラリの選定は、設計時に決める）
- 画面の更新（約10秒。FR-6.7）は、タブが表示されているときだけ行い、不要な再描画・通信を避ける
- コンポーネントは、表示に専念させ、判定・変換のロジックは、`src/shared/` または純粋な関数に置く
- アクセシビリティを守る（意味のある HTML 要素、ラベル、キーボード操作、色だけに頼らない状態の表示。NFR-7.2）。日本語の文言は、コードの直書きを避け、一箇所にまとめる
- リストには安定した `key` を付ける（配列のインデックスを、並び替わるリストの key にしない）

## 避けること

- グローバルな可変状態への依存
- 長大な関数・クラス（責務が混在しているサイン）
- 理由の説明のない Linter 警告の無効化
- テストされていない分岐の追加（[test-policy.md](../30_quality/test-policy.md)を参照）
- 秘密情報・個人情報・実データのコード・テスト・ログへの混入
- `any`、`@ts-ignore`（使う場合は `@ts-expect-error` と理由）、`as` による型の握りつぶし、`!`（非 null アサーション）
- `enum`、`namespace`、`var`、`==`（`===` を使う）
- floating promise、`async` 関数の中での `forEach` による非同期処理
- `console.log` の直接の使用（共通のロガーを使う）
- `Scan` の常用、ハンドラの中での SDK クライアントの生成
- `dangerouslySetInnerHTML`、`useEffect` でのデータの導出

## テスト

- テストの書き方は [test-policy.md](../30_quality/test-policy.md)に従う
- テストしにくいコード（時刻・乱数・外部通信への直接依存）は、差し替え可能な設計にする
