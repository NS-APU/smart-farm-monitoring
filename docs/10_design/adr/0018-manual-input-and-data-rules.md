# ADR-0018 手動入力・データの扱いの規則を、恒久の仕様にする（#145 の決定）

- ステータス: 承認（2026-10-26。ユーザーの判断。Issue #145）
- 日付: 2026-10-26
- 関連: [ADR-0007](./0007-dynamodb-table-design.md)、[ADR-0014](./0014-defer-evaluation-on-manual-entry-write.md)、[ADR-0016](./0016-ingestion-federation-rules.md)、[ADR-0017](./0017-evaluation-rules.md)、[architecture.md](../architecture/architecture.md) 4.2・4.3・6 章、FR-2.3・FR-2.4・FR-2.6・FR-4.1.4・NFR-3.6・NFR-4.2、UC-07・UC-12・UC-18

目的: 手動入力・データの扱いの、暫定だった規則（自動取り込みと手動入力の重なり・修正後の評価と通知・設備の削除・設備の登録方法・保存期間とバックアップ）を、決めて、恒久の仕様にする。決めた経緯（背景・見直しの条件）は、各決定のコメント（#145）にもある。

## 背景

- 手動入力は、自動取り込みの予備の入口でもある（ADR-0016。自動取り込みの項目は、すべて手動でも入力できるようにする。#192）。
- 評価は、合計の項目（収穫数・稼働時間など）を、期間内の値を足して求めていた。これは、自動取り込みの各記録が「その時間帯の増分」だという**未確認の仮定**に基づく（`robot-json` の形式定義の想定）。
- 保存期間・バックアップは、要件が暫定（NFR-3.6・NFR-4.2）で、期限の設定がなかった。

## 決定

### D-26 自動取り込みと手動入力の重なり

- 合計の項目（自動の収穫数・稼働時間・待機時間・収穫稼働時間・走行停止時間の 5 項目）は、**累積のスナップショット**とする（暫定）。**期間の値 = 期間内の増分の合計。値が減ったときは、リセットとみなす**（累積の基準が、今日の分・電源投入後・通算のどれでも、壊れない）。手動入力（#192）の同じ項目も、同じ意味（「今日これまでの累計」など）。手動専用の件数項目（果実損傷数・誤収穫数・取り残し数・緊急停止回数・ヒヤリハット件数・故障回数・復旧に要した時間・メンテナンス費・電気代など）は、現状のまま、入力ごとの件数を足す。
- 理由: 提供元のファイルは、最新の値だけが入り、全体が書き換わる（ADR-0016 D-08）。増分だと、取得の合間に更新された分が失われるが、累積なら、取りこぼしても、次の値に含まれる。累積の値を足すと、過大になる（例: 8:00 に 0、12:00 に 1,200、16:00 に 2,400 なら、足すと 3,600。正しい 1 日の値は 2,400）。
- **合計の項目は、自動を優先する**。**評価の期間**（短期 24 時間・長期 N 日）に、自動の値が 1 件でもあれば、自動だけを使い、手動は使わない。自動がなければ、手動だけを使う（手動のみの運用。ADR-0016 D-12）。両方とも保持する。累積の値は、取得元を混ぜると壊れるため（例: 自動の 1,800 → 手動の 1,700 → 自動の 2,400 で、14:00〜16:00 の増分が、正しくは 600 のところ 2,400 になる）。
- 状態値（温度など）とステータスコードは、現状のまま（どちらも使う。同じ計測日時のときだけ、手動を優先）。
- 画面: 保存のとき、同じ評価の期間に自動取り込みの値があれば、「この期間は自動取り込みの値を使うため、この入力は評価に使われません」と示す（保存はできる）。取り込み済みデータの一覧に、「評価に使われていない」印を付ける。手動入力の項目の説明に、値の意味を書く。
- 見直しの条件: 提供元から、値の意味（累積・増分）が示されたとき。自動が途中で止まった期間を、手動で補いたい要望が出たとき（日ごとの選択や、手動入力に対象期間を持たせる案）。確認は #193。

### D-27 手動入力の修正・削除の後の、評価の更新と通知

- 評価の更新は、現状を恒久化する（ローカルは、その場で。AWS は、定期の評価で、最大 5 分。ADR-0014）。設備を変える修正は、変更前の設備も再評価する。
- 修正・削除で、状態が「注意」「異常」に変わったときも、**通常の状態変化と同じように通知する**。通知に、修正が原因であることは示さない（AWS では、定期の評価が検知するため、修正によるか、時間の経過によるか、判別できない）。出した通知は、履歴として残し、取り消さない。「正常に戻った」ことの通知は、#146 で決める。
- 過去の評価・状態の履歴は、再計算しない（ADR-0017 D-24）。
- 画面（SC-07）も、修正・削除の後に、評価の更新を示す（AWS では「評価への反映には、数分かかります」）。

### D-28 設備を削除したときの扱い

- 設備を削除すると、**設備の記録・観測値（自動・手動）・手動入力・評価結果・状態変化の履歴を削除**する（ハウスは、配下のロボット・センサーも）。**残すもの**: 設備の変更履歴（登録・変更・削除。削除した設備・件数・実行者・日時を記録）、通知、取り込みログ・取り込み済みファイルの記録。手動入力の個別の変更履歴は、削除する。連携キューの未送信分は、破棄する。
- **農業情報基盤に送信済みのデータは、削除しない**（範囲外）。
- **復元は、作らない**。**同じ設備 ID の再登録を許す**（過去のデータが、システムの中に残らないため）。農業情報基盤の側では、同じ ID の過去データに、新しいデータが続く（#176 の連携の設計で扱う）。
- **削除の確認**: ハウスは、警告文を示し、ハウスの名前を入力して確認する（配下の設備とデータがすべて削除されること、元に戻せないこと、農業情報基盤に送信済みのデータは削除されないこと）。ロボット・センサーは、警告つきの確認ダイアログ。
- 取り込みファイルに残る、削除した設備のレコードは、「削除済みの設備」として別に数え、棄却数に含めない。
- 削除は、**非同期の処理**にする（データが大量のため）。削除の履歴を、必ず残す。誤って削除した場合は、35 日以内なら、PITR で別のテーブルに復元して、データを取り出せる（D-30）。
- 見直しの条件: 誤削除が実際に起きたとき（復元機能を検討する）。

### D-46 設備・取り込み設定の登録方法

- **画面で行う**ことを恒久化する。一括登録（CSV など）は、設けない。設備の登録・変更の権限は、管理者のみ（ADR-0013）。登録データ（DB）を正とする構造は、維持する（設定ファイル等は、将来の拡張として、追加できる）。
- 見直しの条件: 設定ファイルが望ましいという要望が出たとき。設備が多数になったとき。

### D-30 保存期間・バックアップ

- 観測値・手動入力・評価結果・状態変化の履歴・通知・変更履歴は、**期限を設けない**（自動では削除しない）。ストレージの費用が小さく、研究用データの価値があり、評価が読むのは 90 日までのため。
- **取り込みログ・連携ログ・送信済みの連携項目は、90 日で自動削除**する（TTL）。
- バックアップは、**PITR 35 日のまま**。「プロジェクト終了後 1 年以上の保持」は、データそのものを残すことで満たし、バックアップの保持期間とは解釈しない。
- 見直しの条件: 保存の費用が予算に影響したとき。発注者から、期限・バックアップの世代の指定があったとき。
- **注意**: D-11 の既定（ロボット 1 分・センサー 5 分）では、観測値が約 10 倍になり、評価の読み取り（直近 90 日分を 5 分ごと）の費用が、月 3,000〜6,900 円程度（試算）になるおそれがある（月 5,000 円の上限に近づくか超える）。別の Issue（#232）で、再試算と対策を検討する。

## 結果・トレードオフ

- 手動入力・データの扱いの規則が、決まり、文書の TODO が置き換わる。実装は、別の Issue（下記）。決定のうち、実装が済んでいないものは、文書に「決定（実装は #xxx）」と書いて、現状と区別する。
- 合計の項目の値の意味（累積）は、提供元の確認前の想定（暫定）。増分だった場合は、集計を足し算に戻す。
- 設備の削除は、元に戻せない（PITR の 35 日以内の取り出しを除く）。誤操作を、確認の UI で防ぐ。
- 合計の項目は、自動が途中で止まった期間を、手動で補えない（自動があれば、手動は使われない）。
- 観測値は、期限なしで増え続ける。ストレージの費用は小さいが、評価の読み取りの費用は、取得間隔に依存する（#232）。
