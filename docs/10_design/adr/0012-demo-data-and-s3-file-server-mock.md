# ADR-0012 評価環境のデモデータは、ファイルサーバーのモック（S3）と、手元のコマンドで用意する

- ステータス: 承認（2026-10-20。ユーザーの判断。Issue #77）
- 日付: 2026-10-20
- 関連: [ADR-0003](./0003-ingestion-adapter-and-provisional-spec.md)、[ADR-0007](./0007-dynamodb-table-design.md)、[ADR-0009](./0009-lambda-production-assembly.md)、[ADR-0011](./0011-jobs-eventbridge-lambda.md)、[security.md](../../20_development/security.md)

目的: 顧客に評価いただく環境で、ログイン直後から画面を評価できるようにするための、ファイルサーバーのモック・デモデータ・リセットの決定を残す。

## 背景

- ファイルサーバー・農業情報基盤・Web Push は、接続方式が未確定（Q-002・Q-005）のため、評価環境では、モックのまま動かす。
- ローカルのファイルサーバーのモックは、ローカルのディレクトリ（`<ルート>/<取り込み元>/`）。**Lambda にはローカルのディレクトリがない**。
- デモデータ（`SEED_MODE=DEMO`）は、起動時に、設備・直近 3 日分の観測値・評価を作る。**Lambda では使えない**（コールドスタートのたびに、投入しないため。ADR-0009）。
- 一度だけ投入したデータは、時間がたつと古くなる（取得間隔 15 分 × 3 = 45 分程度で、「データが古い」「不明」になる）。

## 決定

本 ADR は、Issue #77 を、3 つの PR に分けて実装する（PR1: S3 のモック。PR2: 手元のコマンド。PR3: 合成データの定期生成）。実装済みの範囲は、各節の末尾に記す。

### 1. ファイルサーバーのモックの S3 版（PR1）

- **S3 のバケットを、ファイルサーバーに見立てる**。構成は、ローカルのモックと同じ: `s3://<バケット>/<取り込み元の識別子>/<ファイル名>`（取り込み元: `robot`・`environment-sensor`）。`FileSourcePort` の S3 版（`infrastructure/s3/s3-file-source.ts`）を、ローカル版と同じ契約テストで確かめる。
- **環境変数 `FILE_SERVER_S3_BUCKET` を指定すると、S3 版を使う**（未指定なら、これまでのローカルのディレクトリ）。評価環境の Lambda（API・ジョブ）は、IaC が指定する。
- **ローカル版との違い**: ① 停止・遅延の再現（開発用 API）は、ない（本番で無効）。② 接続テストは、「バケットを一覧できるか」を確かめる（S3 には「ディレクトリ」がなく、ファイルがない取り込み元と、設定の誤りを区別できない）。③ AWS のエラーは、すべて `FileSourceUnavailableError` にする（利用者に見せる文言に、AWS の情報を含めない。原因は `cause` に残す）。
- **IaC**: バケット（非公開・暗号化・SSL 強制・評価環境と一緒に削除・**ファイルは 3 日で自動削除**）。API・ジョブの Lambda には、**このバケットの読み取りだけ**（`s3:ListBucket`・`s3:GetObject`。書き込み・削除はなし）を付ける。3 日で消すのは、古いファイルが、取り込みのたびに、読み込まれ続けないようにするため。
- **置くのは、合成データだけ**（実データ・個人情報は置かない）。

### 2. デモデータの投入とリセット（PR2。実装済み）

- **手元で実行するコマンド**（`pnpm demo-data seed` / `pnpm demo-data reset`）。ユーザーの AWS のプロファイルで、DynamoDB を直接操作する（`pnpm initial-user` と同じ方式。ユーザーの判断）。公開の URL からは呼べないため、安全。
- 投入する内容は、ローカルのデモと同じ（設備 3 件・直近 3 日分の観測値・手入力の例・評価）。設備がすでにあれば、何もしない（`seed`）。
- **リセット（`reset`）**: **ユーザー（`USER`）・ログインの試行回数の記録（`LOGINFAIL`。リセットで制限を解かない）・ジョブのロック（`JOBLOCK`。実行中のジョブを妨げない）以外の、すべてのデータ**（DynamoDB の観測値のテーブルの全項目と、Main テーブルのそれ以外の項目）と、**ファイルサーバーのモックの S3 のファイルを消す**。S3 のファイルを残すと、取り込みのジョブが、古い合成ファイルから、観測値を作り直してしまうため。テーブルの定義（キー・インデックス・TTL・バックアップ）は、変えない。ステータスコードの初期データは、入れ直す。
- **誤って消さないため、`--yes` を付けないと、何も消さずに、消す対象の件数だけを示す**。S3 のファイルを先に消し、そのあとに DynamoDB のデータを消す（先に DynamoDB を消すと、その間に、取り込みのジョブが、古いファイルから観測値を作り直すため）。S3 の削除に失敗したら（一部が消せないときも）、DynamoDB のデータは、消さない。
- 実行の環境変数は、`PERSISTENCE=dynamodb`・`DYNAMODB_*_TABLE`・（S3 のファイルも消すとき）`FILE_SERVER_S3_BUCKET`。Cognito の設定は、要らない（ユーザーは、触らない）。
- AWS のエラーは、名前だけを出力する（`pnpm initial-user` と同じ）。Scan を使う（全項目を読む）。評価環境の規模（デモデータ）を前提にした、運用者の手元の操作。

### 3. 合成データの定期生成（PR3。実装済み）

- 一度だけの投入では、データが古くなるため、**擬似のロボット・環境センサーが、定期的に、新しいファイルを S3 に置く**（EventBridge → 専用の Lambda。ジョブ（JB-01〜JB-04）とは別。要件のジョブではなく、評価環境のデモのための仕掛け）。取り込み（JB-01）が、それを読む（ユーザーの判断）。
- **専用の Lambda**（`runtime/demo-feed-lambda.ts`）を、EventBridge の 1 つのルールが、**15 分ごと**に起動する（`DEMO_FEED_INTERVAL_MINUTES`。取り込みの既定の取得間隔と同じ）。**S3 への書き込みだけ**（`robot/*`・`environment-sensor/*` への `s3:PutObject` のみ。読み取り・削除・DynamoDB・Cognito は、使わない）。メモリ 256 MB・タイムアウト 60 秒。失敗は、次の周期で、再び置く（EventBridge・Lambda の再試行は 0）。
- **ファイルは、区間（15 分）の時刻から決まる**: 区間ごとに、ロボットの JSON（`robot-20261020T0415Z.json`。FormatProfile `robot-json`）と、環境センサーの CSV（`sensor-20261020T0415Z.csv`。`environment-sensor-csv`）を 1 つずつ、記録は区間の開始の時刻の 1 件。値は、デモの投入と同じ生成の規則（`generateAutoSample`。乱数を消費する順序は、変えない）。温度の基準は、デモの投入と同じ 26℃（環境適応性が「注意」になる）。
- **1 回の実行で、直近 4 区間を置く**（`DEMO_FEED_BUCKETS`）。同じ区間は、同じ名前・同じ内容のため、上書きしても、取り込みは、内容のハッシュで読み飛ばす（実行が数回、抜けても、直近の区間は、埋まる）。実データは、使わない（合成データのみ）。

## 検討した代替案

| 案 | 採らなかった理由 |
|----|------------------|
| 合成ファイルを、Lambda のコードに同梱する | 実際の取り込み（FileSourcePort 経由）の動作を、環境で確認できない。Issue の設計（S3 のモック）から外れる |
| 管理用の Lambda（`aws lambda invoke`）で、投入・リセットする | データを消す権限を持つ Lambda が、常に存在する。関数・IAM が増える |
| デプロイ時に、自動で投入する | データを、意図せず、作り直す（または上書きする）おそれがある |
| 一度だけの投入（再投入は手動） | データが 45 分程度で古くなり、顧客に数日見せる用途に向かない |

## 結果・トレードオフ

- 取り込み元（`robot`・`environment-sensor`）の、ファイルの形式は、仮決めの FormatProfile（Q-001・Q-004）のまま。
- バケットのファイルは 3 日で消えるため、**取り込み済みのファイルが消えても、観測値は、DynamoDB に残る**（取り込み済みの記録も残る）。
- **デモの設備が必要**: 合成データのファイルは、デモの設備（外部の識別子 `ROBOT-SAMPLE-01`・`SENSOR-SAMPLE-01`）に対応する。設備がない間（`reset` のあと、`seed` の前）に、取り込みが走ると、記録は、設備が見つからないとして棄却され、そのファイルは、取り込み済みの扱いになる（`seed` のあとに、同じ区間のファイルは、再び取り込まれない）。**`reset` と `seed` は、続けて実行する**。
- 生成の Lambda は、`reset` のあとも、動き続ける。消した S3 のファイルは、次の実行（最長 15 分）で、直近 4 区間の分が、再び置かれる。
- ファイルサーバーのモックが S3 になっても、実際のファイルサーバーのアダプタ（Q-002）は、別。同じ契約テストを適用して追加する。

## 検証（AWS）

### PR1（S3 のモック）のデプロイの後（2026-10-20。ユーザーが実行）

| 項目 | 結果 |
|------|------|
| バケットの設定 | 公開のブロックが 4 項目とも有効・ファイルを 3 日で自動削除（`Enabled`・3）・暗号化（`AES256`） |
| Lambda の環境変数 | API・ジョブの両方に、`FILE_SERVER_S3_BUCKET`（バケット名）が入っている |
| ジョブ（JB-01 など）の実行 | 直近 5 分で `EXECUTED` が 11 件。`level error`・`AccessDenied` は 0 件（S3 の一覧に成功している） |
| 取り込み元の「接続テスト」（API。`robot`・`environment-sensor`） | 2 つとも `ok: true` |

- **未確認**: (1) S3 のファイルの**読み取り**（`s3:GetObject`）と、観測値の取り込み（設備がなかったため。デモデータの投入の後に確認する）。(2) 3 日での自動削除が、実際に起きること。(3) `pnpm demo-data seed / reset` の、実際の AWS での動作（PR2 のデプロイの後に確認する）。

### PR2（`pnpm demo-data`）のデプロイの後（2026-10-20。ユーザーが実行）

| 項目 | 結果 |
|------|------|
| `seed`（データなしの状態から） | ハウス 1・ダッシュボードは `FRESH`・観点 10（NORMAL 6・CAUTION 1・ERROR 2・UNKNOWN 1）。API・画面（目視）とも、問題なし |
| `reset`（`--yes` なし） | 観測値 2,904 件・S3 のファイル 0 件と表示。**何も消えていない**（ハウス 1・同じダッシュボード） |
| `reset --yes` | 観測値 2,904 件・そのほかのデータ 221 件（`USER`・`LOGINFAIL`・`JOBLOCK` を除く）・S3 のファイル 0 件を削除。ハウス 0・ダッシュボード 404。**ログインできる**。S3 は空。**ジョブは動き続けている**（直近 3 分で `EXECUTED` 8 件・`level error` 0 件） |
| 投入し直し（`seed`） | 最初の `seed` と同じ結果（ハウス 1・`FRESH`・観点 10・同じ件数） |

- 観測値 2,904 件は、見込み（3 日 × 1 日 96 回 × 10 項目 + 手入力の例 14 件）と一致した。
- **未確認**: (1) S3 のファイルが**ある**状態での `reset --yes`（S3 の削除。バケットが空だったため。生成の Lambda（PR3）のあとに確認する）。(2) **ユーザーを含む全データの削除 → 再デプロイ → 最初のユーザーの作成 → 再投入**（operations.md 7.5 の前半。`SfmData` を作り直す大きな操作。別に確認する）。
