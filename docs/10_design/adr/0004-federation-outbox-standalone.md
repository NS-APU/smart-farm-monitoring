# ADR-0004 農業情報基盤との連携を、連携キューによる非同期方式にする

- ステータス: 承認（2026-10-21。ユーザーの判断。Issue #81。Sprint 1 から実装・運用している）
- 日付: 2026-10-09
- 関連: [architecture.md](../architecture/architecture.md) 5.3、RQ-006, RQ-007, RQ-020 / FR-8 / NFR-2.1, NFR-2.2, NFR-4.4

## 背景

- 農業情報基盤（FIWAREベース、AWS EC2上）は、運用コストの観点から停止していることがあり、可用性に依存できない（RQ-007）
- 連携対象は、生データ（ロボット・環境センサー・手動入力）と派生データ（メトリクス・診断結果・推奨アクション・分析結果）。連携方式（API・データモデル・頻度）と、停止中のデータの扱い（再送・遅延連携）は未確認（Q-005）

## 決定

1. 連携は FederationPort で抽象化し、方式ごとの実装はアダプタとする
2. 連携対象のデータは、保存・評価の完了と同じトランザクション（DynamoDB のトランザクション書き込み）で、DBの連携キュー（アウトボックス）に積む。連携ジョブ（サーバーレスの関数。スケジューラまたは DynamoDB のストリームを契機に起動）が、非同期に送信し、結果（成功／失敗／保留）を記録する
3. 送信の失敗時は、間隔を広げて再試行する。農業情報基盤の停止は、アプリケーションの異常とはみなさず、他の機能に影響させない
4. 復旧後の再送・遅延連携の許容と、古いデータの破棄の方針は、設定として持てる形にする（TODO: Q-005）
5. 農業情報基盤の側から取りに来る方式（プル）になる場合は、読み取り専用のREST API（NFR-8.3）で対応する

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|--------|------|------|
| A. 連携キュー + 非同期の連携ジョブ（採用案） | 停止中も取りこぼさない。単独稼働を保てる。方式の変更はアダプタに閉じる | キューのテーブルと連携ジョブの実装・運用が要る |
| B. 保存の都度、同期で送信 | 単純 | 停止時に処理が待たされる・失敗する。RQ-007 に反する |
| C. 定期のバッチ（前回以降を一括送信） | 単純。キューが不要 | 失敗した分の管理・重複・順序の管理が個別に要る。連携の結果の粒度が粗い（Aの簡略版として、頻度が低い場合は検討してよい） |
| D. 外部のメッセージキューサービス | 信頼性が高い | 費用・権限・構成要素が増える（NFR-1.6）。この規模では過剰 |

## 結果・トレードオフ

- 農業情報基盤の停止の影響を受けず、復旧後に連携できる。連携方式が変わっても、保存・評価の層は変わらない
- キューが滞留した場合のデータ量・保持期間の管理が必要。送信順序や重複の扱い（冪等性）は、連携方式の確定後に決める（TODO）
- 農業情報基盤への連携は可とする（決定。2026-10-23。#142 の D-35。基盤には、特定のユーザーしかアクセスできず、利用者が限定されるため）。連携対象の設定は、ロボット・環境センサーのデータ（手動入力を含む）、観点の分析結果、満足度などの手動入力、設備の名前・IDに限り、システムに登録するユーザー・設定のデータは、連携しない（NFR-5.5）
