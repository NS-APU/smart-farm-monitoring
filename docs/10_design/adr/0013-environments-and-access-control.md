# ADR-0013 評価環境は、開発サイトと本番サイトに分け、ログイン必須・管理者／一般の 2 ロールで制御する

- ステータス: 承認（2026-10-21。ユーザーの判断。Issue #78）。実装は、Issue #115・#116（未実装）。Issue #117（本番サイト）は、IaC・ワークフロー・手順を用意し、AWS に作成した（2026-10-22。operations.md 9.9）
- 日付: 2026-10-21
- 更新（2026-10-27。#148）: 開発サイトでの、実データによる結合確認の条件を、[ADR-0021](./0021-nonfunctional-ops-doc-rules.md) に記録した（6 章の TODO を置き換えた）。
- 関連: [ADR-0006](./0006-iac-cdk-and-same-origin-delivery.md)、[ADR-0008](./0008-cognito-authentication.md)、[ADR-0009](./0009-lambda-production-assembly.md)、[ADR-0010](./0010-client-ip-from-cloudfront-function.md)、[ADR-0012](./0012-demo-data-and-s3-file-server-mock.md)、[security.md](../../20_development/security.md)、[functional-requirements.md](../requirements/functional-requirements.md) の FR-9

目的: 評価する人が見る環境について、「どこから・どのデータで・どう更新するか」と、アクセス制御（ログイン・ロール・初期ユーザー）の方針を決めた記録を残す。

## 背景

- 評価環境は、現在 1 つ（`SfmData`・`SfmEvaluation`）で、ロールは 1 種類（`worker`＝農作業者。全権限）。ログインは必須だが、ログインした全員が、すべての操作をできる。
- 開発の間は、出来栄えを評価していただき、開発が一段落したら、現場での実証実験を行う。実証実験では、実際のデータを扱う可能性がある。開発の間の環境と、実証実験の環境が、同じでは、データ・ユーザー・更新のタイミングが、混ざる。
- アクセス制御（FR-9.5・FR-9.6）は、要件の確認事項（Q-017）が未確定で、「1 ロールでも 3 ロールでも、設定の変更で対応できる」構造だけを用意していた（architecture.md 9 章）。

## 決定

### 1. 環境を、開発サイトと本番サイトに分ける

| | 開発サイト | 本番サイト |
|---|-----------|------------|
| 目的 | 開発の間の、出来栄えの評価 | 現場での実証実験 |
| デプロイ元のブランチ | `develop`（基本）。動作確認のために、ほかのブランチに切り替えることがある（下の 4） | `main` |
| データ | **基本は合成データ**。実際のロボット・センサーとの**結合確認**では、実データを取り込むことがある（個人情報は不可。条件は、結合確認の前に決める。下の 6） | **実データ可（個人情報は不可）**。扱う条件は、実証実験の前に決める（下の 6） |
| 状態 | **現在の評価環境（`SfmData`・`SfmEvaluation`）が、開発サイト** | **AWS に作成した**（2026-10-22。Issue #117。`main` から、承認つき） |

- 2 つのサイトは、**データ・ユーザー・URL を共有しない**（別のスタック・別のテーブル・別のユーザープール・別の S3）。
- 開発サイトの名前（`SfmData`・`SfmEvaluation`）は、変えない。本番サイトは、環境変数 `SFM_ENVIRONMENT`（`development`（既定）・`production`）で、別の名前のスタック（`SfmProductionData`・`SfmProductionEvaluation`、独自ドメインのときは `SfmProductionEvaluationCertificate`）として作る（Issue #117）。
- **AWS のアカウント・リージョンは、開発サイトと同じ（東京）**（ユーザーの判断）。スタックの名前で分けるため、同じアカウントでも、リソース（テーブル・ユーザープール・バケット・関数・CloudFront）が衝突しない。
- **本番サイトは、合成データを生成する Lambda（デモ）を作らない**。ファイルサーバーのモックの S3 のバケットは、本番にも作る（Lambda には、ローカルのディレクトリがなく、未設定だと、取り込みが失敗し続け、失敗の通知が出続けるため）。空のまま（実ファイルサーバーのアダプタは、Issue #119）。`pnpm demo-data` は、本番サイトでは、実行できない（環境変数 `SFM_ENVIRONMENT=production` のとき、実行しない安全装置）。
- **GitHub の Environment は、開発サイトが `development`（旧 `evaluation` から改名。ユーザーの判断）、本番サイトが `production`**。GitHub Actions の OIDC のロールは、環境ごとに別（開発: `sfm-github-actions-deploy`、本番: `sfm-github-actions-deploy-production`）。それぞれ、対応する Environment のジョブだけが、引き受けられる（開発サイトのジョブは、本番のロールを引き受けられない）。ワークフローは、`deploy-development.yml`・`deploy-production.yml`（旧 `deploy-evaluation.yml` から改名）。

### 2. 評価する人・アクセス元

- 評価する人は、**登録されたユーザー**（**10 人程度**を想定）。アカウントは、管理者が作る（自己登録はない。ADR-0008）。
- アクセス元は、**インターネット**。**接続元 IP による制限は、特別に設けない**。WAF・レート制限も、設けない（費用。NFR-1.6。ログインの試行回数の制限は、これまでどおり、接続元ごと・Cognito のユーザーごと。ADR-0008・ADR-0010）。
- 関数の URL への直接の呼び出しで、ログインの試行回数の制限（接続元ごと）を回避できる点は、Issue #102（Backlog）。この方針（IP 制限なし・10 人程度）では、優先度は低い。

### 3. アクセス制御

- **ログインは、必須**。公開しているのは、ヘルスチェックとログインの API だけ。**多要素認証は、不要**。パスワードの条件・セッションの期限は、現状のまま（ADR-0008）。
- **初期ユーザーは、システムの構築時に、管理者のロールで作る**（`pnpm initial-user`。ADR-0008）。2 人目以降は、管理者が、画面（ユーザー管理）で作る。
- **ロールは、管理者・一般の 2 種類**（現在の 1 ロールを、分ける）。

| 操作 | 管理者（`admin`） | 一般（`general`） |
|------|:---:|:---:|
| ダッシュボード・観点の詳細・推移・観測値・通知の閲覧 | ○（全設備） | ○（**割り当てられた設備だけ**） |
| 手動入力の登録・修正・削除 | ○ | ○（割り当てられた設備に対して。**他人の入力にも**許す） |
| **自身のユーザー情報の編集**（ユーザー名・パスワード） | ○ | ○（自分の分だけ。ロール・ユーザー ID は、変えられない） |
| 設備の管理（登録・変更・削除） | ○ | × |
| 取り込みの設定・実行（即時取得を含む） | ○ | × |
| ステータスコードの管理 | ○ | × |
| 判断基準の編集 | ○ | × |
| ユーザーの管理（作成・変更・削除・ロール・閲覧できる設備の割り当て） | ○ | × |
| 操作履歴の閲覧 | ○ | × |
| 取り込みの状況・ログ、連携のログの閲覧 | ○（全設備） | ○（**割り当てられた設備に関するものだけ**。ユーザーの判断） |

- **一般ユーザーの閲覧範囲は、管理者が、ユーザーごとに、ハウス単位で割り当てる**（ユーザーの判断）。ハウス配下のロボット・センサーを含む。割り当てがない一般ユーザーは、何も閲覧できない（安全側）。割り当てのない設備は、**存在しないものとして**扱う（設備の有無を、漏らさない）。詳細は、Issue #116 で設計する。
- **取り込みの状況・ログ、連携のログは、現在、設備（ハウス）に結び付いていない**。取り込みの状況・ログは、**取り込み元（`robot`・`environment-sensor`）ごと**で、1 回の取り込みに、複数のハウスのファイルが含まれる（`IngestionLog` に、設備の項目はない）。連携のログは、送信のたびの全体の結果（件数・成否）で、これも設備の項目がない。このため、「割り当てられた設備に関するものだけ」を見せるには、**ログを、設備ごとに分けて持つ・導出する設計が要る**（例: 取り込みごとに、ハウスごとの件数・棄却数を記録する／観測値から、ハウスごとの最終取り込みの日時・件数を導く）。方式は、Issue #116 で決める（取り込み元の接続先・全体の件数・失敗の原因など、設備に分けられない項目は、一般ユーザーには見せない扱いになる見込み）。
- 現状との差: 現在は、1 ロール（`worker`）で、全員が全権限を持つ。実装（Issue #115・#116）まで、**この表のとおりには、動かない**。開発サイトの既存のユーザーは、管理者のロールに移す（Issue #115）。

### 4. 更新の方針

- **開発サイト**: **`develop` の更新で、自動デプロイする**（ユーザーの判断。トリガは、Issue #89 で実装した）。手動実行も残す（GitHub Actions の「Deploy development」）。**PR の前の動作確認のために、`develop` 以外のブランチも、デプロイできる**（ユーザーの判断。2026-10-22。PR をマージしないと、開発サイトで確認できなかったため。Issue #131）。GitHub の Environment `development` の、デプロイできるブランチは、`develop`・`feature/*`・`release/*`・`hotfix/*`（`main` は含めない）。Actions の「Use workflow from」で、確認したいブランチを選ぶ（選んだブランチに、ワークフローのファイルが要る）。確認のあとは、`develop` をデプロイして、戻す。**確認の間に `develop` が更新されると、自動デプロイで、確認中の環境が上書きされる**。確認中の上書きを避ける手段（例: 自動デプロイの一時停止）が要るかは、Issue #89 で決める。
- **本番サイト**: **`main` の更新で、自動デプロイする**（ユーザーの判断。Issue #89 と #117。トリガは、Issue #89 で実装した）。Environment は、デプロイできるブランチを `main` だけにし、**承認者による承認を必須にする**（ユーザーの判断。安全のため）。`main` の更新で、デプロイの実行が始まり、承認を待つ。**承認者は、T-Ishikawa-R のみ（自己承認を許可）**（ユーザーの判断。開発者が 1 人の間は、「確認してから本番へ」という停止点を置く。Required reviewers。Prevent self-review はオフ）。デプロイできるブランチは、Environment の設定（`main` のみ）と、ワークフローの条件（`github.ref`）の二重で守る。自動のトリガ（`main` の更新）は、Issue #89。
- **自動デプロイの対象と、CI との順序**（Issue #89）: 対象は、開発サイトが `develop` だけ、本番サイトが `main` だけ。デプロイは、**マージの直後（`push`）に動かし、CI の完了は待たない**。ブランチの保護（Rulesets）で、PR の CI（必須チェック。`main` 宛てはさらに E2E・負荷テスト）が成功しないと、`develop`・`main` にマージできないため、CI を通った内容だけが、デプロイされる。CI は `pull_request` でだけ動くため、`workflow_run` は使えない（また、`workflow_run` のワークフローは、既定のブランチ（`develop`）の上で動くため、本番の Environment（`main` だけ）では動かせない）。
- **確認中の上書きを避ける仕組みは、入れない**（ユーザーの判断。2026-10-22。Issue #89）。PR の前に、別のブランチを開発サイトに確認している間は、`develop` にマージしない、という手順で注意する（operations.md 8.3・git-workflow.md）。
- **評価する人への告知は、しない**（顧客向けの案内を作らないため。下の 5）。

### 5. 評価の進め方

- **フィードバック**: 会議・メール等で聞き取り、**開発者が Issue にする**。評価する人に、GitHub のアカウントを求めない（リポジトリは公開のため、直接書いてもらうと、内容が公開される）。Issue には、個人・組織が特定されない形で書く。Sprint 3 以降の優先度づけにつなげる。
- **期間**: 開発サイトは、開発が一段落するまで（期間は、決めない）。本番サイトは、実証実験の計画に従う（未定）。
- **顧客向けの案内（URL・ログインの方法・できること・既知の制約）は、作らない**。このスプリントの目標は、評価する人が見られる環境を用意することで、案内は、必須ではないため（ユーザーの判断）。

### 6. データの方針

- **共通**: リポジトリ・ログ・コミット・Issue・PR に、実データ・個人情報・秘密情報を入れない（AGENTS.md・security.md の既存の規約）。
- **開発サイト**: **基本は合成データ**（ADR-0012）。**個人情報は、入れない**。**実際のロボット・センサーのデータとの結合確認**のために、実データを取り込むことは、例外として許す（ユーザーの意向）。**結合確認の条件は、[ADR-0021](./0021-nonfunctional-ops-doc-rules.md)（#148 の D-53）に記録した**（取り込み元は実際のファイルサーバー・実データ用の別のハウス・設備に分離・結合確認の後はすみやかに削除・アクセスは本番と同じ）。決めた項目: 取り込み元（実際のファイルサーバーへの接続。FR-1.4・Q-002 が未確定で、**接続のアダプタも未実装**。Issue #119）・実施する期間・取り込む範囲・確認のあとの扱い（データの削除。`pnpm demo-data reset` など）・ログに出ないこと・アクセスできるユーザー（管理者のみ、など）・**合成データの定期生成（ADR-0012）との分離**（同じ取り込み元・同じ設備に、合成と実データが混ざらないようにする）。
  - 現状、ファイルサーバーのモックの S3 には、合成データだけを置く（ADR-0012）。実データの結合確認は、このモックではなく、実際の接続先で行う。
- **本番サイト**: **実データ可（個人情報は不可）**。**扱う条件（確定。ユーザーの判断。2026-10-22。Issue #117）**:

  | 項目 | 案 |
  |------|----|
  | 入れる時期 | 下の「前提」が、すべて済んでから。それまでは、本番サイトに、データを入れない（本番サイトは、作っただけでは、データがない） |
  | 取り込み元 | 実際のファイルサーバー（Issue #119。Q-002 の回答待ち）。ファイルサーバーのモックの S3 は、空のまま |
  | 保管の期間 | 1 年分（NFR-3.6）。保存期間（rfp.md 6 章。未確認）の確認後に、見直す |
  | バックアップ | ポイントインタイムリカバリ 35 日（データのスタックに設定済み）。実証実験の開始前と、大きな変更の前に、オンデマンドのバックアップを取る（backup-restore.md） |
  | 削除の方法 | 実証実験の終了後に、評価環境のスタックと、データのスタックを削除する（削除の保護を外したうえで。operations.md 9.7）。削除の前に、バックアップの要否を決める。`pnpm demo-data` は使えない |
  | ログに出ないこと | 実データ・個人情報・認証情報・トークンを、ログに出さない（security.md の既存の規約。構造化ログは、秘密情報らしい名前のフィールドをマスクする）。ログの保持は 30 日 |
  | アクセスできるユーザー | 登録されたユーザーだけ（自己登録なし）。最初は、管理者だけ。一般ユーザーへの設備の割り当て（Issue #115・#116）の後に、一般ユーザーを追加する |
  | ユーザー名・ID の扱い | 氏名など、個人が特定される名前を使わず、役割・組織の記号などの、匿名の識別子にする（ユーザー名も、個人情報に当たりうるため） |
  | 個人情報 | 入れない（手動入力の備考にも、書かない）。利用者への注意は、運用の案内で示す |
  | 前提（実データを入れる前に、完了させる） | Issue #115（ロールの分割。「最初は管理者だけ」を、仕組みで守るため）・#102（関数の URL への直接の呼び出しの対策。ログインの総当たりへの防御）・#127（配信のヘッダー（Cache-Control・CSP））・#128（独自のサブドメイン・TLS 1.2 以上）。取り込み元の実ファイルサーバーのアダプタ（#119）も、要る |

## 検討した代替案

| 案 | 採らなかった理由 |
|----|------------------|
| 接続元 IP による制限（許可リスト） | 評価する人の接続元が、複数の場所にわたり、一定でない。ログインを必須にした 10 人程度の登録ユーザーに対して、IP による制限は、特別に設けない（ユーザーの判断） |
| 環境を 1 つで運用する（開発と実証実験を、同じ環境） | 合成データと実データが混ざる。開発の更新（`develop`）が、実証実験の環境を、予告なく変える |
| ロールを 3 種類（管理者・評価者・閲覧者。構想時の案）にする | 管理者・一般の 2 種類にする（ユーザーの判断）。設定の変更で、後から増やせる構造は、維持する |
| 多要素認証 | 不要（ユーザーの判断）。Cognito は、必要になれば、後から有効にできる |
| 一般ユーザーに、全設備を閲覧させる | 担当の設備だけを見せる（ユーザーの判断）。実証実験で、現場ごとに、見せる範囲を分けられる |
| 開発サイトのデプロイを `develop` だけに限り、確認のたびに、ブランチを一時的に許可する | PR の前に、開発サイトで動作確認したい（ユーザーの判断。2026-10-22。Issue #131）。許可するブランチは、PR のもとになる名前に固定した |
| 本番サイトを、別の AWS アカウントに作る | ユーザーの判断で、同じアカウントにした（アカウントの用意・bootstrap・OIDC を、最初から行わずに済む。ただし、アカウント内の完全な分離にはならない） |
| 開発サイトの Environment を、`evaluation` のまま使う | ユーザーの判断で、`development` に改名した（Environment の名前を、サイトの名前に合わせる。移行の手順が要る） |
| 開発・本番を、1 つのワークフローで、入力（環境の選択）で切り替える | 環境ごとに、トリガ（自動デプロイの対象のブランチ）・承認・Environment・ロールが違うため、ワークフローを分けた（Issue #89 で、環境ごとのトリガを追加した） |
| 更新を、手動実行だけにする | 自動デプロイにする（ユーザーの判断。上の 4）。ただし、動作確認でブランチを切り替えている間に `develop` が更新されると、上書きされる（仕組みで防がず、手順で注意する。ユーザーの判断。Issue #89） |
| 開発サイトでは、実データを、一切入れない | 結合確認で、実際のロボット・センサーのデータを取り込むことがあるため（ユーザーの意向。上の 6） |

## 結果・トレードオフ

- **ロールの分割と、設備の割り当ては、まだ実装されていない**（Issue #115・#116）。それまでは、ログインした全員が、全権限を持つ。評価する人に見せる前に、少なくとも、Issue #115 を済ませるかは、ユーザーが判断する。
- **一般ユーザーごとの設備の割り当ては、データ・API・画面の変更が大きい**。ユーザーの判断で、全設備を見せる案ではなく、割り当てる案を選んだ（実装の大きさと、現場ごとの閲覧範囲の分離を、引き換えにした）。
- 自動デプロイ（Issue #89）により、`develop` に変更が入ると、開発サイトに反映される。動作確認でブランチを切り替えている間に、`develop` が更新されると、確認中の環境が上書きされる（仕組みで防がず、手順で注意する）。評価する人が使っている間にも、予告なく更新される（告知は、しない）。
- **取り込みの状況・ログを、設備ごとに絞るには、ログの持ち方を変える必要がある**（上の 3。Issue #116）。実装が大きくなる。
- 開発サイトで、結合確認の実データを扱うため、**個人情報を入れない・ログに出さない**ことを、結合確認の条件で、実施の前に決める（上の 6）。リポジトリは公開のため、結合確認の結果を、Issue・PR・docs に書くときは、実データ・個人・組織が特定される内容を含めない。
- IP 制限・WAF を設けないため、**ログインの総当たりに対する防御は、Cognito のロックと、接続元ごとの試行回数の制限だけ**（Issue #102 で、直接の呼び出しの回避の対策を検討する）。評価する人が、10 人程度で、合成データが中心の間は、許容する。本番サイトで、実データを扱う前に、Issue #102 で対策する（上の 6 の前提。Issue #117）。
- **本番サイトは、リリース（#84）の後に、`main` から、承認つきで、AWS に作成した**（2026-10-22。operations.md 9 章）。同じアカウントのため、**開発サイトのロールも、`cdk-*` のロールを引き受けられる**（本番のスタックを、技術的には、変更できる）。環境ごとの Environment・ロールで、通常の経路を分けるが、アカウント内の完全な分離ではない（別のアカウントにすれば分離できるが、ユーザーの判断で、同じアカウントにした）。開発サイトの Environment が許可するブランチは、PR のもとになる名前（`develop`・`feature/*`・`release/*`・`hotfix/*`）に絞った（「すべてのブランチ」にはしない）。担当者が増えたら、見直す。
- **開発サイトの Environment の改名（`evaluation` → `development`）に伴い、移行の手順が要った**（commands.md）。**2026-10-22 に完了した**（operations.md 9.9）。Environment の作り直しと、OIDC のロールの信頼条件の更新（`deploy:oidc`）。開発サイトの全リソースの `Environment` タグの値が、`development` に変わる（リソースの置き換えは、ない）。
