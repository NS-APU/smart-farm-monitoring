# ADR-0014 手動入力・設備・ステータスコード・判断基準の保存・削除の評価の再計算を、AWS では、応答から外し、定期の評価（JB-02）に任せる（手動入力は、「現在」だけ、応答の前に評価する）

- ステータス: 承認（2026-10-21。ユーザーの判断。Issue #123。背景は、Issue #79 の実測）
- 日付: 2026-10-21
- 更新（2026-11-28。Issue #591。ユーザーの判断。本文の決定 1〜3・結果・代替案は、この更新を反映した現在の内容に整理した）: **手動入力の保存・修正・削除（`deferred`）では、応答の前に、「現在」（短期の評価）だけを同期して評価する**。影響する設備とハウスの、短期の結果だけを、直近 7 日の観測値（定期の評価は 90 日）で評価して保存する（`evaluateCurrent`）。「期間の評価」（長期の結果）と、状態の変化の処理（通知・連携・記録）は、これまでどおり、定期の評価（JB-02）が行う。応答の評価の状態は `CURRENT`（失敗したときは `DEFERRED`）。評価結果の保存は、評価の日時が新しいときだけ行う（遅れて終わった古い評価が、新しい結果を上書きしない）。設備・ステータスコード・判断基準の登録・修正・削除は、これまでどおり、評価しない。詳細は、下の「更新（#591）」
- 関連: [ADR-0002](./0002-deployment-serverless.md)、[ADR-0009](./0009-lambda-production-assembly.md)、[ADR-0011](./0011-jobs-eventbridge-lambda.md)、[functional-requirements.md](../requirements/functional-requirements.md) の FR-4.1.5、[as-built.md](../architecture/as-built.md)

目的: 手動入力の保存・修正・削除と、設備・ステータスコード・判断基準の登録・修正・削除の応答を、データの量に左右されずに速くするため、AWS では、**全期間の評価の再計算を**、応答の前に行わない決定と、その影響を残す（手動入力は、「現在」だけを、応答の前に評価する。#591）。

## 背景

- 手動入力の保存・修正・削除は、応答の前に、影響する設備（センサー・ロボット）と、それを含むハウスの評価を、同期して再計算していた（`evaluateAffected`）。評価は、**直近 90 日の観測値**を読み、観点ごとに、短期・長期（1・7・30・60・90 日）の結果を計算して保存する。
- サーバーレス環境（AWS の評価環境）の実測（Issue #79。端末のブラウザから見た時間）:

| データ量 | 手動入力の保存（API） | 手動入力の削除（API） |
|----------|------------------------|------------------------|
| 3 日分 | 約 0.9 秒 | 約 1.0 秒 |
| 30 日分 | 約 2.4 秒（許容 3 秒に近い。超える回もあった） | 約 2.4 秒（3 秒を超えた） |

- サーバー側の処理時間（Lambda の `durationMs`）は、ブラウザから見た API の時間と、ほぼ一致した（通信の遅さではない）。Lambda のメモリの使用は、設定（1024 MB）の約 24 %。
- 評価結果の保存と、状態の読み出しを並列にした（PR #122）が、改善は、保存で約 0.8 秒、削除で約 0.1 秒にとどまった。
- **データの量に比例して遅くなる**（約 0.05 秒/日。**推定**）。評価は、90 日分を読むため、運用でデータが 90 日分以上たまると、保存・削除は、約 5〜6 秒になる見込み（直線で延ばした**推定**）。許容時間 3 秒（NFR に明示はなく、暫定として採った基準）を、大きく超える。

## 決定

### 1. AWS では、保存・修正・削除の応答の前に、全期間の評価を再計算しない

- 設定 `EVALUATION_ON_WRITE`（`sync`・`deferred`。既定 `sync`）を追加する。
  - `sync`（既定。**ローカル・E2E・負荷テスト**）: これまでと同じ。応答の前に、評価を再計算する。
  - `deferred`（**AWS の API の Lambda**。IaC が指定する）: **設備・ステータスコード・判断基準の登録・修正・削除・既定値へ戻す操作**では、評価を実行せずに応答する。**手動入力の保存・修正・削除**では、応答の前に、「現在」（短期の評価）だけを評価し（下の 3-2）、「期間の評価」（長期の評価）と、状態の変化の処理（通知・連携）は、行わない。実行しなかった評価は、**定期の評価（JB-02。5 分ごと）が更新する**（ユーザーの判断）。
- `deferred` でも、入力そのもの（手動入力・観測値・変更履歴・連携キュー）は、これまでどおり、応答の前に保存する。
- 全期間の評価の再計算を外すのは、**手動入力の保存・修正・削除と、設備・ステータスコード・判断基準の登録・修正・削除・既定値へ戻す操作**（手動入力は、「現在」だけを評価する）。取り込み（JB-01）の評価は、ジョブの中で実行する（応答の速さに関係しない）。
- 設備・ステータスコード・判断基準の変更後の評価は、手動入力と違い、全設備（`evaluateAll`。直近 90 日の観測値を、設備ごとに読む）を評価するため、データ・設備が増えると、API の Lambda の上限（29 秒）を超えうる。手動入力と同じ設定（`EVALUATION_ON_WRITE`）・同じ共通の関数（`evaluationWriteStateOf`・`reevaluateAllOnWrite`）で、`deferred` では、実行しない。

### 2. 応答と画面

- 手動入力の保存・修正・削除の応答の「関連する観点のステータス」（`viewpointStatuses`）は、`deferred` では、`current`（「現在」。いま評価した値）と、`period`（「期間の評価」。**前回の評価の値**。評価がまだなければ null）を、別々に返す（`status` は、短期・長期の悪い方）。
- 応答に、任意の項目 `evaluation`（`DONE`・`CURRENT`・`DEFERRED`）を追加する（共有のスキーマ。項目がなければ `DONE` とみなす）。手動入力は、`sync` で `DONE`、`deferred` で `CURRENT`（「現在」の評価に失敗したときは `DEFERRED`）。設備・ステータスコード・判断基準の登録・修正・既定値へ戻す応答にも、同じ項目を加える（`DONE`・`DEFERRED`。設備・ステータスコード・判断基準の本体に `evaluation` を加えた形）。設備・ステータスコードの削除は、204 から、200（`{ evaluation }`）に変える。
- 画面（データ入力 SC-06）は、`CURRENT` のとき、「入力内容を保存し、「現在」の評価を更新しました。「期間の評価」の更新は、定期の評価で行われ、反映には、数分かかります（表示は、前回の評価）」と表示し、関連する観点を、「現在」と「期間の評価」で別々に示す（修正・削除も同じ形）。`DEFERRED`（手動入力では、「現在」の評価に失敗したとき）は、「入力内容を保存しました。評価の更新は、定期の評価で行われ、ステータスへの反映には、数分かかります。関連する観点の、前回の評価のステータスです」と表示する。入力済みデータ一覧（SC-07）は、修正・削除の後も、同じ部品で、同じ表示（「入力内容を修正しました」「入力内容を削除しました」で始まる説明と、関連する観点のステータス）を示す（#150）。
- 設備（SC-10）・ステータスコード（SC-12）・判断基準（SC-13）の結果の通知（`ResultNotice`）は、`DEFERRED` のとき、メッセージの後に「評価の更新は、定期の評価で行われ、反映には、数分かかります」を加える（例: 「修正しました。評価の更新は、定期の評価で行われ、反映には、数分かかります」「保存しました。評価の更新は、定期の評価で行われ、反映には、数分かかります」）。判断基準の保存は、`DEFERRED` のとき、「現在の評価を更新しました」とは言わない。`DONE` のときは、従来どおり。

### 3. 反映までの時間

- 手動入力の「現在」（ダッシュボード・観点の詳細）は、**保存の応答の前に**更新する。「期間の評価」・通知、および、設備・ステータスコード・判断基準の変更後の評価（ダッシュボード・観点の詳細・通知）は、**最大 5 分**（JB-02 の間隔）で反映する。通知は、評価のあと、JB-04（1 分ごと）が配信する。設備を登録した直後は、JB-02 が評価するまで、その設備の評価は、まだない（ダッシュボードは、評価がないものとして示す）。
- ユーザーの判断として、まず、この方法（最も小さい変更）にする。5 分より短くする必要があれば、下の「検討した代替案」から、段階的に進める。

### 3-2. 手動入力は、「現在」だけを、保存の応答の前に評価する（#591）

- **背景**: 保存したのに、ダッシュボードにすぐ反映されないのは、操作として違和感がある。値だけを先に更新すると、診断・推奨アクションと食い違う。そのため、ダッシュボードを、「現在」（短期の評価）と「期間の評価」（長期の評価）に分け、「現在」だけを、保存の直後に更新する（評価の呼び名の整理は、#594・#595）。
- **評価の範囲**: 短期を持つ 6 観点（収穫精度・収穫速度・環境適応性・操作性・メンテナンス性・安全性）の、短期の結果。ハウスの結果は、配下の設備の短期の結果の最悪（保存済みの長期の結果は、集約に使わない）。
- **読む観測値**: 直近 7 日（`CURRENT_EVALUATION_READ_DAYS`）。短期の窓は 24 時間だが、累積の項目の基準（窓の直前の値）は、取得元・使える品質ごとの最新の値のため、24 時間分だけを読むと、定期の評価と結果が違うことがある（単体テストで確認）。7 日の範囲の観測値は、定期の評価と、同じ結果になる。7 日より前の基準は、設備・項目ごとの最新の値（取得元・品質を問わない）。**まれに（7 日より前の基準が、取得元ごとに違うとき）、「現在」の累積の値が、定期の評価と違い、次の定期の評価で、直る**。
- **通知・連携・状態の変化の記録は、しない**: 状態の変化の処理は、同じ回の既定の期間の長期の結果を起点にするため。通知は、最大 5 分遅れる。
- **保存の条件**: 評価結果の保存を、保存済みの結果より評価の日時が新しいときだけにした（同じ日時は上書き）。同時に動く別の評価（JB-02・取り込みの評価）が遅れて終わっても、新しい結果を上書きしない（DynamoDB の条件つきの書き込み）。
- **応答**: 評価の状態 `CURRENT`。関連する観点のステータスは、`current`（「現在」）と `period`（「期間の評価」。まだなければ null）を別々に返す。
- **費用・時間（仮定。実測は未確認）**: 読む観測値は、90 日分の約 1/13（7 日分）。1 回の保存で、読み取り約 700〜1,400 RRU（ADR-0007 の DynamoDB Local の実測〔15 分間隔で、ロボット 90 日 約 540 RRU・センサー 90 日 約 340 RRU〕を、ロボット 1 分・センサー 5 分の間隔に直線で換算し、7 日分にした値が約 710 RRU。強い整合の読み取りなら、2 倍）で、約 0.015〜0.03 円（AWS の公式の料金表。東京。2026-11-25 公開。0.1425 USD/100 万 RRU。1 ドル 150 円）。応答の時間は、90 日分で約 5〜6 秒の見込みだったものが、約 1〜1.5 秒と推定（ADR-0014 の実測の直線の換算。AWS では未実測）。インフラの変更は、ない。

### 4. 評価が更新されていない警告（#158。2026-11-23）

- 反映が定期の評価（JB-02）に任されるため、JB-02 が止まると、ダッシュボードの古い状態が、現在のものに見える。ダッシュボードは、**最終の評価の日時から、評価の間隔（5 分）× 3 回分 = 15 分以上**たっているとき、「評価が更新されていません（最終の評価: 日時）」の警告を出す。基準は、共有の定数（`EVALUATION_INTERVAL_MINUTES`・`EVALUATION_STALE_MINUTES`。`src/shared/constants/evaluation-schedule.ts`）で、評価のジョブの間隔（`DEFAULT_SCHEDULE` の JB-02）と一致することを、単体テストで確かめる。
- 現在の時刻は、端末の時計で判定する（API の変更はない。サーバーとの時計のずれは、考慮しない）。
- 「最終の評価」の横のヘルプヒントで、定期の評価（5 分ごと）と、反映が最大 5 分遅れることを説明する。運用側のアラームは、#429。

## 検討した代替案

| 案 | 採らなかった理由 |
|----|------------------|
| 保存・読み出しの並列化だけ | 実施した（PR #122）が、効果が小さく、データの量に比例する部分は、残る |
| Lambda のメモリを増やす（CPU が増える） | 計算の部分は速くなるが、90 日分では、見込みで約 3.3 秒で、足りない。インフラの設定の変更が要る。単独では、採らない（コールドスタートの対策としては、別に検討する） |
| JB-02 を 1 分ごとにする | 反映は最大 1 分になるが、ジョブの実行が 5 倍になる（費用がわずかに増える）。ユーザーの判断で、まず 5 分（現状の間隔）にする。必要になれば、追加する |
| 応答を返したあとに、同じ Lambda で評価を続ける（ストリーミング応答） | 反映は数秒だが、API の入口の書き換えとインフラの変更が要り、AWS でしか確かめられない（リスクが大きい） |
| 評価が必要な設備を DynamoDB に記録し、頻繁なジョブが処理する | 反映は 1 分程度だが、データ（スキーマ）の追加・新しいジョブ・ADR-0007 の更新が要る（変更が大きい） |
| 手動入力の応答の前に、全期間の評価（`sync`）に戻す（#591） | 90 日分の読み出しで、応答が約 5〜6 秒の見込み（上の背景。許容 3 秒を超える）。「現在」だけにして、直近 7 日の観測値で評価すると、約 1〜1.5 秒と推定（3-2。AWS の開発サイトで、3 秒以内を確認した。ユーザーの確認。数値は未記録） |
| 「現在」を、直近 24 時間の観測値だけで評価する（#591） | 累積の項目の基準（窓の直前の値）が、定期の評価と違い、6 つのデータセットのうち 3 つで、結果が違った（単体テスト）。直近 7 日にした（3-2） |
| すべての環境で、評価を遅らせる | 動作が 1 つになるが、E2E の期待（保存の直後に、ステータス・通知が変わる）を、多数変える必要がある。ユーザーの判断で、AWS だけにする |

## 検証（AWS の評価環境。2026-10-21）

30 日分のデータで、`deferred` にすると、手動入力の保存・削除が、データ量に依存せず、約 0.4 秒になった（`pnpm test:smoke`。端末のブラウザから見た時間。詳細は test.spec.md 13.3・`test-result/smoketest.result.log`）。

| 条件 | 保存（API） | 削除（API） |
|------|-------------|-------------|
| 30 日分・`sync`（PR #122 の前） | 3.17 秒（NG） | 2.57 秒（NG） |
| 30 日分・`sync`（PR #122 のあと） | 2.40 秒 | 2.44 秒（NG） |
| 3 日分・`sync` | 0.92 秒 | 0.97 秒 |
| **30 日分・`deferred`** | **0.30 秒** | **0.28 秒** |

## 結果・トレードオフ

- **保存の直後に、「期間の評価」（と、関連する観点の最終ステータス）が、最新にならない**（AWS。「現在」は、最新）。画面に、その旨を示す。設備・ステータスコード・判断基準の変更後は、評価の全体が、最新にならない。
- **異常な値を入力しても、通知が、最大約 6 分遅れる**（JB-02 の最大 5 分 + JB-04 の 1 分。手動入力の「現在」の評価は、通知を扱わない。#591）。HITL の早期対応への影響は、ユーザーが許容した（評価環境。10 人程度）。
- **AWS とローカル・E2E で、動作が違う**（`deferred` と `sync`）。違いは、設定（`EVALUATION_ON_WRITE`）に集約し、どちらも、結合テストで確かめる。E2E（`sync`）では、AWS の動作（遅延）を確かめられない。AWS では、`pnpm test:smoke`（Issue #79）で確かめる。
- JB-02（全設備の評価）は、データが増えると、実行時間が延びる（30 日分のデータで、Lambda の実行記録（REPORT）の 5 分間隔の実行が、約 3.6〜4.6 秒。JB-02 の実行と推定。ジョブの上限は 300 秒）。上限に近づく前に、評価の読み出し量そのもの（90 日分の観測値）を減らす方法（集計の事前計算など）を、別に検討する。
- 手動入力の削除の応答は、保存・修正と同じ形（200。`entry` は、削除済みの入力）で、評価の状態と関連する観点のステータスを含む（#150。以前は 204 で、含められなかった）。応答の前に、関連する観点のステータスの読み出しが、1 回加わる。
- 設備・ステータスコード・判断基準の変更後の評価を、応答から外すため、これらの応答の時間は、データの量に左右されない。AWS での所要時間・応答時間の実測は、未確認。
