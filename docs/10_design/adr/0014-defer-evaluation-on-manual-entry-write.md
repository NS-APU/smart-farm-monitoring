# ADR-0014 手動入力の保存・削除の評価の再計算を、AWS では、応答から外し、定期の評価（JB-02）に任せる

- ステータス: 承認（2026-10-21。ユーザーの判断。Issue #123。背景は、Issue #79 の実測）
- 日付: 2026-10-21
- 関連: [ADR-0002](./0002-deployment-serverless.md)、[ADR-0009](./0009-lambda-production-assembly.md)、[ADR-0011](./0011-jobs-eventbridge-lambda.md)、[functional-requirements.md](../requirements/functional-requirements.md) の FR-4.1.5、[as-built.md](../architecture/as-built.md)

目的: 手動入力の保存・修正・削除の応答を、データの量に左右されずに速くするため、AWS では、評価の再計算を、応答の前に行わない決定と、その影響を残す。

## 背景

- 手動入力の保存・修正・削除は、応答の前に、影響する設備（センサー・ロボット）と、それを含むハウスの評価を、同期して再計算していた（`evaluateAffected`）。評価は、**直近 90 日の観測値**を読み、観点ごとに、短期・長期（1・7・30・60・90 日）の結果を計算して保存する。
- サーバーレス環境（AWS の評価環境）の実測（Issue #79。端末のブラウザから見た時間）:

| データ量 | 手動入力の保存（API） | 手動入力の削除（API） |
|----------|------------------------|------------------------|
| 3 日分 | 約 0.9 秒 | 約 1.0 秒 |
| 30 日分 | 約 2.4 秒（許容 3 秒に近い。超える回もあった） | 約 2.4 秒（3 秒を超えた） |

- サーバー側の処理時間（Lambda の `durationMs`）は、ブラウザから見た API の時間と、ほぼ一致した（通信の遅さではない）。Lambda のメモリの使用は、設定（1024 MB）の約 24 %。
- 評価結果の保存と、状態の読み出しを並列にした（PR #122）が、改善は、保存で約 0.8 秒、削除で約 0.1 秒にとどまった。
- **データの量に比例して遅くなる**（約 0.05 秒/日。**推定**）。評価は、90 日分を読むため、運用でデータが 90 日分以上たまると、保存・削除は、約 5〜6 秒になる見込み（直線で延ばした**推定**）。許容時間 3 秒（NFR に明示はなく、暫定として採った基準）を、大きく超える。

## 決定

### 1. AWS では、保存・修正・削除の応答の前に、評価を再計算しない

- 設定 `EVALUATION_ON_WRITE`（`sync`・`deferred`。既定 `sync`）を追加する。
  - `sync`（既定。**ローカル・E2E・負荷テスト**）: これまでと同じ。応答の前に、評価を再計算する。
  - `deferred`（**AWS の API の Lambda**。IaC が指定する）: 手動入力の保存・修正・削除では、評価を実行せずに応答する。評価は、**定期の評価（JB-02。5 分ごと）が更新する**（ユーザーの判断）。
- `deferred` でも、入力そのもの（手動入力・観測値・変更履歴・連携キュー）は、これまでどおり、応答の前に保存する。
- 評価の再計算を外すのは、**手動入力の保存・修正・削除だけ**。取り込み（JB-01）の評価は、ジョブの中で実行する（応答の速さに関係しない）。設備・ステータスコード・判断基準の変更後の評価（管理者の、まれな操作）は、同期のまま。

### 2. 応答と画面

- 手動入力の保存・修正の応答の「関連する観点のステータス」（`viewpointStatuses`）は、`deferred` では、**前回の評価の値**（評価がまだなければ、空）。
- 応答に、任意の項目 `evaluation`（`DONE`・`DEFERRED`）を追加する（共有のスキーマ。項目がなければ `DONE` とみなす）。
- 画面（データ入力 SC-06）は、`DEFERRED` のとき、「入力内容を保存しました。評価の更新は、定期の評価で行われ、ステータスへの反映には、数分かかります。関連する観点の、前回の評価のステータスです」と表示する。

### 3. 反映までの時間

- 評価（ダッシュボード・観点の詳細・通知）への反映は、**最大 5 分**（JB-02 の間隔）。通知は、評価のあと、JB-04（1 分ごと）が配信する。
- ユーザーの判断として、まず、この方法（最も小さい変更）にする。5 分より短くする必要があれば、下の「検討した代替案」から、段階的に進める。

## 検討した代替案

| 案 | 採らなかった理由 |
|----|------------------|
| 保存・読み出しの並列化だけ | 実施した（PR #122）が、効果が小さく、データの量に比例する部分は、残る |
| Lambda のメモリを増やす（CPU が増える） | 計算の部分は速くなるが、90 日分では、見込みで約 3.3 秒で、足りない。インフラの設定の変更が要る。単独では、採らない（コールドスタートの対策としては、別に検討する） |
| JB-02 を 1 分ごとにする | 反映は最大 1 分になるが、ジョブの実行が 5 倍になる（費用がわずかに増える）。ユーザーの判断で、まず 5 分（現状の間隔）にする。必要になれば、追加する |
| 応答を返したあとに、同じ Lambda で評価を続ける（ストリーミング応答） | 反映は数秒だが、API の入口の書き換えとインフラの変更が要り、AWS でしか確かめられない（リスクが大きい） |
| 評価が必要な設備を DynamoDB に記録し、頻繁なジョブが処理する | 反映は 1 分程度だが、データ（スキーマ）の追加・新しいジョブ・ADR-0007 の更新が要る（変更が大きい） |
| すべての環境で、評価を遅らせる | 動作が 1 つになるが、E2E の期待（保存の直後に、ステータス・通知が変わる）を、多数変える必要がある。ユーザーの判断で、AWS だけにする |

## 結果・トレードオフ

- **保存の直後に、関連する観点のステータスが、最新にならない**（AWS）。画面に、その旨を示す。
- **異常な値を入力しても、通知が、最大約 6 分遅れる**（JB-02 の最大 5 分 + JB-04 の 1 分）。HITL の早期対応への影響は、ユーザーが許容した（評価環境。10 人程度）。
- **AWS とローカル・E2E で、動作が違う**（`deferred` と `sync`）。違いは、設定（`EVALUATION_ON_WRITE`）に集約し、どちらも、結合テストで確かめる。E2E（`sync`）では、AWS の動作（遅延）を確かめられない。AWS では、`pnpm test:smoke`（Issue #79）で確かめる。
- JB-02（全設備の評価）は、データが増えると、実行時間が延びる（30 日分のデータで、Lambda の実行記録（REPORT）の 5 分間隔の実行が、約 3.6〜4.6 秒。JB-02 の実行と推定。ジョブの上限は 300 秒）。上限に近づく前に、評価の読み出し量そのもの（90 日分の観測値）を減らす方法（集計の事前計算など）を、別に検討する。
- 手動入力の削除の応答（204）には、評価の状態を含められない。画面は、これまでと同じ「削除しました」を示す。
