# ADR-0026 ファイルサーバーの接続を、設備ごとに持つ（#367）

- ステータス: 承認（2026-11-19。Issue #367）。実装は完了（2 つの PR。下の「決定」の 9。PR B で、共通の接続を廃止した）。
- 日付: 2026-11-19
- 関連: [ADR-0022](./0022-file-server-http-connection-provisional.md)（接続の項目・検証・接続テスト・認証情報）、[ADR-0023](./0023-http-file-source-per-equipment-file.md)（設備ごとのファイルパス）、[ADR-0025](./0025-demo-http-file-feed.md)（MOCK の廃止）、[ADR-0016](./0016-ingestion-federation-rules.md)（SecretPort は D-55。設備ごとの取得間隔は D-11）、[security.md](../../20_development/security.md)、[functional-specification.md](../functions/functional-specification.md) SC-10・SC-11

目的: ファイルサーバーの接続（ホスト・ポート・プロトコル・認証方式・認証情報）を、取り込み元（ロボット・環境センサー）で共通の 1 つから、**設備ごと**に持つ形に変える方法を決める（#367）。

## 背景

- 取り込みは、設備ごとに 1 ファイルを `HEAD`・`GET` で取得する（ADR-0023）。取得間隔も、設備ごと（ADR-0016 D-11）。一方、接続は、取り込み元ごとの共通の 1 つで、設備ごとに別のファイルサーバーを使えない。
- 共通の接続のままだと、1 つの接続の失敗が、同じ種別のすべての設備の取り込みを止める。

## 決定

1. **共通の接続を廃止し、設備ごとに接続を持つ**。対象は、ファイルのパスを持つ、ロボット・センサー（ハウスは対象外）。ファイルのパスを設定して取り込む設備は、接続も必要（接続がなければ、取り込みは、「接続先が設定されていません」の失敗）。接続は HTTP だけ（項目・検証は ADR-0022 と同じ。内部アドレスの拒否なども、設備ごとに適用する）。
2. **保存先**: 設備の項目には持たず、取り込みの設定の 1 つの保存先（設備 ID → 接続。キー `ingestion.equipment-connections`）に持つ。設備（`GET /equipment`）は、ログインした利用者のだれもが読めるが、接続先は、取り込みの閲覧権限（`ingestion:read`）が必要なため。設備を削除したら、その設備の接続も削除する。
3. **認証情報**: 設備ごと。秘密情報の参照名は、`file-server/equipment/<設備 ID の SHA-256 の先頭 32 文字（16 進）>`（書き込み専用。値は、ログ・画面・履歴に出さない）。設備 ID は、大文字・100 文字まで使えるが、参照名は、小文字・1 階層 64 文字までのため、ハッシュにする（同じ設備 ID は、常に同じ参照名）。共通の認証情報（`file-server/<取り込み元>`）は、廃止する。設備を削除すると、その設備の認証情報も、削除する（設備の削除のジョブ〔JB-05〕が、保管先〔パラメータストア〕から削除する。ジョブの Lambda には、`file-server/equipment/` の下だけの削除権限を付ける。変更: #229。以前は、保管先に削除の機能がなく、残る仕様だった）。
4. **権限**: 設備ごとの接続の保存・削除・認証情報の登録は `ingestion:configure`、接続テストは `ingestion:run`、閲覧は `ingestion:read`（いまの取り込み設定と同じ）。設備そのものの登録・修正は、`equipment:manage`。
5. **API**: `PUT`・`DELETE /ingestion/equipment/{equipmentId}/connection`、`PUT /ingestion/equipment/{equipmentId}/credentials`、`POST /ingestion/equipment/{equipmentId}/test`。`GET /ingestion/settings` の、取り込み元ごとの設備の項目に、ファイルのパス・接続（未設定なら省略）・認証情報の状態を加える。共通の接続の廃止に伴い、取り込み元の `PUT /ingestion/{sourceId}/credentials`・`POST /ingestion/{sourceId}/test` は、削除した。`PUT /ingestion/settings` は、取り込み元ごとに `{ sourceId, isEnabled }` だけを受け取る。`GET /ingestion/settings` の取り込み元から、`connection`・`connectionRef`・`credentials` はなくなった。
6. **取り込みの実行**: 設備ごとの `HEAD`・`GET` で、その設備の接続・認証情報を使う。**失敗は、設備ごとに分ける**: 1 つの設備の接続の失敗（認証・停止など）が、他の設備の取り込みを止めない。失敗した設備には、設備ごとの失敗のログと、設備ごとの最終の実行（失敗）を残し、再試行は、失敗した設備のファイルだけにする。取り込みの結果は、取り込めた設備があれば一部成功、なければ失敗。通知は、取り込み元ごとに 1 回（設備名と、固定の理由の文言）。
7. **画面**: 設備の登録・修正のダイアログ（SC-10）に「取り込み元の接続」の欄（認証情報の入力・その設備だけの接続テスト・同じ種別の既存設備から接続をコピー〔認証情報は写さない〕）。SC-11 は、共通の接続の入力欄をなくし、設備ごとの接続先・状態の表にする（接続先は、接続先か「未設定」。接続の出どころの列は、ない）。設備ごとの接続の解除は、「未設定に戻す」。
8. **既存の設備の移行**: 移行コマンド `pnpm migrate-equipment-connections` が、共通の接続の値を、ファイルのパスを持つ各設備へ、1 回だけコピーした（認証情報は、コピーせず、設備ごとに、画面から入力し直す）。開発サイトで 1 回使い（2026-11-19）、PR B で、コマンドを削除した。本番サイトは、共通の接続を設定したことがないため、移行は不要。
9. **実装の分け方**: PR A（設備ごとの接続・取り込みの失敗の分離・画面・移行コマンド。共通の接続は、移行期間として残した）→ 運用者が、開発サイトで移行コマンドを実行 → PR B（共通の接続・共通の認証情報・共通の接続へのフォールバックの廃止、移行コマンドの削除、ADR-0022・0023・0025 の更新）。共通の接続・参照名は、保存済みでも、読み込むときに無視する（データの移行はしない）。共通の認証情報（`file-server/<取り込み元>`）は、パラメータストアに残っていれば、アプリからは削除できないため、運用者が、AWS で削除する（[operations.md](../../40_operations/operations.md) 8.10）。

## 結果

- 設備ごとに別のファイルサーバーを使える。1 台の接続の失敗は、他の設備の取り込みに及ばない。
- AWS のリソース・依存パッケージ・IaC の変更は、ない（秘密情報の保管先のパスは、既存の接頭辞の下）。データスキーマ: 取り込みの設定に、新しい保存先（設備 ID → 接続）が加わる。
- 費用: Parameter Store の標準パラメータは、保管・標準のスループットの API とも、追加料金なし（AWS の公式の料金ページ。2026-11-19 に確認）。設備ごとの認証情報の数は、数件〜数十件を想定（パラメータの件数の上限は、確認していない）。取り込みの 1 回ごとに、設定の読み取りが 1 件増える（金額の見積もり・実測は、していない）。
