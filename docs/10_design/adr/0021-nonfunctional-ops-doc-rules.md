# ADR-0021 非機能・運用・文書の規則を、恒久の仕様にする（#148 の決定）

- ステータス: 承認（2026-10-27。ユーザーの判断。Issue #148）
- 日付: 2026-10-27
- 関連: [ADR-0002](./0002-deployment-serverless.md)、[ADR-0006](./0006-iac-cdk-and-same-origin-delivery.md)、[ADR-0013](./0013-environments-and-access-control.md)、[ADR-0017](./0017-evaluation-rules.md)、[ADR-0018](./0018-manual-input-and-data-rules.md)、[architecture.md](../architecture/architecture.md) 10〜12 章、NFR-1.4・NFR-3.4・NFR-3.5・NFR-4.1・NFR-6.2・NFR-6.8、[use-cases.md](../requirements/use-cases.md)

目的: 非機能の目標値・運用体制・文書の形式・採用する機能の範囲など、暫定だった規則を、決めて、恒久の仕様にする。決めた経緯（背景・見直しの条件）は、各決定のコメント（#148）にもある。

## 背景

- 非機能の要求には、矛盾（稼働率 95% と月 4 時間以内）や、未定の事項（運用体制・初期構築コストの目安額）が、残っていた。
- 発注者の要求にはなく、受注者の提案として加えた機能（UC-13〜UC-22・UC-24）の扱いが、確認待ちのまま、すべて実装済みだった。
- このリポジトリは**公開**で、担当者の氏名・連絡先・過去の案件の詳細・ドメイン名は、書けない。

## 決定

### D-31 非機能の目標値

- **稼働率**: 計画停止を除くダウンタイムを、**月あたり 4 時間以内（約 99.4%）**とする**努力目標**（「95%」は削除）。AWS のサービスだけで、収まる見込み（公開 SLA の積は約 99.7%〔未確認〕）。
- **稼働の定義**: 画面と API が使えること（ヘルスチェック `/health` が成功）。計画停止（デプロイ・メンテナンス）は除く。農業情報基盤・ファイルサーバーの停止は、含めない。確認は、**自動の監視をせず**（NFR-1.5）、障害が起きたときに、期間を Issue に記録して、実績で判断する。
- **性能**: ダッシュボードの初期表示 3 秒以内・1 か月分の推移 10 秒以内・画面の更新 10 秒程度を、恒久化する（「暫定」を外す）。
- 見直しの条件: 実績で、目標を満たせないと分かったとき。発注者から、数値の指定があったとき。実証で、実データ量での実測が取れたとき。
- 発注者には、決めた値を、報告する（#248）。

### D-32 運用体制

- **受注者**が、稼働後の**運用・保守**（AWS 上の運用・デプロイ・障害対応・バックアップの確認・不具合の修正）と、**システムの管理者**（ユーザー・設備・設定の管理。利用者の問い合わせの窓口）を担う。**発注者（秋田県立大学）**は、AWS 環境を提供する（と、農業情報基盤を運用する）。
- 帰結: アプリの管理者ロールは、受注者の担当者（ADR-0020 により、2 名以上）。現場の農作業者は、一般ロール。判断基準の編集などは、管理者のみのため、**現場の依頼を受けて、受注者が行う**。
- 障害の受付: 利用者 → システムの管理者（受注者）→ 運用・保守の担当（受注者）。連絡先は、**リポジトリの外**で管理する（公開のため）。
- バックアップの復元の確認は、実証実験の開始前と、大きな変更の前に、運用・保守の担当が行う（回数・記録の様式は、決めない）。
- 見直しの条件: 稼働後の分担が、変わったとき（契約の終了後など）。
- 発注者には、報告する（#248）。

### D-34 初期構築コストの目安額

- **目安額は、設けない**。NFR-1.4 は、方針（設計の手段）として確定する。AWS の初期費用は、従量課金で、固定の初期費用がほぼない。開発の工数・費用は、契約の範囲で、本書では扱わない。

### D-49 提案の要件に対応するユースケース

- **UC-13〜UC-22・UC-24 は、受注者の提案として採用し、対象として恒久化する**。「提案」の記載は残し、「採用」と明示する。発注者には、採用した機能の一覧を報告する（#248）。

### D-51 バックアップ・復旧・更新

- **運用手順のままにする**（ユースケースにしない）。復旧・更新は、システム外（AWS・CI）の手順。見直しの条件: これらを、画面から行う機能を持つとき。

### D-52 ADR-0002 の前提

- 実績の記載は、「受注者のこれまでの知見（詳細は書かない）」に簡素化する。採用の根拠は、今回の環境で、実際に確認した権限（#70・#71）と、ほかの理由（固定費・冗長性など）に置く。無料枠は、使えない見込みとし、無料枠に依存しない見積もりを使う。

### D-53 開発サイトでの、実データによる結合確認の条件

- 取り込み元は、**実際のファイルサーバー**（#119）。最小の範囲で、**実データ用のハウス・設備を、別に作って、合成データと分離**する（別の設備 ID・設備ごとのファイルパス）。**結合確認ごとに、期間を決め、確認が終わったら、すみやかに、実データを削除する**（設備の削除〔ADR-0018〕。それまでは `pnpm demo-data reset`）。
- アクセスは、**本番サイトと同じ**（登録されたユーザーだけ。最初は管理者だけ）。#115・#116 の実装前は、実データがある間、登録するユーザーを、管理者に限る。ログに実データ・個人情報・認証情報・トークンを出さない。個人情報が含まれないことは、ユーザーが確認する。前提: #119・#206・#207。実施ごとに、Issue のコメントに記録する。

### D-54 依存パッケージの脆弱性確認

- **Dependabot alerts（有効済み）を、自動の確認とする**。CI に `pnpm audit` は、加えない（新しい勧告で、無関係の PR が失敗するため）。`pnpm audit` は、補助。Dependabot の自動更新 PR は、有効にしない（更新は、人が確認して行う）。**シークレットスキャン・プッシュ保護を有効にする**（#249。ユーザーが設定）。

### D-56 AWS の費用・無料枠の比較表

- architecture.md 11.5 の比較表は、**暫定の概算**（公式の料金表で未確認）と明記し、TODO を外す。無料枠は、**使えない見込み**で、無料枠に依存しない見積もりとする。実際の費用は、請求で確認する（自動の監視なし）。評価の読み取り費用は、#232 で再試算する。

### D-57 独自のサブドメイン・証明書

- 独自のサブドメインを使うことを、決定として記録する。実施は、#128（ユーザーが実行）。

### D-58 API 仕様の形式

- **機能仕様書の表と、共有のスキーマ（`src/shared/schemas/`。Zod）**のまま。入出力の詳細は、共有のスキーマが正。OpenAPI 等は、使わない。見直しの条件: 外部のシステムが、API を使うことになったとき。

## 結果・トレードオフ

- 非機能・運用・文書の TODO が、決定に置き換わる。実装は、シークレットスキャンの有効化（#249。ユーザーの設定）だけで、コードの変更はない。
- 稼働率は、測る仕組みを持たない努力目標で、障害時の記録で補う。
- 運用・保守とシステムの管理者を、受注者が担うため、契約の終了後の運用は、別に決める必要がある。
- 実データを、開発サイトに、残さない（確認後に削除）ため、デモ・顧客への提示は、合成データか、本番サイトで行う。

## 発注者への確認事項

依頼文の送付は、ユーザーが行う（AI は、文面・項目の案を用意する）。

- **報告事項**（#248）: 稼働率の目標・運用体制・採用した機能の一覧。
