# ADR-0024 農業情報基盤との連携を、NGSI-LD（Orion-LD）の upsert で行う（#176）

- ステータス: 承認（2026-11-13。ユーザーの判断。Issue #176）。実装は #177
- 日付: 2026-11-13
- 関連: [ADR-0004](./0004-federation-outbox-standalone.md)（連携キュー・FederationPort）、[ADR-0015](./0015-provisional-policy-external-specs.md)（農業情報基盤は、私たちで調査して決める）、[ADR-0016](./0016-ingestion-federation-rules.md)（D-06 停止中の扱い・順序に依存しない時系列）、[architecture.md](../architecture/architecture.md) 5.3、FR-8 / NFR-2.2 / Q-005

目的: 農業情報基盤（FIWARE。Orion-LD・QuantumLeap）への連携の方式（API・データモデル・頻度・認証）を決める（D-05。連携の範囲は D-35）。実装は #177。

## 背景

- 農業情報基盤は、私たちが以前に作成したもので、**NGSI-LD**（Orion-LD）と、時系列の蓄積の **QuantumLeap** で構成されている。インターネットに公開されていて、**認証はない**（ユーザーの記憶による）。複数のテナントを、`NGSILD-Tenant` ヘッダーで分けられる。**ふだんは停止していて、起動は、ユーザーが、開発・実証実験のタイミングで行う**（起動の間隔は、決まっていない）。
- 既存のエンティティの定義と、2025 年度のインターフェース資産は、ない（NFR-2.8）。モデルは、スマートデータモデル（Environment）を参考に、こちらで設計する。
- 基盤のデータは、Grafana などで読まれる。
- 本システムの側には、連携キュー（ADR-0004）と `FederationPort`（`send(items)`）があり、モックだけが実装されている。キューに積むのは、観測値（自動取り込み・手動入力・満足度。取り込んだファイルごと・手動入力ごと）と、評価結果（観点のステータスが変わったとき）。

## 決定

### 1. API・向き

- 本システムから送る（プッシュ）。NGSI-LD の **`POST {endpoint}/entityOperations/upsert?options=update`**（複数のエンティティを、配列で送る。`options=update` は、送った属性だけを更新し、ほかの属性を消さない）。
- ヘッダー: `NGSILD-Tenant`（テナント名）、`Content-Type: application/json`、`Link`（context の URL。`rel="http://www.w3.org/ns/json-ld#context"; type="application/ld+json"`）。
- HTTP クライアントは、Node の `http`・`https`（依存の追加なし）。接続先を管理者が設定できるため、ファイルサーバーの接続（ADR-0022）と同じ SSRF の対策（内部のアドレスへの接続の拒否・名前の解決の検査・リダイレクトに従わない・失敗の文言に接続先・本文を含めない）を守る（`fetch` では、接続の直前の名前の解決を検査できないため、`fetch` は使わない）。タイムアウトは、連携の設定（`ioTimeoutMs`）に従う。1 回の要求に含めるエンティティは、100 件まで。
- 結果の対応（`FederationPort` の契約）:

| 結果 | 例外 | キューの状態 |
| --- | --- | --- |
| 2xx（すべて成功） | なし | 送信済み |
| 接続できない・タイムアウト・5xx・502／503／504 | `FederationUnavailableError` | 保留 |
| 連携先が未設定・無効 | `FederationUnavailableError`（積んだ項目は、期限の判定も、これまでどおり行う） | 保留 |
| 4xx・207（一部が失敗） | `FederationRejectedError`（メッセージに、データの内容・接続先を含めない） | 失敗 |

### 2. 設定（連携先）

- 設定項目: **接続先（エンドポイントの URL。http・https）・テナント名（既定 `smart_farm_monitoring`）・context の URL・有効／無効**。**固定せず、画面（SC-11）から変更できる**（画面は、#177 の PR 3。PR 1 では、保管と読み出し〔`federation-connection-store.ts〕まで）。
- **方式の切り替え**: 環境変数 `FEDERATION_MODE`（`mock`〔既定。ローカル・テスト〕／`ngsi-ld`）。`ngsi-ld` のとき、接続先が未設定・無効のあいだは、連携を**保留**にする（モックのように、受け取ったことにしない。積んだ項目は、破棄の期限の判定を受ける）。AWS の評価環境を `ngsi-ld` にするのは、画面で接続先を設定できるようになってから（PR 3 のあと。IaC の変更は、あなたがデプロイする）。
- 接続先は、ファイルサーバーの接続設定（#207・ADR-0022）と同じ仕組みで、**書き込み専用**（画面・ログ・エラーメッセージに出さない。`SecretPort` に置く）。テナント名・context の URL・有効／無効は、通常の設定。**接続先・認証情報・ホスト名を、リポジトリ・Issue・PR に書かない**（リポジトリは公開）。
- 更新できるのは、連携の管理の権限を持つ利用者（取り込み設定と同じ）。変更は、変更履歴に残す。
- 接続の確認（テスト）の操作を持つ（接続先に、読み取りの要求だけを送る。データは、書き込まない）。

### 3. 認証・暗号化

- **認証は、基盤にも本システムにも、設けない**（ユーザーの判断。2026-11-13）。接続先の URL は、http・https のどちらも設定できる（https を勧める）。
- **リスクを承知のうえの決定**: D-35（ADR-0004）で連携を可としたのは、基盤に特定のユーザーしかアクセスできない前提だった。認証がなく、インターネットに公開されている間は、**送った運用データ（NFR-5.5 で機密扱い）を、誰でも読め、書き換えられる**。見直しの条件: 実データの機密性が問題になったとき、基盤に認証（リバースプロキシの API キーなど）が入ったとき（アダプタは、認証ヘッダーを足せる構造にしておく）。

### 4. データモデル

エンティティの識別子は、`urn:ngsi-ld:{型}:{設備の ID（URN で使えない文字は、パーセントエンコード）}`。**設備を削除して、同じ ID で登録し直しても、同じエンティティに続ける**（D-28。基盤のデータは、削除しない）。

context は、本システムの用語を定義した JSON-LD（独自の型・属性）を、**このリポジトリに置き（[ngsi-ld-context.jsonld](../data/ngsi-ld-context.jsonld)）、GitHub の raw の URL を、設定の context URL にする**（独自の context は、スマートデータモデル（Environment）の context を取り込み、独自の用語は `@vocab` で定義する）。context URL の既定は、`develop` の raw の URL（リリース〔v0.5.0。#343〕のあとに、タグの URL に切り替える）。機密情報は含まない。

| エンティティ | 型 | 対象 | 主な属性 |
| --- | --- | --- | --- |
| 設備（D-35: 名前・ID） | `Greenhouse`（ハウス）・`HarvestRobot`・`EnvironmentSensor`（独自） | 設備ごと | `name`、`refGreenhouse`（Relationship。ハウスは持たない） |
| 環境（標準） | **`IndoorEnvironmentObserved`**（スマートデータモデル） | 環境の項目を持つ設備ごと | `temperature`（℃）・`relativeHumidity`（%）・`illuminance`（lx）・`co2`（ppm）、`dateObserved`、`refDevice`（センサーのとき） |
| 設備の観測 | `EquipmentObserved`（独自） | 環境以外の項目を持つ設備ごと | 項目ごとの属性（下記） |
| 評価 | `ViewpointEvaluation`（独自） | 設備×観点ごと（`urn:ngsi-ld:ViewpointEvaluation:{設備}:{観点}`） | `status`、`diagnosticMessage`、`recommendedAction`、指標ごとの数値、`refEquipment` |

- **属性の形**: 観測値は、`Property`（`value`・`unitCode`・`observedAt`・`source`）。`observedAt` は、計測日時（UTC）。`source`: `AUTO_IMPORT`・`MANUAL`（属性ごとの付随の項目）。
- **単位**: こちらの単位のまま送り、`unitCode`（UN/CEFACT）を付ける（温度 `CEL`・湿度 `P1`〔%〕・照度 `LUX`・CO2 `59`〔ppm〕・時間 `HUR`・分 `MIN`・秒 `SEC`・件数・回数 `C62`）。標準モデルの単位との違い（湿度は 0〜1、CO2 は mg/L とする記載がある）は、`unitCode` で示す。円は、`unitCode` を付けず、context で定義する。
- **属性名**: 環境の 4 項目は、標準の名前（`temperature`・`relativeHumidity`・`illuminance`・`co2`）。そのほかは、項目の識別子（`itemKey`）のまま。識別子に `.` を含む満足度（`satisfaction.xxx`）は、`satisfactionXxx`（ローワーキャメル）にする。ステータスコードは、コードの文字列（`statusCode`）。
- **送らないもの**: 値が使えない観測値（品質が不正・欠損のもの）、手動入力の**備考・入力者**（利用者のデータ。D-35 の範囲外）、ユーザー・設定のデータ。
- 評価の指標は、数値の属性に平らにする（Grafana で、そのまま引けるようにする）。属性名は、指標の識別子の `metric` + ローワーキャメル。

### 5. 頻度・順序・冪等性

- **観測値**: 取り込み・手動入力の都度、連携キューに積む（現状のまま）。連携ジョブ（JB-03。5 分ごと）が、5 分ごとに最大 100 項目（バッチの件数）ずつ送る（1 日で最大 約 28,800 項目）。
- **評価**: **観点のステータスが変わったときだけ**送る（現状のまま。ユーザーの判断。Issue の「評価を行ったタイミング」は、「変化を検出した評価」とする）。
- **設備**: 設備を登録・修正（名称・ハウス）したとき、キューに積む。連携を設定したあとの初回に、既存の設備を、まとめて積む。削除では、何も送らない（D-28）。
- **順序**: 順序は保証しない（D-06）。時系列は、QuantumLeap が、計測日時（`observedAt`）で持つため、順序が入れ替わっても、時系列は成り立つ。基盤の「現在の値」（Orion の属性）は、最後に書いた値になる（古い値が、あとから届くと、一時的に古い値になる。次の値で直る）。
- **同じエンティティの複数の時刻**: 1 回の要求には、同じエンティティを 1 つしか入れられない。同じエンティティで、時刻が複数あるときは、時刻の古い順に、要求を分ける。
- **冪等性**: 同じ（エンティティ・属性・計測日時）を再送しても、時系列に重複が残らないことを、基盤側で確認する（確認事項。後述）。再送は、本システムでは、そのまま許す（ADR-0016 の D-06）。
- **停止中の運用**: 基盤は、ふだん停止している。**破棄の期限は、既定 30 日のまま**（設定で変えられる。ユーザーの判断。起動の間隔が 30 日を超えると、その間のデータは、基盤に届かない）。**停止中の再試行の間隔の上限は、12 時間から 60 分に縮める**（起動後、最大 60 分で再開する）。

### 6. 基盤側の準備と確認（ユーザーの作業）

- QuantumLeap への**購読**（Orion-LD → QuantumLeap）を、型（`IndoorEnvironmentObserved`・`EquipmentObserved`・`ViewpointEvaluation`）ごとに、テナントを指定して作る。
- 確認すること: ① `entityOperations/upsert?options=update` が使えること。② QuantumLeap が、NGSI-LD の通知を受けて、`observedAt` を時刻にすること。③ 同じ（エンティティ・時刻）の再送で、重複が残らないこと。④ テナントが、初回の書き込みで作られること。確認の手順は、#177 で用意する。

## 検討した選択肢（主なもの）

| 項目 | 案 | 採否・理由 |
| --- | --- | --- |
| 連携の API | 観測値ごとに、別のエンティティを作る | 採らない。エンティティが増え続け、基盤の負荷が大きい |
| | 時系列の API（temporal）に、直接書き込む | 採らない。基盤が、QuantumLeap の構成で、使えるか不明 |
| | **エンティティを、設備ごとに 1 つ持ち、属性を更新する（採用）** | 順序に依存しない時系列（D-06）を、QuantumLeap で実現できる |
| 環境センサーの型 | `AirQualityObserved` | 採らない。位置情報（`location`）が必須で、本システムにない |
| | **`IndoorEnvironmentObserved`（採用）** | 温度・湿度・照度・CO2 を、1 つの型で持ち、必須の属性は、時刻だけ |
| 単位 | 標準モデルに合わせて変換する | 採らない。CO2 の ppm → mg/L は、温度・気圧に依存し、近似になる |
| context | 送るデータに埋め込む | 採らない。QuantumLeap の購読が、用語を展開できない可能性がある |

## 結果・トレードオフ

- 認証がないため、連携したデータは、公開される（上記のリスク）。基盤の側で認証を入れたときは、アダプタに認証ヘッダーを足す（本システムの変更は、小さい）。
- 基盤が停止している間は、キューが溜まり、保持の費用が増える（概算・未実測。1 日 約 1,700 項目・1 項目 約 3〜5 KB の仮定で、30 日で 数百 MB）。期限を超えると、破棄され、基盤に届かない。
- 基盤の起動が、決まった間隔でないため、停止の期間は、予測できない。必要なら、破棄の期限を、設定で延ばす（最大 365 日）。
- 独自の context を、リポジトリに置くため、用語を変えるときは、context の変更が要る（基盤の過去のデータの用語は、変わらない）。
