# ADR-0023 HTTP のファイルサーバーの取得を、設備ごとのファイルパスで行う（#119）

- ステータス: 承認（2026-11-06。ユーザーの判断。Issue #119）。暫定（宇都宮大学のファイルサーバーへの接続で見直す。#298）
- 日付: 2026-11-06
- 関連: [ADR-0022](./0022-file-server-http-connection-provisional.md)（接続の設定・接続テスト・内部のアドレスの拒否）、[ADR-0003](./0003-ingestion-adapter-and-provisional-spec.md)（取得と解釈の分離）、[ADR-0015](./0015-provisional-policy-external-specs.md)（1 ファイルを随時更新する方式）、[architecture.md](../architecture/architecture.md) 5.1、[data-dictionary.md](../data/data-dictionary.md) 2 章、[functional-specification.md](../functions/functional-specification.md) SC-10・SC-11

目的: HTTP の `FileSourcePort`（一覧・取得）を作るにあたり、「どのファイルを取得するか」を、取り込み元ごとの接続設定ではなく、**設備ごとのファイルパス**で決める。あわせて、HTTP の一覧・取得・接続テストの動作を記録する。

## 背景

- ADR-0022 では、接続設定（`connection`）に `filePath` を持たせ、**1 取り込み元 = 1 ファイル**とした。取り込み元は、ロボットデータ・環境センサーデータの 2 つ。
- 実際には、ロボット・環境センサーの**設備ごとに、別のファイル**になる想定（ロボット 1 台・環境センサー 1 台なら、2 ファイル。1 ファイルが 1 設備）。ファイルの中の機体 ID・センサー ID（`externalId`）は、ファイルの内容を設備に対応づけるために引き続き使う（ADR-0003）。
- 宇都宮大学のファイルサーバーは、ここでは扱わない（#298）。汎用の HTTP サーバー（自前・公開）で、接続と取り込みを確かめる。

## 決定

### 1. ファイルパスは、設備（ロボット・センサー）が持つ（実装: PR 1）

- 設備に、任意の `sourceFilePath` を持たせる。形式は、ADR-0022 の `filePath` と同じ（`/` で始まる、ファイル 1 つ。英数字と `. _ ~ ! $ & ' ( ) * + , ; = : @ / -` のみ。`..`・`?`・`#`・空白・`%` は使えない。500 文字以内）。検証は、共通のスキーマ（`FilePathSchema`）で行う。
- **ハウスは、持てない**（取得するファイルがない）。ロボット・センサーだけに指定できる（API は 400）。
- **同じ種別の設備の中で、一意**（重複は 409。削除済みの設備は、数えない）。`externalId` と同じ扱い。
- 変更履歴の登録・修正の記録に含める（ホスト・認証情報と違い、秘密情報ではなく、管理者だけが参照できる）。
- 修正で省略すると、解除する（`externalId` と同じ）。
- データスキーマの変更: 設備に、任意の項目を 1 つ足す。**既存の設備は、未設定のまま**（移行は、不要）。IaC・依存パッケージの変更は、ない。

### 2. 取得の対象は、ファイルパスが設定された設備のファイル（実装: PR 2）

- **一覧（`listFiles`）**: ファイルパスが設定された設備（取り込み元の種別に合う、有効なもの）ごとに、`HEAD` で、ファイルのメタデータ（大きさ・更新日時）を得る。`fileId` は、ファイルパスとする。更新日時の古い順。
- 更新日時は、`Last-Modified` を使う。**`Last-Modified` がないサーバー**（GitHub の raw など）は、`ETag`・`Content-Length` がないときも含め、確認の時刻を更新日時とみなし、**毎回、取得する**（変わっていないときの無駄な取得の回避〔D-08〕は、更新日時があるサーバーだけ）。
- **取得（`readFile`）**: `GET`。UTF-8 のテキスト。大きさの上限を超えたら、失敗として扱う（本文を読み切らない）。
- **接続テスト**: ファイルパスが設定された最初の設備のファイルを、`HEAD` で確かめる（ADR-0022 の 2 の手順）。**設定された設備がなければ、「ファイルパスが設定された設備がありません」**として失敗する。
- 接続設定の `filePath` は、**廃止する**。保存済みの設定にある `filePath` は、読み出すときに、無視する（移行）。
- リダイレクトに従わない・内部のアドレスの拒否（接続の直前の名前の解決の検査）・認証（Basic・Bearer・API キー）・認証失敗時の 1 度の再試行・エラーの理由だけを出す（接続先・ファイルパス・認証情報を含めない）は、ADR-0022 のとおり、一覧・取得にも共通で適用する。

## 検討した選択肢

| 選択肢 | 判断 |
|--------|------|
| 取り込み元の接続設定に、複数のファイルパスを持たせる | ファイルと設備の対応が、設備の登録と離れる。設備を追加・削除したときに、2 か所を直すことになる |
| ディレクトリの一覧（HTTP のインデックス）から、ファイルを探す | HTTP では、一覧の形式が決まっていない（サーバーごとに違う）。設備ごとに明示する方が、確実で、安全（任意のパスを辿らない） |
| 設備ごとのファイルパスを、別のテーブル・設定に持つ | 設備の登録・削除と、整合を取る手間が増える。設備に持たせる方が、小さい |
| ファイルパスを、必須にする | 既存の設備・モック（ディレクトリ・S3）の取り込みでは不要。任意にして、HTTP のときだけ使う |

## 結果

- ロボット・センサーの登録・修正（SC-10）で、ファイルパスを設定できる。一覧に表示する。
- 取得のアダプタ（PR 2）は、設備の登録だけで、取得するファイルが決まる。
- 見直しの条件: 宇都宮大学のファイルサーバーの実際の構成（ファイルの置き方・更新日時の返し方）が分かったとき（#298）。1 設備が複数のファイルを持つ必要が生じたとき。
