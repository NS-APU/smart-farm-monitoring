# ADR-0011 ジョブ（JB-01〜JB-04）を、EventBridge から Lambda で実行し、DynamoDB のロックで重複を防ぐ

- ステータス: 承認（2026-10-20。ユーザーの判断。Issue #76）
- 日付: 2026-10-20
- 関連: [ADR-0002](./0002-deployment-serverless.md)、[ADR-0006](./0006-iac-cdk-and-same-origin-delivery.md)、[ADR-0007](./0007-dynamodb-table-design.md)、[ADR-0009](./0009-lambda-production-assembly.md)、[architecture.md](../architecture/architecture.md) 3.2 節、[as-built.md](../architecture/as-built.md)「ジョブ」

目的: 取り込み・評価・連携・通知の配信のジョブを、サーバーレス構成で、定期的に実行するための決定（起動・構成・重複の防止・再試行）を残す。

## 背景

- ジョブは、ローカルでは、Node サーバーの中のスケジューラ（`createScheduler`）が、`JobRunner` の同じ入口で実行する。Lambda には、タイマーも、常駐するプロセスもない（API の Lambda は、スケジューラを使えない。ADR-0009）。
- 同一プロセスの中の排他（取り込み元ごとの `running`）は、Lambda の複数の実行環境（同時に起動した複数の Lambda）の間では、効かない。EventBridge は、前回の実行が終わる前に、次の起動をしうる（ジョブが、起動の間隔より長くかかったとき）。また、起動の再配信もありうる。同じジョブが、同時に動くと、通知の配信（Web Push）・農業情報基盤への連携が、二重になる。

## 決定

### 1. 起動と構成

- **ジョブ専用の Lambda を 1 つ**（`runtime/job-lambda.ts`。API の Lambda とは別。バンドルは、API と同じ方式）。API の Lambda と同じ組み立て（コンテナ。`parseLambdaConfig`）を使い、`JobRunner` の同じ入口から実行する。ローカルのスケジューラ・開発用 API・テストと、同じ処理になる。
- **EventBridge のルールを 4 つ**（JB-01 は 1 分・JB-02 は 5 分・JB-03 は 5 分・JB-04 は 1 分）。実行間隔は、ローカルのスケジューラの `DEFAULT_SCHEDULE`（`application/jobs/job-schedule.ts`）と、同じ定数から作る。ルールの入力は、`{ "jobId": "JB-01" }`。Lambda は、入力を検証し（想定外の入力は、内容を出さずに拒否）、そのジョブを実行する。
- **ローカルの動作は、変えない**（Node サーバーのスケジューラ）。Lambda の中では、スケジューラは動かさない（`SCHEDULER_ENABLED` は、常に無効）。
- 関数は、Node.js 24・ARM・メモリ 1024 MB・**タイムアウト 300 秒**（初期値。実測による調整は Issue #79）。ログの保持期間は、API と同じ 1 か月。
- **IAM は最小権限**: DynamoDB の 2 テーブル（インデックスを含む）への、必要な操作だけ（API と同じ）。**Cognito の権限は付けない**（ジョブは、認証を使わない）。

### 2. 重複の防止（DynamoDB のリース式ロック）

- ジョブは、実行の前に、`job:{jobId}` のロックを取る。**取れなければ、何もせずに終わる**（`SKIPPED`。ログに残す）。ロックは、ジョブごと。別のジョブは、同時に実行できる。
- ロックは、`Main` テーブルの項目 `JOBLOCK` / `job:{jobId}`（`owner`・`expiresAt`・`ttl`）。取得は、「項目がない、または、期限が過ぎている」ときだけ成功する、条件つきの書き込み。同時に取りに来ても、1 つだけが成功する。解放は、「自分が取ったロック」のときだけ、期限を 0 にする（期限が過ぎて、別の実行に取られていたら、何もしない）。項目は、TTL で自動で消える。
- **ロックの期限（リース）は 360 秒**（Lambda のタイムアウト 300 秒 + 60 秒）。実行中に、期限が切れて、次の実行が始まらないようにする。実行が異常終了（タイムアウト・クラッシュ）して、ロックが解放されなくても、最長 360 秒で、次の実行が取れる。
- ジョブが失敗しても、ロックは解放する。ロックの解放に失敗しても、ジョブの結果は、隠さない（警告を残す）。
- `Main` テーブルの設計（ADR-0007）への追加: パーティション `JOBLOCK`。アクセスパターンは、キーによる条件つきの更新のみ（Query・Scan は使わない）。

### 3. 失敗と再試行

- ジョブが失敗したら、**例外を投げる**（CloudWatch のログ・Lambda のエラーの指標に残る）。
- **再試行はしない**: EventBridge の配信の再試行は 0、起動の時刻から 1 分を過ぎたイベントは捨てる。Lambda の非同期の自動の再試行も 0。ジョブは、次の周期（1 分または 5 分）で、また実行される。失敗した実行が、あとから、二重に配信を起こすことを避ける。
- ジョブは、同じ契機が重複しても結果が変わらない（冪等）ように実装されている（取り込みは、取り込み済みのファイルを記録する）。ロックは、冪等でない部分（Web Push の配信・農業情報基盤への送信）の二重実行を、防ぐ。

### 4. 1 回の実行を、時間内に収める

- 取り込みは、取り込み元ごとに独立して実行する（1 つの失敗が、ほかを止めない）。評価は、取り込み後・手動入力の後は、変わった設備だけを評価する（`evaluateAffected`）。連携は、1 回の件数の上限（`batchSize`）がある。通知の配信は、未配信の通知だけ。
- 定期の評価（JB-02。データの途絶を「不明」に反映する）は、全設備を評価する。**設備・観測値が多くなったとき、300 秒に収まるかは、実測が必要**（Issue #79。収まらないときは、設備ごとに分ける）。

## 検討した代替案

| 案 | 採らなかった理由 |
|----|------------------|
| Lambda の予約同時実行数を 1 にする | 実装は最小だが、アカウントの同時実行の上限が小さい（新しいアカウントは 10 など）と、予約が拒否される。EventBridge の再配信・重複の起動を、完全には防げない。上限の確認が先に必要 |
| 冪等性だけに頼る（ロックなし） | 二重の Web Push の配信・農業情報基盤への二重の送信を、防げない |
| ジョブごとに Lambda を 4 つ | タイムアウト・メモリ・IAM を、ジョブごとに分けられるが、関数・ログ・IaC が 4 倍になる。今は、差がない。実測（#79）で必要になれば、分ける |
| EventBridge Scheduler | CDK の部品が、まだ低水準（CfnSchedule）で、ロールも自分で作る必要がある。今回は、標準の部品（Rule）で足りる |
| API の Lambda が、ジョブも処理する（入力でルーティング） | API の関数の URL（公開）と、ジョブの起動を、同じ関数に混ぜると、権限・タイムアウト・ログを分けられない |

## 結果・トレードオフ

- **ジョブの失敗は、次の周期まで、再実行されない**。連続して失敗すると、取り込み・評価が止まる。失敗の通知（ログ・指標へのアラーム）は、本 ADR の範囲外（運用の整備。Issue #80 以降）。
- **ロックの期限（360 秒）が、ジョブの実行時間の上限になる**: 実際の実行時間が、期限を超えると、次の実行が始まり、二重になりうる。Lambda のタイムアウト（300 秒）で、実行は打ち切られるため、通常は起きない。タイムアウトを変えるときは、ロックの期限も変える（定数 `JOB_LAMBDA_TIMEOUT_SECONDS` から、期限を作る。テストで、期限がタイムアウトより長いことを確認する）。
- 取り込みの実行は、評価環境の S3 のファイルのモック（Issue #77）が入るまで、読み込む元がない（取り込み元がなければ、何もしない）。
- 手動の取り込み（API の `POST /ingestion/sources/{id}/run`）の二重実行の防止は、これまでどおり、API の Lambda の同一プロセスの中だけ。ジョブの Lambda との同時実行は、取り込み済みのファイルの記録（冪等性）に頼る。
- AWS での確認は、デプロイ後に行う（4 つのルールが、周期どおりに起動する・ログに `ジョブを終了しました` が出る・IAM の不足がない）。
