# ADR-0019 通知の規則を、恒久の仕様にする（#146 の決定）

- ステータス: 承認（2026-10-26。ユーザーの判断。Issue #146）
- 日付: 2026-10-26
- 関連: [ADR-0013](./0013-environments-and-access-control.md)、[ADR-0016](./0016-ingestion-federation-rules.md)、[ADR-0017](./0017-evaluation-rules.md)、[ADR-0018](./0018-manual-input-and-data-rules.md)、[architecture.md](../architecture/architecture.md) 8 章、FR-7.1〜FR-7.7、UC-05・UC-10・UC-22・UC-23・UC-24

目的: 通知の、暫定だった規則（通知の条件・抑制・配信の再送・既読・対応状況・Web Push の宛先・手段）を、決めて、恒久の仕様にする。決めた経緯（背景・見直しの条件）は、各決定のコメント（#146）にもある。

## 背景

- 通知は、画面内の通知と Web Push で、「注意」「異常」に変わったとき、取り込みの失敗、データ取得の停止を、農作業者に知らせる（HITL の入口）。
- 通知の規則の多くは、暫定の仕様で、実装が先に進んでいた（dev_spec.md 4.1 No.6〜8・19・35）。要件には、TODO が残っていた（FR-7.1〜FR-7.3・FR-7.6・FR-7.7）。
- **Web Push の配信は、ダミー**（記録だけ）で、実配信は、未実装。

## 決定

### D-37 「不明」「欠損・遅延」の通知

- **「不明」そのものは、通知しない**。自動のデータの途絶は、「データ取得停止」の通知が知らせる。手動入力の漏れは、データ活用度合いの観点が知らせる。
- **「不明」は、状態の変化とみなさない**。直前の「不明でない」状態と比べる（「異常 → 不明 → 異常」は、継続とみなし、再通知しない）。
- 欠損・遅延（データ品質）は、**個別には通知しない**（棄却数は、取り込みログで見られる）。
- **ファイル単位の失敗**（読み取れない・形式違い・大きすぎる）は、**既定で通知する**（設定で切り替えは残す）。
- 見直しの条件: 「不明」で、異常を見逃した事例が出たとき。実データで、不正な値が多いと分かったとき。

### D-42 「正常」に戻ったときの扱い

- **通知ごとの「経過」と「回復日時」を、状態の変化の履歴から導出して示す**。経過は、その通知の時点から、同じ観点・設備の次の通知（なければ現在）までの状態の変化。回復日時は、経過の中で、最初に「正常」に戻った日時と、異常からの経過時間（なければ「未回復」）。新しい保存はなく、これまでの通知にも使える。
- **回復の通知は、出さない**（通知が増えるため）。**自動既読（自動クローズ）も、しない**（既読は、利用者ごとの「確認した」の記録）。
- **改善（異常 → 注意）は、通知しない**。悪化（正常 → 注意、正常 → 異常、注意 → 異常）だけ通知する。
- **通知に、利用者が、メモ（自由記述）を入力できる**。共有（全員が読める）、追記のみ（編集・削除なし）、入力者と日時つき、手動入力と同じ権限、農業情報基盤には送らない、保持は通知と同じ（期限なし）。
- 理由: 最新の評価から出す「現在の状態」は、古い通知で、後の別の出来事と混ざり、誤った表示になる。出来事ごとの記録にする。
- 見直しの条件: 回復の通知の要望が出たとき。メモの訂正の要望が出たとき。

### D-38 通知の抑制の条件・配信の再送

- **抑制**: 「**正常が、一定時間（設定値。既定 15 分）続いたあとの悪化**」を、新しい出来事として通知する。それより短い行き来は、同じ出来事として通知しない。「注意 ⇄ 異常」だけの行き来は、同じ出来事。取り込みの失敗・停止の通知は、同じ取り込み元・状況について、**60 分**に 1 件（現状のまま）。
- 理由: 現状の 60 分の抑制では、再発（異常 → 正常 20 分 → 異常）が、通知されないまま継続する。
- **配信の再送**: 配信の状態を、**購読ごと**に持ち、失敗した購読にだけ再送する（二重配信をなくす）。間隔は、**1 分から倍々**にして、最大 1 時間。**通知を作ってから 1 時間**を過ぎたら、断念する（Web Push の有効期限も 1 時間）。断念した通知は、画面内の通知として、残る。
- 見直しの条件: 再発の見落とし、または行き来による通知の増加が、運用で問題になったとき。

### D-39 既読の単位・一括既読

- **既読は、利用者ごと**（現状を恒久化）。通知を選んで対象の画面へ移ると、自動で既読になる（現状）。**未読に戻す操作は、設けない**。
- **一括既読は、画面に読み込んだ時点までに届いた通知**だけを対象にし、**件数つきの確認ダイアログ**で実行する（現状は、後から届いた通知も、確認なしで既読にしてしまう）。

### D-40 対応状況の管理・承認

- **対応状況（未対応・対応中・完了）の管理は、扱わない**。**承認フローは、設けない**。**未確認の通知の再通知（リマインド）・担当者の割り当ては、しない**。
- 対応の記録は、**回復日時（自動）と、メモ（D-42）**で行う。認識している限界: 「まだ対応していない通知はどれか」を、一覧で絞り込めない。
- 見直しの条件: 対応の抜け漏れが課題になったとき。承認が必要な操作が出たとき。重要な異常の見落としが起きたとき。

### D-41 Web Push の対象端末・受け取る種類

- 購読は、**利用者 × 端末**（現状）。受け取る種類・対象は、**選ばせない**（すべて配信）。設定画面は、**この端末の有効化・解除**だけ。
- **宛先**: 通知は、**その設備を閲覧できる利用者にだけ**、配信・表示する（管理者は、すべて）。設備の割り当て（#116）の実装と一緒に行う。それまでは、全員。
- 見直しの条件: 通知が多すぎるという声が出たとき（プッシュの重大度の選択〔異常のみ／注意と異常〕）。不要な購読が残る事例が出たとき。

### D-36 通知の手段・宛先・条件

- 手段は、**画面内の通知と Web Push**（FR-7.2）。**メールは、見送る**（宛先〔個人情報〕の管理、SES の設定、運用の負荷）。
- **Web Push の実配信は、実証実験の前に実装する**（依存パッケージの追加は、事前確認。VAPID 秘密鍵は、パラメータストア。`SecretPort`〔#206〕が前提）。
- 取り込み系の通知（失敗・停止）の宛先も、**対象の設備を閲覧できる利用者**。
- **24 時間、通知する**（静音の時間帯は、設けない）。
- 見直しの条件: 現場の端末で、Web Push が使えないと分かったとき。発注者が、既存の通知サービスの利用を望んだとき（通知手段のポート〔NotifierPort〕に、アダプタを追加する）。

## 結果・トレードオフ

- 通知の規則が、決まり、文書の TODO が置き換わる。実装は、別の Issue（下記）。決定のうち、実装が済んでいないものは、文書に「決定（実装は #xxx）」と書いて、現状と区別する。
- 実配信ができるまでは、通知は、画面を開いているときにしか届かない（実証の前に実装する）。
- 対応状況を持たないため、未対応の通知の絞り込みは、できない。メモと回復日時で、補う。
- 改善と回復を通知しないため、「直った」ことは、通知ではなく、通知の経過・ダッシュボードで知る。
- 夜間の照度・温度で「注意」が出入りする運用（ADR-0017 D-16）では、夜間の通知が増えうる。利用者の基準の調整と、プッシュの重大度の選択（見直しの条件）で対処する。
