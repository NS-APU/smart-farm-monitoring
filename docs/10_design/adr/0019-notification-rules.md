# ADR-0019 通知の規則を、恒久の仕様にする（#146 の決定）

- ステータス: 承認（2026-10-26。ユーザーの判断。Issue #146）
- 日付: 2026-10-26
- 関連: [ADR-0013](./0013-environments-and-access-control.md)、[ADR-0016](./0016-ingestion-federation-rules.md)、[ADR-0017](./0017-evaluation-rules.md)、[ADR-0018](./0018-manual-input-and-data-rules.md)、[architecture.md](../architecture/architecture.md) 8 章、FR-7.1〜FR-7.7、UC-05・UC-10・UC-22・UC-23・UC-24

目的: 通知の、暫定だった規則（通知の条件・抑制・配信の再送・既読・対応状況・Web Push の宛先・手段）を、決めて、恒久の仕様にする。決めた経緯（背景・見直しの条件）は、各決定のコメント（#146）にもある。

## 背景

- 通知は、画面内の通知と Web Push で、「注意」「異常」に変わったとき、取り込みの失敗、データ取得の停止を、農作業者に知らせる（HITL の入口）。
- 通知の規則の多くは、暫定の仕様で、実装が先に進んでいた（dev_spec.md 4.1 No.6〜8・19・35）。要件には、TODO が残っていた（FR-7.1〜FR-7.3・FR-7.6・FR-7.7）。
- **（決定時の状況）Web Push の配信は、ダミー**（記録だけ）で、実配信は、未実装だった（#241 で実装済み。D-36）。

## 決定

### D-37 「不明」「欠損・遅延」の通知

- **「不明」そのものは、通知しない**。自動のデータの途絶は、「データ取得停止」の通知が知らせる。手動入力の漏れは、データ活用度合いの観点が知らせる。
- **「不明」は、状態の変化とみなさない**。直前の「不明でない」状態と比べる（「異常 → 不明 → 異常」は、継続とみなし、再通知しない）。
- 欠損・遅延（データ品質）は、**個別には通知しない**（棄却数は、取り込みログで見られる）。
- **ファイル単位の失敗**（読み取れない・形式違い・大きすぎる）は、**既定で通知する**（設定で切り替えは残す）。
- 見直しの条件: 「不明」で、異常を見逃した事例が出たとき。実データで、不正な値が多いと分かったとき。

### D-42 「正常」に戻ったときの扱い

- **通知ごとの「経過」と「回復日時」を、状態の変化の履歴から導出して示す**。経過は、その通知の時点から、同じ観点・設備の次の通知（なければ現在）までの状態の変化。回復日時は、経過の中で、最初に「正常」に戻った日時と、異常からの経過時間（なければ「未回復」）。新しい保存はなく、これまでの通知にも使える。
- **回復の通知は、出さない**（通知が増えるため）。**自動既読（自動クローズ）も、しない**（既読は、利用者ごとの「確認した」の記録）。
- **改善（異常 → 注意）は、通知しない**。悪化（正常 → 注意、正常 → 異常、注意 → 異常）だけ通知する。
- **通知に、利用者が、メモ（自由記述）を入力できる**。共有（全員が読める）、追記のみ（編集・削除なし）、入力者と日時つき、手動入力と同じ権限、農業情報基盤には送らない、保持は通知と同じ（期限なし）。
- 理由: 最新の評価から出す「現在の状態」は、古い通知で、後の別の出来事と混ざり、誤った表示になる。出来事ごとの記録にする。
- 見直しの条件: 回復の通知の要望が出たとき。メモの訂正の要望が出たとき。

### D-38 通知の抑制の条件・配信の再送

- **抑制**: 「**正常が、一定時間（設定値。既定 15 分）続いたあとの悪化**」を、新しい出来事として通知する。それより短い行き来は、同じ出来事として通知しない。「注意 ⇄ 異常」だけの行き来は、同じ出来事。取り込みの失敗・停止の通知は、同じ取り込み元・状況について、**60 分**に 1 件（現状のまま）。
- 理由: 現状の 60 分の抑制では、再発（異常 → 正常 20 分 → 異常）が、通知されないまま継続する。
- **配信の再送**: 配信の状態を、**購読ごと**に持ち、失敗した購読にだけ再送する（二重配信をなくす）。間隔は、**1 分から倍々**にして、最大 1 時間。**通知を作ってから 1 時間**を過ぎたら、断念する（Web Push の有効期限も 1 時間）。断念した通知は、画面内の通知として、残る。
- 見直しの条件: 再発の見落とし、または行き来による通知の増加が、運用で問題になったとき。

### D-39 既読の単位・一括既読

- **既読は、利用者ごと**（現状を恒久化）。通知を選んで対象の画面へ移ると、自動で既読になる（現状）。**未読に戻す操作は、設けない**。
- **一括既読は、画面に読み込んだ時点までに届いた通知**だけを対象にし、**件数つきの確認ダイアログ**で実行する（以前は、後から届いた通知も、確認なしで既読にしてしまった）。
  - 実装（#240）: 一覧の応答が、サーバーが読み込んだ時点（`asOf`）を返す。画面は、その時点を `until` として、まず `GET /notifications/unread-count?kind&until` で範囲の未読の件数を取り、ダイアログで件数を示す。確認すると、同じ `until` で `POST /notifications/read-all` を呼ぶ（`until` は必須。以降に届いた通知は、未読のまま）。応答は、新しく既読にした件数 `markedCount`。0 件のときは、確認を開かず、その旨を示す。件数の確認と実行の間に届いた通知は、どちらにも数えない（同じ `until`）

### D-40 対応状況の管理・承認

- **対応状況（未対応・対応中・完了）の管理は、扱わない**。**承認フローは、設けない**。**未確認の通知の再通知（リマインド）・担当者の割り当ては、しない**。
- 対応の記録は、**回復日時（自動）と、メモ（D-42）**で行う。認識している限界: 「まだ対応していない通知はどれか」を、一覧で絞り込めない。
- 見直しの条件: 対応の抜け漏れが課題になったとき。承認が必要な操作が出たとき。重要な異常の見落としが起きたとき。

### D-41 Web Push の対象端末・受け取る種類

- 購読は、**利用者 × 端末**（現状）。受け取る種類・対象は、**選ばせない**（すべて配信）。設定画面は、**この端末の有効化・解除**だけ。
- **宛先**: 通知は、**その設備を閲覧できる利用者にだけ**、配信・表示する（管理者は、すべて）。**実装済み（Issue #331。#116 の子）**: 状態変化の通知は、作成時のハウス（`facilityId`。ハウス自身はその ID。作成時に固定）を閲覧できる利用者（全設備を閲覧する権限 `equipment:view-all` をもつ利用者と、そのハウスに割り当てた一般ユーザー）にだけ、表示（一覧・未読の件数・既読・一括既読・メモ）・配信（Web Push）する。**ハウスに属さない通知（取り込みの失敗・取得停止・連携の期限切れ）は、全設備を閲覧できる利用者（管理者）のみ**（ユーザーの判断）。範囲外の通知は、存在しないもの（404）。Web Push の宛先は、**最初の配信の時点**で決まる（あとで割り当てを変えても、配信を始めた通知の宛先は変わらない。一覧・件数は、すぐに反映）。
- **対応する環境**: 下の「確認事項（#234）の扱い」。Web Push は、iOS・iPadOS では、ホーム画面に追加したウェブアプリのときだけ使える。
- 見直しの条件: 通知が多すぎるという声が出たとき（プッシュの重大度の選択〔異常のみ／注意と異常〕）。不要な購読が残る事例が出たとき。

### D-36 通知の手段・宛先・条件

- 手段は、**画面内の通知と Web Push**（FR-7.2）。**メールは、見送る**（宛先〔個人情報〕の管理、SES の設定、運用の負荷）。
- **Web Push の実配信は、実証実験の前に実装する**（依存パッケージの追加は、事前確認。VAPID 秘密鍵は、パラメータストア。`SecretPort`〔#206〕が前提）。
  - 実装（#241。実機での確認は、運用手順 8.6 で、ユーザーが行う）: 配信アダプタ（`infrastructure/web-push/`）が、購読ごとに、プッシュサービスへ送る。設定 `WEB_PUSH_DELIVERY=vapid`（既定は `dummy`。ローカル・E2E は、ダミー）・`WEB_PUSH_PUBLIC_KEY`・`WEB_PUSH_SUBJECT`（連絡先。https の URL。個人のメールアドレスは使わない）。秘密鍵は、配信のたびに `SecretPort`（`web-push/vapid-private-key`）から読む（ログ・エラー・環境変数に出さない）。
  - 結果の扱い: 2xx は配信、404・410 は購読が無効、429・5xx・接続できない・400 台の設定の問題（400・401・403）は、一時的な失敗（D-38 の再送の対象。メッセージに HTTP の状態コードのみ）。有効期限（TTL）は、通知を作ってから 1 時間までの残り（D-38）。緊急度は high。
  - **本文つきの配信には、購読の暗号鍵（p256dh・auth）が要る**ため、購読の登録（`PUT /push-subscription`）に `keys` を追加して保存する（任意。鍵の保存より前の購読・鍵を返さない端末には、本文なしで送り、端末は既定の文言「新しい通知があります」で表示する。無効にして、もう一度有効にすると、本文つきになる）。本文は、種別の表示名（見出し）・メッセージ（300 文字まで）・通知の識別子。
  - 送信と暗号化（RFC 8291）・VAPID の署名は、`web-push` 3.6.7（MPL-2.0。改変せずに使う。ライセンスの扱いは、`.license-check/license-report.md`）。
- 取り込み系の通知（失敗・停止）の宛先も、**対象の設備を閲覧できる利用者**。
- **24 時間、通知する**（静音の時間帯は、設けない）。
- 見直しの条件: 現場の端末で、Web Push が使えないと分かったとき。発注者が、既存の通知サービスの利用を望んだとき。**利用者のフィードバックで、ショートメッセージ・メール・LINE などとの併用を望む声が出たとき**（通知手段のポート〔NotifierPort〕に、アダプタを追加する）。

## 結果・トレードオフ

- 通知の規則が、決まり、文書の TODO が置き換わる。実装は、別の Issue（下記）。決定のうち、実装が済んでいないものは、文書に「決定（実装は #xxx）」と書いて、現状と区別する。
- 実配信は、実装済み（#241）。既定の `dummy`（ローカル・E2E）では、実際には送らない。実配信（`WEB_PUSH_DELIVERY=vapid`）を設定しない環境では、通知は、画面を開いているときにしか届かない。
- 対応状況を持たないため、未対応の通知の絞り込みは、できない。メモと回復日時で、補う。
- 改善と回復を通知しないため、「直った」ことは、通知ではなく、通知の経過・ダッシュボードで知る。
- 夜間の照度・温度で「注意」が出入りする運用（ADR-0017 D-16）では、夜間の通知が増えうる。利用者の基準の調整と、プッシュの重大度の選択（見直しの条件）で対処する。

## 確認事項（#234）の扱い（2026-11-06。ユーザーが判断した）

通知の確認事項は、**ユーザーが、自分で判断した**。決定のまま進め、見直しの条件（各決定）に当たったときに見直す。

| 確認事項 | ユーザーの判断 |
| --- | --- |
| 既存の通知サービスの有無・望む通知手段（Q-011） | **Web Push で進める**。通知は、利用者に伝えたいことが、確実に伝わることが大事。ブラウザの画面内の表示だけでは、利用者が画面を見ていないと気づけない（または、気づくのが遅れる）。そのため、利用者が持つ端末（スマートフォンなど）の通知機能を使って、素早く気づける仕組みにする。基本は Web Push で十分と考えるが、**利用者のフィードバックによっては、ショートメッセージ・メール・LINE などとの併用を検討する**（NotifierPort にアダプタを追加） |
| 現場の端末で Web Push を使えるか | **これ以上、確認しない**（下の「対応する環境」） |
| 夜間・休日の通知 | **24 時間通知**。端末の設定で、通知を抑制できる（静音の時間帯は、設けない） |
| 通知の既読・未読の管理（Q-018） | **利用者ごとに、既読を管理する**（D-39） |
| 対応状況・承認（Q-018） | **承認を扱わない前提で進める**（D-40） |

**対応する環境**（ユーザーの判断。具体的な端末は、利用者によるため、決めない）:

- 端末: PC・タブレット・スマートフォン。OS: Windows・Mac・iOS・Android（**最新の安定版**）。ブラウザ: Chrome・Safari・Edge などの主要なブラウザ
- Web Push の制約（一般的な知識。実機での確認は #241）: iOS・iPadOS では、**ホーム画面に追加したウェブアプリ**のときだけ使える（Safari のタブのままでは使えない）。16.3 以前の iOS では使えない
- **利用者が、利用できる環境を使う**前提とする（問題ない）。Web Push を使えない端末では、画面内の通知のみとなる（現状の動作）
