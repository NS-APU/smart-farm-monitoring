# ADR-0007 DynamoDB のテーブルを、観測値の専用テーブルと、そのほかの集約テーブルに分ける

- ステータス: 承認（2026-10-15。ユーザーの判断。Issue #72）
- 日付: 2026-10-15
- 関連: [data-model.md](../data/data-model.md) 2章、[ADR-0001](./0001-modular-monolith-ports-and-adapters.md)、[ADR-0002](./0002-deployment-serverless.md)、[ADR-0004](./0004-federation-outbox-standalone.md)、Issue #72・#73

## 背景

- DB は DynamoDB（ADR-0002・ADR-0005）。ADR-0002 は、機能要件（FR-6.5 の推移のグラフなど）が DynamoDB で満たせるかを、**実装の前に検証する**ことを求めた。data-model.md 2 章に、設計時の案（2.2）があったが、実装が最適化される前のもので、実際の Repository のポート（`src/backend/application/ports/repositories.ts`）の使われ方と、ずれている
- 実際の使われ方（コードから洗い出した）のうち、DynamoDB で設計に効くもの:
  - **評価（JB-02。既定 5 分ごと）**: 設備の範囲（ハウスなら、ハウスとロボット・センサー）の、**最大 90 日分の観測値を、全項目まとめて**読む（`findForEvaluation`）。読み取りの量が、費用を決める
  - **推移**: 同じ読み取りで、期間は 30〜90 日（`series`）
  - **一覧（`query`）**: 計測日時の順（既定）・カテゴリ・値の 3 種類の並べ替え。設備・カテゴリ・項目・取得元・期間で絞る。キーワード検索は、設備名・ステータスコード名を使うため、アプリ側で絞る。カーソルでページを送る
  - **ダッシュボード・ヘッダー（約 10 秒ごとのポーリング）**: 最終の受信日時（`latestReceivedAt`）、未読の通知の件数（`unreadCount`）、設備ごとの最新の評価結果（`listLatest`）
  - 通知の既読は、通知と利用者の組ごと（暫定。Q-018）。ローカルの実装は、利用者が作られる前の通知も、未読として数える
- 検証は、DynamoDB Local（AWS の公式の配布物）で、**負荷テストと同じ規模**（観測値 約 63 万件・1 年分・ハウス 3・手動入力 約 2.1 万件）の合成データで行った。再現の手順は、「検証」に示す

## 決定

テーブルを 2 つにする。観測値を持つ **`Observations`**（件数が多く、時系列）と、そのほかをすべて持つ **`Main`**（少量〜中量。単一テーブル設計）。両方とも、オンデマンド課金（固定費なし）。

### 1. Observations（観測値）

| 項目 | 内容 |
|------|------|
| PK（`pk`） | `{equipmentId}#{itemKey}`（1 つの設備の 1 つの項目が、1 つのパーティション） |
| SK（`sk`） | `{observedAt}#{A\|M}`。`observedAt` は、UTC・ミリ秒つきの固定長（`2026-10-15T01:02:03.000Z`）に正規化する。末尾は、取得元（`A` = 自動取り込み、`M` = 手動入力）。一意キー（設備・項目・計測日時・取得元）と対応する |
| 属性 | `v`（値）、`q`（品質）、`r`（受信日時。エポックミリ秒。評価・最終の受信日時の精度を保つため。測定では秒で保存したが、サイズの差は 1 項目あたり 1 バイト程度）。ある場合だけ: `d`（論理削除）、`f`（取り込み元ファイル）、`e`（入力者）、`n`（メモ）、`m`（手動入力の ID）、`fv`（FormatProfile の版）。**カテゴリは保存しない**（項目カタログから導く）。属性名は短くする |
| GSI `manual`（疎） | 手動入力だけに付ける。`g2` = `{equipmentId}`、`g2s` = `{observedAt}#{itemKey}`。手動入力の一覧（`source=MANUAL`）を、1〜数 RRU で引く |

- **属性名・値は、アイテムのサイズに数える**。短い属性名・導出できる値を保存しない形で、平均 **84 バイト**（観測値をそのまま保存すると 289 バイト）。読み取りの費用が、約 3.4 倍の差になる
- 設備ごとの**項目の一覧（レジストリ）**を、`Main` に持つ（書き込みのときに、更新する）。評価・一覧が、読むパーティションを、1 回の GetItem で知るため
- 設備ごとの**最終の受信日時**（自動取り込みのみ・全体）を、`Main` に持つ（書き込みのときに、最大値で更新する）。`latestReceivedAt` が、1 回の GetItem になる

### 2. 読み取り（検証済み）

| ポートの操作 | 読み方 |
|--------------|--------|
| `findForEvaluation(設備の集合, 期間)` | 設備ごとのレジストリの項目 × 期間で、パーティションごとに Query（並列）。論理削除は、アプリ側で除く |
| `query`（計測日時の順） | 対象のパーティション（設備 × 項目。項目・カテゴリで絞れば、少なくなる）に、`limit + 1` 件ずつ Query し、計測日時の順に併合して、1 ページ分を取る。カーソルは、最後の（計測日時、一意キー）。同じ計測日時のものは、一意キーの昇順（現在のローカルの実装と同じ） |
| `query`（`source=MANUAL`） | GSI `manual` |
| `query`（値・カテゴリの順、キーワード検索） | 期間（`from`・`to`。**31 日以内を必須**。API・画面で検証する。別 Issue）の範囲を取得し、アプリ側で並べ替え・絞り込みをする。アダプタは、安全のため、取得が 5 万件を超えたら、エラー（期間を狭めるよう求める）にする |
| `findByKey` | GetItem（`pk`・`sk`） |
| `saveMany` | BatchWriteItem（25 件ずつ）。一意キーで、上書き（冪等）。レジストリ・最終の受信日時も更新する |
| `latestReceivedAt` | 設備ごとの、最終の受信日時の項目（GetItem） |

### 3. Main（そのほか）

| 集約 | PK | SK | 備考 |
|------|----|----|------|
| 設備 | `EQUIPMENT` | `{equipmentId}` | `list` は、パーティションを Query。論理削除は、属性で絞る |
| ステータスコード | `STATUSCODE` | `{code}` | |
| 判断基準 | `CRITERIA` | `{viewpointId}` | |
| 設定 | `SETTING` | `{key}` | |
| 利用者 | `USER` | `{userId}` | 認証情報の保持先は、Issue #74 |
| Web Push 購読 | `PUSH` | `{subscriptionId}` | 少量。利用者ごと・有効の絞り込みは、アプリ側 |
| 評価結果（最新） | `EVAL#{equipmentId}` | `{viewpointId}#{horizon}#{periodDays\|0}` | `listLatest` は、パーティションを Query |
| ステータスの変化（最終） | `SCLAST#{equipmentId}` | `{viewpointId}` | |
| ステータスの変化（履歴） | `SCH#{equipmentId}#{viewpointId}` | `{changedAt}` | 古い順の Query |
| 通知 | `NOTIF` | `{createdAt}#{notificationId}` | 新しい順の Query。`get`・`dedupKey` は、GSI1 |
| 通知の既読 | `READ#{userId}` | `{notificationId}` | 既読にしたときに、条件つきで作る |
| **カウンター** | `COUNTER` | `NOTIF_TOTAL`・`READ#{userId}`・`FED#{status}` | 通知の総数、利用者ごとの既読数、連携の状態ごとの件数。トランザクションで更新する |
| 取り込み済みファイル | `SRC#{sourceId}` | `FILE#{fileId}#{contentHash}`・`HASH#{contentHash}`（成功のみ）・`STATE`（直近の開始・成功・データ取り込みの日時） | `findIngestedFile` は GetItem。取り込み元の状態（`lastStartedAt` など）は、1 回の GetItem |
| 取り込みログ | `ILOG#{sourceId}` | `{startedAt}#{logId}` | 取り込み元ごとの Query。全取り込み元は、併合。TTL |
| 連携項目 | `FED` | `{federationItemId}` | `listDue` は、未送信の項目だけが載る疎な GSI1（`FDUE` / `{enqueuedAt}#{id}`） |
| 連携ログ | `FLOG` | `{occurredAt}#{logId}` | TTL |
| 変更履歴 | `AUDIT` | `{occurredAt}#{auditId}` | 操作種別・変更者などは、FilterExpression。期間は、キー条件。TTL |
| 手動入力 | `ME` | `{observedAt}#{entryId}` | 少量。`get` は GSI1。並べ替え・絞り込みは、アプリ側 |

- **GSI1**（`Main`。汎用）: `gsi1pk`・`gsi1sk`。通知の `get`（`NID#{id}`）、通知の重複抑制（`DEDUP#{key}` / `{createdAt}`）、連携の未送信（`FDUE`）、手動入力の `get`（`ME#{entryId}`）に使う
- **通知の未読件数**: `NOTIF_TOTAL − READ#{userId}` の 2 回の GetItem。**全件を数えない**（約 10 秒ごとのポーリングで、全件を読むと、費用が桁違いに増える）。ローカルの実装と同じ意味（利用者が作られる前の通知も、未読）
- **通知の一覧**: `NOTIF` の新しい順のページに、`READ#{userId}` を BatchGet して、既読を付ける。未読の絞り込みは、ページが埋まるまで繰り返す
- **TTL**: 取り込みログ・連携ログ・変更履歴・送信済みの連携項目に、`ttl` の属性と、TTL の設定を用意する。**期間は、保存期間（rfp.md 6章。未確定）が決まるまで、設定しない**
- **読み取りの整合性**: 既定は、結果整合（容量が半分）。書き込みの直後に読み直す処理（冪等の判定・カウンター）は、強い整合を使う。詳細は、Issue #73 のテストで確定する

## 検証

DynamoDB Local 3.3.1（AWS の公式の配布物。SHA-256 を確認）で、観測値 634,620 件（自動 613,200・手動 21,420）を投入し、測定した。読み取りの容量は、結果整合の RRU（DynamoDB Local が返す消費容量）。時間は、DynamoDB Local のもの（**実際の AWS の遅延とは異なる**。参考値）。

| 操作 | 件数 | 容量（RRU） | 時間 |
|------|------|-------------|------|
| 評価の入力: HOUSE-01（ハウス + ロボット + センサー。90 日。15 分間隔） | 87,674 件・6.9 MB・Query 24 回 | 882 | 1.3 秒（並列 12）／1.9 秒（逐次） |
| 評価の入力: ROBOT-01 のみ／SENSOR-01 のみ | 53,114 件／34,560 件 | 542／340 | 0.7 秒／0.4 秒 |
| 評価の入力: HOUSE-02（ハウス + ロボット 2 + センサー 2。60 分間隔） | 45,804 件 | 495.5 | 0.5 秒 |
| 推移: HOUSE-01 の 30 日／90 日 | 29,304 件／87,674 件 | 300.5／882 | 0.3 秒／0.9 秒 |
| 参考: HOUSE-01 の 365 日（全期間） | 355,762 件・27.9 MB | 3,569.5 | 5.2 秒 |
| 一覧: ハウス全体・50 件（1 ページ目／21 ページ目） | 1,224 件（24 パーティション × 51） | 22／22 | 38 ms／39 ms |
| 一覧: 観点の項目（2 項目）／1 つの項目／直近 7 日 | 102 件／51 件／538 件 | 2／0.5／15 | 5／4／26 ms |
| 手動入力の一覧: GSI `manual`（50 件） | 50 件 | 1 | 5 ms |
| 悪い例: 自動取り込みの項目を、手動入力かで FilterExpression で絞る | 0 件（全件を読んで除く） | 329.5 | 324 ms |
| 時間順以外の並べ替え: 全期間を読んでアプリで並べ替え | 355,762 件 | 3,569.5 | 4.9 秒 |
| 時間順以外の並べ替え: 直近 5,000 件に限る | 55,372 件 | 593.5 | 0.6 秒 |

- **FR-6.5・NFR-3.5（推移 10 秒以内）**: 90 日の推移は、約 0.9 秒（DynamoDB Local）で、大きな余裕がある。**満たせる**
- **NFR-3.4（初期表示 3 秒以内）**: 評価結果の最新は、設備のパーティションの Query（約 50 件）で、読み取りは軽い。評価の読み取り（上の表）は、画面の表示とは別に、ジョブで行う
- **アイテムのサイズ**: 平均 84 バイト（短い属性名）。観測値をそのまま保存すると 289 バイト（約 3.4 倍の読み取り費用）
- **書き込み**: 投入は、4,658 件/秒（DynamoDB Local。25 件ずつの BatchWrite・並列 12）。1 件 = 1 WRU（アイテムが 1 KB 以下）。手動入力は、GSI にも書くため、2 WRU

### 費用の見込み（読み取り。評価）

評価は、設備ごとに、その設備の範囲の 90 日分を読む（ハウスの評価は、ロボット・センサーの分も含むため、同じ観測値を、ハウスの評価と、その設備自身の評価で、2 回読む）。1 回の評価の周期（既定 5 分）あたりの、読み取りの容量:

| 構成 | 1 周期あたりの RRU | 1 か月（8,640 周期）の RRU | 月額の見込み（※） |
|------|---------------------|-----------------------------|-------------------|
| 想定の規模（ハウス 1・ロボット 1・センサー 1。15 分間隔。HOUSE-01 相当） | 約 1,760（882 + 542 + 340） | 約 1,520 万 | 約 1.9〜4.3 USD（約 290〜650 円） |
| 負荷テストの規模（ハウス 3・ロボット 4・センサー 4） | 約 3,170 | 約 2,740 万 | 約 3.4〜7.8 USD（約 510〜1,170 円） |

※ オンデマンドの読み取りの単価は、**公式の料金表では未確認**。第三者の情報にもとづく範囲（100 万 RRU あたり 0.125〜0.285 USD）で試算した（為替は 150 円）。月 5,000 円の上限（NFR-1.3）に対して、収まる見込み。ダッシュボードのポーリング（約 10 秒ごと）の読み取りは、別に加わる（1 回あたり 10〜20 RRU と見込み、利用者 10 名が 1 日 8 時間使うと、月に 1,000 万 RRU 前後。**未検証**。実環境の実測は Issue #79）。評価とあわせても、月 5,000 円の上限に対して、十分に小さい見込み。

費用を下げる手段（必要になったときに、検討する）: 評価の周期を長くする（5 → 15 分で 1/3）、Lambda の実行環境で、前回までの観測値を保持し、差分（前回以降）だけを読む（読み取りが、1/50 程度）、評価の入力を、時間ごとの集計に置き換える（ドメインの変更を伴う）。

### 再現の手順

1. DynamoDB Local（`https://d1ni2b6xgvw0s0.cloudfront.net/v2.x/dynamodb_local_latest.zip`。SHA-256 は、同じ場所の `.sha256`）を、別のディレクトリに展開し、`java -Djava.library.path=./DynamoDBLocal_lib -jar DynamoDBLocal.jar -inMemory -sharedDb -port 18000` で起動する。アクセスキーは、**英数字だけのダミー**（ハイフンを含むと、DynamoDB Local が拒否する）
2. 検証のプログラム（`bench.ts`。**リポジトリには含めず**、Issue #72 のコメントに掲載した。ユーザーの判断）を、`@aws-sdk/client-dynamodb`・`@aws-sdk/lib-dynamodb`（3.1147.0）を入れた、リポジトリの外のディレクトリで、`node --disable-warning=ExperimentalWarning bench.ts` で実行する。合成データは、負荷テストと同じ生成関数（`generateAutoObservations`・`generateManualObservations`）・同じ種（実データは使わない）。リポジトリの `work/` は、Git・lint の対象外で、置き場所に使える

## ユーザーの判断（2026-10-15）

1. **時間順以外の並べ替え（値・カテゴリ）と、キーワード検索は、期間（31 日以内）の指定を必須にする**。DynamoDB は、ソートキー（計測日時）の順にしか、効率よく読めない。全期間を対象にすると、1 回で 3,570 RRU・約 5 秒・35 万件をメモリに載せる（Lambda のメモリも圧迫する）ため。期間内（31 日。想定の規模で、約 3 万件・300 RRU）は、正確な結果になる。API の入力検証と画面（並べ替え・検索を選んだときの案内）は、別の Issue で行う。計測日時の順（既定）は、期間の指定が不要で、全期間をページで送れる
2. **通知の既読の単位（Q-018）**: 現在のローカルの意味（利用者ごと。利用者が作られる前の通知も未読）を、そのまま実現する。確定後に変更する場合は、カウンターの持ち方が変わる
3. **評価の読み取りの費用**: 想定の規模で、評価だけで月に約 300〜650 円、ポーリングを加えて 1,000 円前後の見込み（いずれも、単価が未確認の概算）。評価の周期（既定 5 分）は、そのまま。費用が問題になったら、「費用の見込み」の手段で下げる
4. **検証のプログラム**は、リポジトリに含めず、Issue のコメントに残す。手順と結果は、この ADR に記録する
5. **DynamoDB アダプタの実装（Issue #73）**: AWS SDK（`@aws-sdk/client-dynamodb`・`@aws-sdk/lib-dynamodb`）を、`src/backend` の依存に追加する。契約テスト（`repository-contract.test.ts`）を、DynamoDB Local にも適用し、**CI でも、DynamoDB Local を起動して実行する**（配布物は、固定の URL・SHA-256 で取得する）

## 結果・トレードオフ

- 観測値は、設備・項目ごとのパーティションで、評価・推移・一覧が、どれも**キーによる Query だけ**で読める（Scan を使わない。coding-standards.md）。パーティションあたりの書き込みの量は、上限に比べて、十分に小さい（1 設備・1 項目で、15 分に 1 件）
- 一覧は、設備 × 項目のパーティションを併合する（1 ページあたり、パーティション数 × 51 件を読む。想定の規模で 22 RRU）。併合・カーソルのロジックを、アダプタに持つ（契約テストで、ローカルの実装と同じ順序・同じ結果を検証する）
- 属性名を短くするため、DynamoDB のコンソールで、データが読みにくい。アダプタ内の変換（`toItem`・`fromItem`）が、唯一の窓口になる
- 計測日時を、ミリ秒つきの UTC に正規化する。ローカルの実装は、文字列の違い（ミリ秒の有無）を、別のキーとして扱うが、DynamoDB では、同じ時刻は、同じキーになる（重複の防止として、より厳密）
- 疎な GSI `manual` は、手動入力の書き込みを、2 WRU にする（件数が少なく、影響は小さい）
- カウンターは、通知の追加・既読・連携の状態の変化と、同じトランザクションで更新する。ずれが生じた場合に備え、再計算の手段（Query で数え直す）を、運用に用意する（Issue #80）
- DynamoDB Local の時間は、実際の AWS の遅延と異なる。実環境での計測（Lambda から。コールドスタートを含む）は、Issue #79 で行う
- 保存期間（TTL）の期間は、未確定のまま。確定したら、TTL を設定する

## 実装（Issue #73。2026-10-15）

実装は、`src/backend/infrastructure/dynamodb/`（Repository 13 種）と、`infra/lib/data-stack.ts`（テーブル。スタック `SfmData`）。契約テスト（`tests/integration/repository-contract.test.ts`）の 39 件（実装ごと）が、ローカルの 2 実装と同じく DynamoDB（DynamoDB Local 3.3.1）でも成功し、DynamoDB 固有の振る舞いは `tests/integration/dynamodb-adapter.test.ts` で確かめた。バックエンドを `PERSISTENCE=dynamodb`（デモデータ）で起動し、ログイン・ダッシュボード・通知・観測値の一覧（時刻順・値順）・設備が動くことも確認した。**AWS 上（Lambda から）は、未確認**（Issue #79）。

### 設計を具体化した点・変えた点

- **ポインタ項目**: 通知（`NID#{通知ID}`・`DEDUP#{重複抑制のキー}`）と手動入力（`MEID#{入力ID}`）の ID 引きは、設計の GSI1 ではなく、ポインタ項目（ソートキーを持つ。強い整合で引ける）にした。書き込みの直後に読み直す処理（既読にする・重複の判定・上書きの保存）が、GSI の結果整合で、見つからなくなることを避けるため。GSI1 は、設計どおり、**連携の未送信（`FDUE`）と、配信が未完了の通知（`UNDELIVERED`）**だけに使う（どちらも疎。ジョブが読むため、結果整合でよい）
- **Main の値**: 集約の値は、`data` の属性にそのまま持ち、読み込み時に、集約のスキーマで検証する。観測値は、短い属性名のまま変換し、検証しない（評価で、1 回に数万件を読むため。保存の前に、アプリ側で検証している）
- **時刻のキー**: 観測値だけでなく、通知・取り込みログ・連携ログ・変更履歴・手動入力・状態の変化の履歴のソートキーも、ミリ秒つき UTC に正規化する（文字列の順が、時刻の順になる）。値の本体は、保存したときの文字列のまま返す（観測値は、正規化した形と違うときだけ `ot` に元の文字列を持つ）
- **取り込み元の状態**（`STATE`）: 直近の開始・成功・データ取り込みの日時は、エポックミリ秒の数値で持ち、ログの追加のたびに、条件つきの更新（新しい値のときだけ）で、最大値にする
- **読み取りの整合性**: 観測値の Query・評価の入力は、結果整合。`findByKey`、Main の GetItem・Query・ポインタ・カウンターは、強い整合。疎な GSI（連携の未送信・配信が未完了）は、結果整合
- **読み取りの上限**: 値・カテゴリの順と、キーワード検索（`matches`）は、読む観測値が 50,000 件を超えたら、入力不正（期間の絞り込みを求める）にする。計測日時の順は、必要なページ分だけ読む（同じ計測日時のものをそろえるため、パーティションごとに、最大 1 件を先読みする）。API・画面の「期間の指定を必須にする」は、Issue #91
- **TTL の設定**: `Main` の `ttl` の属性（エポック秒）の TTL を、Issue #74 で有効にした。使っているのは、ログインの試行回数の記録（`LOGINFAIL`。[ADR-0008](./0008-cognito-authentication.md)）だけ。取り込みログ・連携ログ・変更履歴の期間は、未設定のまま（保存期間の確定後）
- **書き込みの順**: 観測値の保存は、読む側が使う「項目の一覧（`OBSREG`）」と「最終の受信日時（`OBSSTAT`）」を、観測値より先に更新する（途中で失敗しても、読めない観測値が残らない。取り込みは、冪等のため、再実行できる）

### ローカルの実装との違い（契約テストの範囲の外）

| 項目 | ローカル | DynamoDB |
|------|----------|----------|
| 同じ作成日時の通知の並び | 通知 ID の昇順 | 通知 ID の降順（ソートキーの逆順） |
| ミリ秒の有無だけが違う計測日時（`…:00Z` と `…:00.000Z`） | 別のキー | 同じキー（あとのものが上書き） |
| 最終の受信日時 | 毎回、全件から再計算 | 書き込みのたびに、最大値で更新（論理削除・古いデータの追加で、戻らない） |
| 通知の作成日時 | 変更できる | 変更できない（ソートキーに入っているため。更新は、作成時のソートキーに書く） |
| カテゴリの絞り込み | 保存された値で絞る | 項目カタログから導いて、読むパーティションを絞る（カタログと違うカテゴリで保存した観測値は、カテゴリの絞り込みでは見つからない。通常は発生しない） |
| 手動入力の一覧 | 全件から絞る | 日時の範囲で読み、アプリ側で絞る（件数が少ない前提。増えたら見直す） |
| カウンター（通知の総数・既読数・連携の状態ごとの件数） | 数えて返す | トランザクションで更新。同じ項目を同時に更新する処理は想定しない（ずれたら、再計算。Issue #80）。重複抑制のキーの最新も、同時の追加では逆転しうる |

### CI での DynamoDB Local（ユーザーの判断 5 の具体化）

判断 5 は、「固定の URL・SHA-256 で取得する」だった。確認したところ、**バージョンを固定した URL はなく**（`dynamodb_local_latest.zip` のみ。最新に更新される）、SHA-256 を固定すると、AWS の更新のたびに CI が失敗する。そのため、同じ目的（変更されない配布物を、検証して使う）を、**AWS の公式のコンテナイメージ（`public.ecr.aws/aws-dynamodb-local/aws-dynamodb-local`。3.3.1）を、ダイジェスト（`sha256:ff89bd48…`）で固定した service container**で実現した（ECR Public と Docker Hub で、同じダイジェストを確認）。ローカルでは、手順（commands.md）のとおり、zip を入手して使う。**CI での動作は、この PR の CI で確認する**（ローカルに Docker がないため、service container は、手元では未確認）。
