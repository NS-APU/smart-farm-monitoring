# ADR-0008 認証に Amazon Cognito を使い、資格情報は Cognito、ロールは DynamoDB に持つ

- ステータス: 承認（2026-10-16。ユーザーの判断。Issue #74）
- 日付: 2026-10-16
- 関連: [ADR-0001](./0001-modular-monolith-ports-and-adapters.md)、[ADR-0002](./0002-deployment-serverless.md)、[ADR-0005](./0005-tech-stack.md)、[ADR-0007](./0007-dynamodb-table-design.md)、[architecture.md](../architecture/architecture.md) 9 章、[security.md](../../20_development/security.md)、Issue #74・#75

## 背景

- 現在の認証は、アプリ内（`createLocalAuth`）のみ。パスワードのハッシュを、ユーザーの記録に持ち、セッションは、プロセスのメモリに持つ。**Lambda では使えない**（実行環境が、複数あり、再起動で消えるため）
- サーバーレス構成の基本は、Amazon Cognito を AuthPort のアダプタとして使うこと（ADR-0002・ADR-0005）。顧客に評価いただく環境で、認証の安全性とパスワードの管理を、マネージドサービスに任せる
- 守る要件: FR-9.1〜FR-9.5（ログイン・ログアウト、試行回数の制限、パスワードの条件、セッションの期限 30 分／7 日、ユーザー管理、ロールと権限）、NFR-5.1（すべての API に認証・認可）。画面（SC-14 を含む）と API の形は、変えない

## 決定

### 1. 役割分担（ユーザーの判断。推奨案）

| 持つもの | 持ち主 | 理由 |
|----------|--------|------|
| ユーザーID（ユーザー名）・パスワード・トークンの発行と更新・セッションの失効・ユーザーごとの一時的なロック | **Cognito** | 認証の安全性・パスワードの管理を、マネージドサービスに任せる |
| ユーザー名・ロール・最終ログイン日時・作成日時 | **DynamoDB**（`Main` の `USER`。UserRecord。`passwordHash` は、持たない） | ロールの変更・ユーザーの削除を、トークンの更新（最大 30 分）を待たず、**次のリクエストから反映**する（ローカルの実装と同じ）。ユーザーの一覧・最終ログイン・ユーザー名は、そのまま使える（画面の変更がない） |
| ロール → 権限（8 権限） | アプリの設定（`AccessPolicy`。`ROLE_DEFINITIONS_JSON`） | 変更なし |

ロールを Cognito のグループに持つ案は、採らない（ロールの変更が、トークンの更新まで反映されない。一覧・最終ログインを Cognito から取る必要があり、画面の変更も増える）。

### 2. 方式

- **画面と API は、変えない**。画面は、これまでどおり、API のログイン（`POST /auth/login`。ユーザーID・パスワード）・更新・ログアウトを呼ぶ。API が、**サーバー側（Lambda の IAM の権限）**で、Cognito を呼ぶ（`AdminInitiateAuth`。`ADMIN_USER_PASSWORD_AUTH`・`REFRESH_TOKEN_AUTH`）。アプリクライアントの ID は、ブラウザには出ない。Cognito のホスト型 UI（OAuth）は、使わない（画面の変更が大きく、同じオリジンの構成と合わない）
- **アクセストークンの検証は、リクエストごとに、Cognito へ問い合わせる**（`GetUser`。ユーザーの判断。推奨案）。パスワードの再設定・ログアウト・ユーザーの削除で、アクセストークンも、**すぐ**無効になる（ローカルの実装と同じ）。追加の依存は、なし。1 リクエストあたり、数十ミリ秒の増加（評価環境の 10 名程度では、問題ない）。利用者が増えたら、署名のローカル検証（`aws-jwt-verify`）に切り替えられる（失効の反映は、期限の最大 30 分に遅れる）
- **記録のない Cognito のユーザーは、ログインできない**（ロールがないため）。Cognito にだけいるユーザー（途中の失敗の残り）が、使われないようにする
- **セッションの期限**: アクセストークン 30 分、リフレッシュトークン 7 日（FR-9.3）。Cognito のアプリクライアントの設定で決め、IaC とアプリで、同じ値（`auth-policy.ts`）を共有する。リフレッシュトークンは、更新しても、**回転しない**（同じものを使い続ける。期限は、Cognito が検証する）。画面は、リフレッシュトークンの期限を使わない
- **パスワードの条件**（8 文字以上、英大文字・英小文字・数字。FR-9.2）: アプリの入力検証（API）と、Cognito のユーザープールの設定の両方に、同じ条件を置く。Cognito が拒否したときは、入力不正（`VALIDATION_ERROR`）にする
- **ユーザー管理（SC-14）**: 作成は、Cognito（`AdminCreateUser`。招待のメッセージは送らない）→ パスワードの設定（`AdminSetUserPassword`。恒久）→ DynamoDB の記録。再設定は、`AdminSetUserPassword` のあと、そのユーザーの全セッションを失効（`AdminUserGlobalSignOut`）。削除は、Cognito → DynamoDB の記録の順。途中で失敗しても、残った資格情報で別のユーザーが作られない・記録だけが先に消えない順序にする。記録のないまま残った Cognito のユーザーと、同じユーザーID を作るときは、引き継ぐ（古いセッションを失効）。記録はあるのに Cognito にいないユーザーの、パスワードの再設定は、Cognito のユーザーを作り直す
- **ログインの試行回数の制限**（同じ接続元から 15 分あたり 5 回まで。FR-9.2。ユーザーの判断。推奨案）: ローカルと同じ振る舞いを、Lambda の複数の実行環境でも保つため、**DynamoDB のカウンター**（`Main` の `LOGINFAIL`。接続元は、ハッシュにして保存。TTL で自動削除）で持つ。Cognito 自身の、ユーザーごとの一時的なロック（失敗が続いたとき。回数・時間は変えられない）と、二重の防御になる。Cognito の呼び出しの上限（スロットリング）は、失敗として数えず、`RATE_LIMITED` にする
- **最初のユーザー**（ユーザーの判断。推奨案）: Lambda は、環境変数の初期ユーザー（`INITIAL_USER_*`）を、**読まない**（設定すると、起動時の検証が拒否する）。運用者が、AWS のプロファイルを指定して、手元で、**1 回だけ**、コマンド（`pnpm initial-user`）を実行する。Cognito のユーザー（パスワードつき）と、DynamoDB の記録を、同時に作る。ユーザーが 1 人でもいれば、何もしない。パスワードは、実行時の環境変数で渡し、保存・出力しない。AWS のエラーは、名前だけを出力する（メッセージに、アカウント ID・ARN が含まれるため）
- **IaC**（`infra/lib/data-stack.ts`。`SfmData`）: ユーザープールも、状態（ユーザー）を持つため、データのスタックに置く（削除の保護・RETAIN）。管理者だけがユーザーを作る（自己登録・メール・SMS・MFA・パスワードの回復なし）。ユーザー名は、大文字・小文字を区別する（ローカルと同じ）。アプリクライアントは、シークレットなし、`ALLOW_ADMIN_USER_PASSWORD_AUTH` と `ALLOW_REFRESH_TOKEN_AUTH` だけ、ユーザーの存在を推測させない設定（`PreventUserExistenceErrors`）、トークンの失効を有効にする。機能のプランは、Essentials（10,000 MAU まで無料。architecture.md 11 章）。出力: `UserPoolId`・`UserPoolClientId`
- **Lambda に必要な IAM の権限**（Issue #75 で、ユーザープールの ARN に限って、付ける）: `cognito-idp:AdminInitiateAuth`・`AdminCreateUser`・`AdminSetUserPassword`・`AdminDeleteUser`・`AdminUserGlobalSignOut`。`GetUser`・`GlobalSignOut` は、アクセストークンで認可される API のため、IAM の権限は、不要

### 3. 暫定の代替（リスク対応）

Cognito が使えない（IAM の権限が足りない・振る舞いが想定と違う）場合は、**アプリ内の認証（セッションを DynamoDB に持つ版）を、評価環境の暫定にする**。必要になるのは、セッション（トークンのハッシュ・期限）を DynamoDB に持つ `SessionStore` と、ローカル認証のセッションの置き換え（約 150 行）。ユーザー・ロール・試行回数の制限（DynamoDB 版）は、今回の実装を、そのまま使える。**今は、実装しない**（Cognito の実装が、AWS での確認の前に、完了しているため。確認で問題が出たら、実装する）。

## 検討した代替案

| 案 | 採らなかった理由 |
|----|------------------|
| ロールを Cognito のグループ・カスタム属性に持つ | ロールの変更が、トークンの更新まで反映されない。ユーザー一覧・最終ログインの取得が、Cognito の API に依存する |
| アクセストークンの署名を、ローカルで検証する（`aws-jwt-verify`） | 速いが、パスワードの再設定・ログアウトの後も、アクセストークンが、期限（最大 30 分）まで有効。依存が増える。利用者が増えたときの選択肢として残す |
| Cognito のホスト型 UI（OAuth・PKCE） | 画面（ログイン画面・トークンの保持）の変更が大きい。同じオリジンの構成（ADR-0006）と、リダイレクトの設定が増える |
| 接続元ごとの試行回数の制限を、Cognito の組み込みだけにする | ユーザー単位のため、接続元ごとの制限（FR-9.2）が、実現できない |

## 結果・トレードオフ

### ローカルの実装との違い

| 項目 | ローカル | Cognito |
|------|----------|---------|
| ログアウト | その端末のセッションだけ終了 | **そのユーザーのすべての端末のセッションが終了**（`GlobalSignOut`。Cognito は、端末ごとに選べない） |
| 本人が自分のパスワードを再設定したとき | 現在のセッションは残り、ほかの端末は終了 | **現在のセッションも終了**（再ログイン。`keepAccessToken` は、使わない） |
| リフレッシュトークンの更新 | 更新のたびに、新しいトークンに替わる（古いものは無効） | 同じトークンを使い続ける（回転しない）。画面の更新の競合（Issue #60）は、起きにくい |
| リフレッシュトークンの期限の値 | 発行時に決まる | 更新の時点から 7 日の目安（画面は、使わない。期限は Cognito が検証する） |
| パスワードのハッシュ | ユーザーの記録（`passwordHash`）に持つ | 持たない（`UserRecord.passwordHash` は、任意） |
| 試行回数の制限 | プロセス内（メモリ） | DynamoDB（複数の実行環境で共有）+ Cognito のユーザーごとのロック |

### その他

- **トークンの長さ**: Cognito のトークンは長い（アクセストークン 約 1,000 文字、リフレッシュトークン 1,000 文字を超える。長さは、固定ではない）。API の入力の長さの上限（V-009）は、リフレッシュトークンを 4096 文字までとする（当初の 256 文字では、Cognito の更新が、必ず入力不正になった。AWS での確認で見つかり、Issue #95 で直した。偽の Cognito が、実際に近い長さのトークンを返すようにして、再発を防ぐ）
- 認証の呼び出しが、Cognito の API の上限（スロットリング）に当たると、`RATE_LIMITED` を返す。評価環境の規模（10 名程度）では、起きにくい
- ユーザーの記録（DynamoDB）と Cognito は、別々に書くため、途中で失敗すると、片方だけが残ることがある。書く順序と、引き継ぎ・作り直し（上の「ユーザー管理」）で、運用で回復できるようにした
- 画面は、アクセス・リフレッシュトークンを `sessionStorage` に持つ（dev_spec.md 4 章）。今回は変えない

## 検証

- 契約テスト（`tests/integration/auth-contract.test.ts`）を、ローカルの実装と、Cognito の実装（**偽の Cognito**。実際の AWS には接続しない）の両方に適用した。ログイン・更新・ログアウト・トークンの検証・失効・試行回数の制限・ユーザー管理（作成・パスワードの再設定・削除）が、同じ振る舞いになる。既存のテスト（認証・権限・ユーザー管理）は、変更なしで成功する。実装ごとの違いは、同じファイルの末尾に、別に書いた
- Cognito 固有のエラーの扱い・後始末、DynamoDB の試行回数の制限、組み立て、最初のユーザーのコマンドは、別のテストで確認した（`cognito-identity.test.ts`・`cognito-wiring.test.ts`・`user-service.test.ts`）
- **実際の Cognito での確認は、未実施**。IaC の AWS への適用（ユーザーが実行）のあとに、次を確認する: (1) `pnpm initial-user` で、最初のユーザーを作れる（Admin API の権限）。(2) そのユーザーで、ログイン・更新・ログアウトできる（`ADMIN_USER_PASSWORD_AUTH`）。(3) パスワードの誤り・存在しないユーザーで、同じ失敗になる。(4) 失敗を続けると、接続元の制限が働く。(5) ユーザー管理の画面で、作成・パスワードの再設定・削除ができ、削除・再設定のあと、古いトークンが、すぐ無効になる。(6) `GetUser` の応答の時間
