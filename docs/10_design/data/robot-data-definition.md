# 収穫ロボットのデータ定義

目的: 収穫ロボットのデータを、本システムが取り込むための仕様（項目・ファイルの構造・設備への割り付け・累積の値の扱い・ステータスコード・運用の仮定・欠損や異常値の扱い）を、提供元（ロボットの作り手・ファイルサーバーの管理者）に示せる形でまとめる。システム内の項目の一覧は [data-dictionary.md](./data-dictionary.md)、取り込みの仕組みは [architecture.md](../architecture/architecture.md) 5.1・5.4、実装での位置づけは [dev_spec.md](../functions/dev_spec.md) 4.2 を参照する。環境センサーの定義は [environment-sensor-data-definition.md](./environment-sensor-data-definition.md)。

## 1. 位置づけ

| 項目 | 内容 |
|------|------|
| 状態 | **確定**（版 1.0.0。取り込んだ観測値に残る版の表記は `robot-json@1.0.0(CONFIRMED)`） |
| 意味 | 本システムが定める、収穫ロボットの取り込み仕様。提供元から別の定義が示されていない間は、この定義で取り込む |
| 提供元の定義が示されたとき | 差分（項目・型・単位・値の範囲・累積の基準・ステータスコードの一覧・ファイルの形式・構造・計測日時・更新の頻度・配置方法）を洗い出し、影響を確認して、形式定義を追加・差し替え、**版を上げる**（9 章） |
| ロボットの機種・提供元の定義 | 未入手。この定義は、構想時の項目と、提供元から示された「1 つのファイルを随時更新していく」方式（更新のたびに全体が書き換わり、中身は最新の値だけ。設備ごとにファイルを分ける）に合わせて定めた |
| 手動入力との関係 | 同じ項目は、手動でも入力できる（予備の入口。取得元が「自動・手動の両方」）。合計の項目は、評価の期間に自動取り込みの値があれば自動だけを使い、なければ手動だけを使う（4 章） |
| 使う観点 | 収穫精度・収穫速度・安全性・コスト効率・メンテナンス性・耐久性（[robot-health.md](../viewpoint/robot-health.md)。項目ごとの観点は 2 章） |

## 2. 項目

項目は、収穫数・1 果実あたりの収穫時間・稼働時間・待機時間・収穫稼働時間・走行停止時間・ステータスコードの 7 つ。ファイルの項目名（ファイルの中のキー）は、システム内の識別子（`camelCase`）と**同じ**。単位は、この表のとおり（ファイルには書かない）。

| ファイルの項目名（＝識別子） | 日本語名 | 型 | 単位 | 意味 | 値の範囲（範囲外は不正） | 必須／任意 | 使う観点 | 根拠 | 確認したい点 |
|------------------------------|----------|----|------|------|--------------------------|------------|----------|------|--------------|
| `harvestCount` | 収穫数 | 整数 | 個 | 収穫した果実の累計（**累積の値**。4 章） | 0 以上 | 任意（値がなければ `null`） | 収穫精度・収穫速度・コスト効率 | 構想時の項目。件数のため、整数で負でない値 | 累積の基準（今日の分・電源投入後・通算）。収穫に成功した数か、試行した数か |
| `harvestSecondsPerFruit` | 1果実あたりの収穫時間 | 数値（小数可） | 秒/果実 | 1 果実の収穫にかかった時間（その時点の値。累積ではない） | 0〜3,600（手動入力は 0〜300） | 任意（値がなければ `null`） | （参考。収穫速度の平均処理時間は、収穫稼働時間と収穫数から算出する） | 構想時の項目。範囲は、ゆるく取り、極端な値（故障・単位の取り違えなど）を不正として区別できる広さにした（[ADR-0016](../adr/0016-ingestion-federation-rules.md) の D-10） | 秒で出力されるか。直近の 1 果実か、平均か。出力しない場合は、収穫稼働時間と収穫数から算出する |
| `operatingHours` | 稼働時間 | 数値（小数可） | 時間 | ロボットが稼働していた時間（**累積の値**。4 章） | 0 以上 | 任意（値がなければ `null`） | 安全性・コスト効率・耐久性 | 構想時の項目。単位は、収穫時間の算出式（収穫稼働時間 × 3600 ÷ 収穫数 が 1 果実あたりの秒数）から「時間」とした | 時間の単位（時間か、秒・分か）。累積の基準 |
| `standbyHours` | 待機時間 | 数値（小数可） | 時間 | 待機していた時間（**累積の値**。4 章） | 0 以上 | 任意（値がなければ `null`） | （参考。どの観点の判定にも使わない） | 構想時の項目。稼働時間と同じ単位 | 時間の単位。累積の基準 |
| `harvestOperatingHours` | 収穫稼働時間 | 数値（小数可） | 時間 | 収穫の作業をしていた時間（**累積の値**。4 章） | 0 以上 | 任意（値がなければ `null`） | 収穫速度・コスト効率 | 構想時の項目。稼働時間と同じ単位 | 時間の単位。累積の基準。稼働時間に含まれるか |
| `travelStoppedHours` | 走行停止時間 | 数値（小数可） | 時間 | 走行が止まっていた時間（**累積の値**。4 章） | 0 以上 | 任意（値がなければ `null`） | 収穫速度 | 構想時の項目。稼働時間と同じ単位 | 時間の単位。累積の基準。稼働時間に含まれるか |
| `statusCode` | ステータスコード | 文字列 | （なし） | ロボットの状態を表すコード値（5 章） | 登録済みのコード値（未登録・論理削除の値は不正） | 任意（値がなければ `null`） | 収穫速度・メンテナンス性・耐久性 | 構想時の項目。コードの一覧は、構想時の定義を初期値にした | コード値の一覧と意味（5 章）。コードが数値や、別の形式で出力されないか |

- 数値の範囲の境界（0 と 3,600）は有効。範囲の外の値は、評価に使わない（7 章）。
- 7 項目は、**すべて任意**。ファイルに、一部の項目だけがあってもよい。必須なのは、`timestamp`（3 章）。
- 項目の追加・単位の変更は、この版では行わない（追加が必要になったら、9 章のとおり、版を上げて扱う）。
- 収穫成功回数・収穫試行回数・誤認識数などは、ファイルの項目に含めない（手動入力の項目として扱う。入力できる項目は [data-dictionary.md](./data-dictionary.md) 5.2）。ロボットから取得できる項目が増える場合は、8 章で確認する。

## 3. ファイルの構造

### 3.1 構造

- **1 台のロボットにつき、1 つのファイル**。形式は、UTF-8 の JSON（先頭の BOM があっても読める）。
- ファイルは、**その時点のスナップショット 1 つ**（計測日時 `timestamp` と、各項目のフラットな JSON）。配列・入れ子は、使わない。
- ファイルは、**更新のたびに全体が書き換わり、中身は最新の値だけ**を持つ（1 つのファイルを随時更新する方式）。履歴は、本システムが、取得を繰り返して積み上げる。通常は 1 MB 以内を想定する（本システムが読む上限は 10 MiB）。
- ファイルの中に、**設備（ロボット）の識別子は、持たない**。ファイルがどの設備のものかは、設備ごとのファイルのパスで決める（3.3）。

| キー | 型 | 必須 | 内容 |
|------|----|------|------|
| `timestamp` | 文字列（ISO 8601） | ○ | 計測日時。3.2 のとおり読む |
| `harvestCount` | 整数または `null` | 任意 | 収穫数（個）。2 章 |
| `harvestSecondsPerFruit` | 数値または `null` | 任意 | 1 果実あたりの収穫時間（秒/果実）。2 章 |
| `operatingHours` | 数値または `null` | 任意 | 稼働時間（時間）。2 章 |
| `standbyHours` | 数値または `null` | 任意 | 待機時間（時間）。2 章 |
| `harvestOperatingHours` | 数値または `null` | 任意 | 収穫稼働時間（時間）。2 章 |
| `travelStoppedHours` | 数値または `null` | 任意 | 走行停止時間（時間）。2 章 |
| `statusCode` | 文字列または `null` | 任意 | ステータスコードのコード値。2 章・5 章 |

- **値のない項目は `null`** にする（欠損。0 で代用しない）。項目そのものを書かなくてもよい（その項目は、そのファイルについて、取り込まない〔未取得〕）。
- 数値は JSON の数値で書く。文字列（例: `"3.25"`）は、不正な値として扱う。
- 上の表にないキー（旧来の設備の識別子・記録の配列を含む）は、読まない。`timestamp` も、上の 7 項目も、1 つもないファイルは、構造が仕様と異なるファイルとして扱う（7 章）。

### 3.2 計測日時（`timestamp`）

| 書き方 | 例 | 読み方 |
|--------|----|--------|
| UTC（`Z`） | `2026-10-09T02:00:00Z` | そのまま |
| オフセットつき | `2026-10-09T11:00:00+09:00` | そのまま（空白区切りは `T` に直して読む） |
| タイムゾーンなし | `2026-10-09T11:00:00` | **日本時間（+09:00）として読む**。秒の省略・小数秒つき・空白区切り（`2026-10-09 11:00:00`）も読める |

ISO 8601 以外の形式（`Oct 9 2026`・エポック秒など）・日付のみ・存在しない日時は、読めない日時として扱う（そのファイルは、読み取れなかった記録として数える）。**ロボットの時計は、正しい時刻に合わせておく**（現在から 5 分を超える未来の日時は、不正）。

### 3.3 設備への割り付け（設備ごとに 1 ファイル）

- 本システムは、**設備（ロボット）ごとに、ファイルのパス（設備の `sourceFilePath`。ファイルサーバー〔HTTP〕の、`/` で始まるパス）を設定**し、そのパスのファイルを、その設備のデータとして取り込む。
- **1 設備 = 1 ファイル**。ファイルのパスは、設備（環境センサーを含む）の間で重複させない（ほかの設備と同じパスは、登録できない）。ファイルの中の識別子で、設備を見分ける仕組みは、持たない。
- 設備ごとの接続・認証は、設備ごとに設定する（取り込みの設定は、画面〔取り込み〕・設備管理で行う）。本定義の対象外。

### 3.4 サンプル（合成データ。実データではない）

例 1: 通常（UTC の日時。累積の値）

```json
{
  "timestamp": "2026-10-09T02:00:00Z",
  "harvestCount": 128,
  "harvestSecondsPerFruit": 42.5,
  "operatingHours": 3.25,
  "standbyHours": 0.5,
  "harvestOperatingHours": 2.5,
  "travelStoppedHours": 0.125,
  "statusCode": "HARVESTING"
}
```

例 2: 欠損（1 果実あたりの収穫時間が `null`）・タイムゾーンなしの日時（日本時間）・項目の省略（走行停止時間がない）。累積の値は、例 1 から増えている

```json
{
  "timestamp": "2026-10-09T11:10:00",
  "harvestCount": 130,
  "harvestSecondsPerFruit": null,
  "operatingHours": 3.4,
  "standbyHours": 0.5,
  "harvestOperatingHours": 2.6,
  "statusCode": "STANDBY"
}
```

この 2 つのサンプルは、テスト（`tests/fixtures/file-server/robot/` の `robot-definition-sample-001.json`・`robot-definition-sample-002-partial.json`）で、実際の形式定義で取り込めることと、文書と同じ内容であることを確認している。

## 4. 累積の値の扱い

- **合計の 5 項目**（収穫数・稼働時間・待機時間・収穫稼働時間・走行停止時間）の、ファイルの値は、**時間とともに増える累積の値**（その時点のスナップショット）。増分（前回からの差）を書くのではなく、累積の値を、そのまま書く。1 果実あたりの収穫時間とステータスコードは、その時点の値（累積ではない）。
- **期間の値は、期間内の増分の合計**として求める（評価・推移）。設備ごとに、計測日時の順に、直前の値との差を足す。**期間の直前の値を基準にし**、なければ 0 から始まるとみなす。
- **値が減ったときは、リセットとみなし**、減った時点の値そのものを増分にする（ロボットの電源を入れ直す・日が変わるなどで、累積が 0 に戻っても壊れない）。
- 累積の値なので、取得の合間の更新を取りこぼしても、次の値に含まれる（増分で書くと、取りこぼした分が失われる）。累積の値を足すと過大になるため、足さない（例: 8:00 に 0、12:00 に 1,200、16:00 に 2,400 なら、1 日の値は 2,400）。
- 手動入力の同じ項目も、同じ意味（「今日これまでの累計」など）で入力する。取得元を混ぜると累積が壊れるため、評価の期間に自動取り込みの値が 1 件でもあれば、自動だけを使い、手動は使わない（[ADR-0018](../adr/0018-manual-input-and-data-rules.md) の D-26）。
- **累積の基準（今日の分・電源投入後・通算のどれか）は、提供元の確認前の想定**。どの基準でも、上の「値が減ったらリセット」の規則で、期間の値は求められる。基準が分かったら、8 章の確認の結果として、本章を更新する。

## 5. ステータスコード

- ファイルの `statusCode` は、ステータスコードの**コード値**（`code`。英大文字で始まり、英大文字・数字・アンダースコア。100 文字以内。例: `HARVESTING`）。
- **登録済みのコード値**（[data-dictionary.md](./data-dictionary.md) 7 章。設定画面〔ステータスコード〕で、名称・カテゴリ〔正常／注意／異常〕とともに登録する）だけを、有効とする。初期の登録値は、`STANDBY`（待機中）・`RUNNING`（走行中）・`HARVESTING`（収穫中）・`STOPPED`（停止中）・`LOW_BATTERY`（バッテリー不足）・`RUNNING_ERROR`（走行異常）・`HARVEST_ERROR`（収穫異常）・`FALLEN`（転倒〔姿勢異常〕）。この一覧は、構想時の定義で、提供元の確認前の想定（8 章）。
- **未登録のコード値・論理削除したコード値は、不正**として、棄却せず、不正の品質で保存する（元の値は残す。評価には使わない）。コード値ごとに集計した一覧（未登録のコード値。画面 SC-12）で確認でき、そこから登録できる。
- コード値を登録しても、**保存済みの不正の観測値は、再判定しない**（登録後に取り込んだ値から有効になる）。

## 6. 運用の仮定

提供元に確認できていない、運用についての仮定。確認できたら、本章を更新する（8 章）。

| 事項 | 仮定 |
|------|------|
| 更新の頻度 | ロボットが、ファイルを、1 分おき程度に更新する。本システムの取得間隔の既定は **1 分**（設備ごとに、1・5・10・15・30・60 分から選ぶ）。ロボットの更新が取得間隔より遅いときは、新しい値がない周期は、何もしない。速いときは、取得の間の値は、取り込まれない（ファイルは、最新の値だけを持つため。累積の項目は、次の値に含まれる） |
| ファイルの配置 | 設備（ロボット）ごとに 1 つのファイルを、ファイルサーバー（HTTP）の `/` で始まるパスに置く（3.3）。本システムは、読み取り専用で取得する。機体が複数あるときは、機体ごとにファイルを分ける |
| 1 つのファイルを随時更新する方式 | 更新のたびに全体を書き換える。書き換えの途中のファイルを読まないよう、更新日時が 1 秒以内のファイルは、次の周期に回す（一時ファイルに書いてから置き換える方式が望ましい） |
| 取り込まれ方 | 毎周期、ファイルを読み、**新しい計測日時の値、または、同じ計測日時で値が変わったものだけ**を保存する（同じ値は、触らない）。履歴は、取得を繰り返して積み上がる |
| 計測日時 | ロボットの時計が正しい。タイムゾーンを書かない場合は、日本時間 |
| 設備の識別子 | ファイルの中には持たない（設備は、ファイルのパスで決める。3.3）。設備のデータ上の識別子（`externalId`）は、取り込みの照合には使わない |

## 7. 欠損・異常値・遅延の扱い

評価での扱いの定義は、[ADR-0016](../adr/0016-ingestion-federation-rules.md) の D-10 に従う。ロボットのファイルでは、次のように扱う。

| ファイルの内容 | 品質 | 評価での扱い |
|----------------|------|--------------|
| 値が範囲内の数値・登録済みのコード値 | 有効 | 使う |
| 値が `null`（値がない項目） | 欠損 | 使わない（0 で代用しない）。取り込みの記録に、棄却として数える |
| 項目を書いていない | （保存しない） | そのファイルについては、取り込まない |
| 値が範囲外（例: 収穫数 −3、1 果実あたりの収穫時間 3,600.5）・整数でない収穫数（12.5） | 不正 | 使わない。元の値は残し、棄却として数える |
| 値が数値でない（例: `"abc"`・`"3.25"`） | 不正 | 同上 |
| 未登録・論理削除のステータスコード | 不正 | 同上（5 章。未登録のコード値の一覧に集計する） |
| 計測日時が、受信より 5 分を超えて未来 | 不正 | 同上 |
| 受信が、計測日時から 60 分を超えて遅れた | 遅延 | **使う**（棄却に数えない） |
| `timestamp` がない・読めない（項目はある） | （読み取れなかった記録） | 取り込まない。取り込みの記録に、読み取れなかった数として数える |
| JSON として読めない・トップが JSON のオブジェクトでない・`timestamp` も 7 項目もない・`timestamp` はあるが 7 項目が 1 つもない（項目名が違う） | （形式違いのファイル） | そのファイルは取り込まず、失敗として記録・通知する |

## 8. 確認したい点

提供元（ロボットの作り手・ファイルサーバーの管理者）に、確認したいこと。

1. **累積の基準**: 合計の 5 項目（収穫数・稼働時間・待機時間・収穫稼働時間・走行停止時間）が、今日の分・電源投入後・通算のどれか。値が減るのは、どんなとき（日が変わる・電源の入れ直しなど）か
2. **時間の単位**: 稼働時間・待機時間・収穫稼働時間・走行停止時間の単位（本定義は「時間」の小数）。1 果実あたりの収穫時間の単位（本定義は秒）。収穫稼働時間・走行停止時間が、稼働時間に含まれるか
3. **ステータスコードの一覧**: ロボットが出力するコード値の一覧と、それぞれの意味（正常・注意・異常の区別）。形式（本定義は、英大文字・数字・アンダースコアの文字列）
4. **項目**: 7 項目が出力できるか。収穫数の意味（成功した数か、試行した数か）。1 果実あたりの収穫時間は、直近の値か、平均か。ほかに出力される項目（追加したい項目。収穫成功回数など）はあるか
5. **ファイルの形式・構造**: 本定義（JSON。その時点のスナップショット 1 つ。項目名は 2 章のとおり）に合わせられるか。異なる場合は、項目・型・単位・構造の違いを教えてほしい（差分を洗い出して、版を上げる）
6. **更新の頻度**: ファイルを更新する間隔。本システムの取得間隔（既定 1 分）で足りるか
7. **配置方法**: ファイルを置く場所（パスの規則）。機体（ロボット）ごとにファイルを分けられるか（台数が増えたときの置き方を含む）。書き換えの方法（一時ファイルに書いてから置き換えるか）
8. **計測日時**: タイムゾーンの扱い（UTC か、オフセットつきか、日本時間のタイムゾーンなしか）。ロボットの時計を合わせる方法
9. **欠損の表し方**: 計測できないときの出力（`null` にできるか。項目を省くか）

## 9. 変更の方針（版の上げ方）

- 提供元の定義が示されたら、(1) 本定義との差分を洗い出し（項目・型・単位・値の範囲・累積の基準・ステータスコードの一覧・ファイルの形式・構造・計測日時・更新の頻度・配置方法）、(2) 影響（評価のメトリクス・判断基準・画面・手動入力・連携・保存済みのデータ）を確認し、(3) 形式定義（`robot-json`）の新しい版を追加（提供された形式が大きく違うときは、新しい形式定義を追加）して、(4) 本文書の版の履歴（10 章）と、[data-dictionary.md](./data-dictionary.md) 10.2 に、差分と影響を記録する。
- 版の付け方: 項目・構造が互換のままの補足・修正は、修正の版（1.0.x）。互換性を保った拡張（任意の項目の追加など）は、副の版（1.x.0）。互換性のない変更（項目名・構造・単位の変更）は、主の版（2.0.0）。
- 取り込んだ観測値には、解釈に使った版を残す。**保存済みの観測値・取り込みの記録の版の表記は、移行しない**（過去の表記は、そのまま残る）。
- 項目の追加・範囲の変更・単位の変更は、項目の定義・データ辞書・評価の観点・手動入力の見直しを伴う（別に設計する）。
