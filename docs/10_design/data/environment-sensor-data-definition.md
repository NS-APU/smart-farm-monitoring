# 環境センサーのデータ定義

目的: 環境センサーのデータを、本システムが取り込むための仕様（項目・ファイルの構造・運用の仮定・欠損や異常値の扱い）を、提供元（センサーの作り手・ファイルサーバーの管理者）に示せる形でまとめる。システム内の項目の一覧は [data-dictionary.md](./data-dictionary.md)、取り込みの仕組みは [architecture.md](../architecture/architecture.md) 5.1・5.4、実装での位置づけは [dev_spec.md](../functions/dev_spec.md) 4.2 を参照する。

| 意味 | 本システムが定める、環境センサーの取り込み仕様。提供元から別の定義が示されていない間は、この定義で取り込む |
| 提供元の定義が示されたとき | 差分（項目・型・単位・値の範囲・ファイルの形式・構造・計測日時・更新の頻度・配置方法）を洗い出し、影響を確認して、形式定義を追加・差し替え、**版を上げる**（7 章） |

| 使う観点 | 環境適応性（[house-health.md](../viewpoint/house-health.md)） |

## 2. 項目

項目は、温度・湿度・照度・CO2濃度の 4 つ。識別子（`camelCase`）は、ファイルの中のキー名と、本システムの項目の識別子で、同じ。

| 識別子 | 日本語名 | 型 | 単位 | 意味 | 値の範囲（範囲外は不正） | 必須／任意 | 根拠 | 確認したい点 |
|--------|----------|----|------|------|--------------------------|------------|------|--------------|
| `temperatureCelsius` | 温度 | 数値（小数可） | ℃ | ハウス内の気温 | -50〜100 | 任意（値がなければ `null`） | 構想時の項目。範囲は、ハウス内で起こりうる値と、センサーの故障・単位の取り違えを区別できる広さにした | 摂氏で出力されるか。計測の位置（作物の高さ）。小数点以下の桁数 |
| `humidityPercent` | 湿度 | 数値（小数可） | % | ハウス内の相対湿度 | 0〜100 | 任意（値がなければ `null`） | 構想時の項目。相対湿度の定義の範囲 | 相対湿度か（絶対湿度でないか）。小数点以下の桁数 |
| `illuminanceLux` | 照度 | 数値（小数可） | lx | ハウス内の照度 | 0〜200,000 | 任意（値がなければ `null`） | 構想時の項目。範囲は、屋外の直射日光（約 10 万 lx）を超える値を、故障・単位の取り違えとして区別できる広さにした | 単位が lx か（日射量〔W/m²〕など、別の量でないか）。計測の位置。夜間の値（0 に近い値になる想定） |
| `co2Ppm` | CO2濃度 | 数値（小数可） | ppm | ハウス内のCO2濃度 | 0〜10,000 | 任意（値がなければ `null`） | 構想時の項目。範囲は、ハウス内の濃度（数百〜数千 ppm）と、センサーの測定の上限の目安から定めた | 単位が ppm か（%で出力する機種はないか）。測定の範囲 |

- 値の範囲の境界（-50 と 100、0 と 100、0 と 200,000、0 と 10,000）は有効。範囲の外の値は、評価に使わない（5 章）。
- 4 項目は、**すべて任意**。1 つの記録に、一部の項目だけがあってもよい。必須なのは、ファイルの `sensorId` と `records`、各記録の `timestamp`（3 章）。
- 項目の追加・単位の変更は、この版では行わない（追加が必要になったら、7 章のとおり、版を上げて扱う）。

## 3. ファイルの構造

### 3.1 構造

- **1 台のセンサーにつき、1 つのファイル**。形式は、UTF-8 の JSON（先頭の BOM があっても読める）。
- ファイルは、**更新のたびに全体が書き換わり、中身は最新の値（または直近の少数）だけ**を持つ（1 つのファイルを随時更新する方式）。通常は 1 MB 以内を想定する（本システムが読む上限は 10 MiB）。

| キー | 型 | 必須 | 内容 |
|------|----|------|------|
| `sensorId` | 文字列（空でない） | ○ | ファイル全体で 1 台のセンサーの識別子。設備（センサー）の外部の識別子 `externalId` に対応づける |
| `records` | 配列 | ○ | 記録の配列。最新の 1 件、または直近の少数。記録がなければ空の配列 |
| `records[].timestamp` | 文字列（ISO 8601） | ○ | 計測日時。3.2 のとおり読む |
| `records[].temperatureCelsius` | 数値または `null` | 任意 | 温度（℃）。2 章 |
| `records[].humidityPercent` | 数値または `null` | 任意 | 湿度（%）。2 章 |
| `records[].illuminanceLux` | 数値または `null` | 任意 | 照度（lx）。2 章 |
| `records[].co2Ppm` | 数値または `null` | 任意 | CO2濃度（ppm）。2 章 |

- **値のない項目は `null`** にする（欠損。0 で代用しない）。項目そのものを書かなくてもよい（その項目は、その記録について、取り込まない〔未取得〕）。
- 数値は JSON の数値で書く。文字列（例: `"24.5"`）は、不正な値として扱う。

### 3.2 計測日時（`timestamp`）

| 書き方 | 例 | 読み方 |
|--------|----|--------|
| UTC（`Z`） | `2026-10-09T02:00:00Z` | そのまま |
| オフセットつき | `2026-10-09T11:00:00+09:00` | そのまま（空白区切りは `T` に直して読む） |
| タイムゾーンなし | `2026-10-09T11:00:00` | **日本時間（+09:00）として読む**。秒の省略・小数秒つき・空白区切り（`2026-10-09 11:00:00`）も読める |

ISO 8601 以外の形式（`Oct 9 2026`・エポック秒など）・日付のみ・存在しない日時は、読めない日時として扱う（その記録は、読み取れなかった記録として数える）。**センサーの時計は、正しい時刻に合わせておく**（現在から 5 分を超える未来の日時は、不正）。

### 3.3 サンプル（合成データ。実データではない）

例 1: 通常（2 件の記録。UTC の日時）

```json
{
  "sensorId": "SENSOR-SAMPLE-01",
  "records": [
    {
      "timestamp": "2026-10-09T02:00:00Z",
      "temperatureCelsius": 24.5,
      "humidityPercent": 62.0,
      "illuminanceLux": 48000,
      "co2Ppm": 650
    },
    {
      "timestamp": "2026-10-09T02:05:00Z",
      "temperatureCelsius": 24.8,
      "humidityPercent": 61.5,
      "illuminanceLux": 49500,
      "co2Ppm": 640
    }
  ]
}
```

例 2: 欠損（湿度が `null`）・タイムゾーンなしの日時（日本時間）・項目の省略（2 件目に CO2濃度がない）

```json
{
  "sensorId": "SENSOR-SAMPLE-01",
  "records": [
    {
      "timestamp": "2026-10-09T11:10:00",
      "temperatureCelsius": 25.1,
      "humidityPercent": null,
      "illuminanceLux": 51000,
      "co2Ppm": 630
    },
    {
      "timestamp": "2026-10-09T11:15:00",
      "temperatureCelsius": 25.3,
      "humidityPercent": 60.0,
      "illuminanceLux": 52000
    }
  ]
}
```

この 2 つのサンプルは、テスト（`tests/fixtures/file-server/environment-sensor/` の `sensor-definition-sample-001.json`・`sensor-definition-sample-002-partial.json`）で、実際の形式定義で取り込めることと、文書と同じ内容であることを確認している。

## 4. 運用の仮定

提供元に確認できていない、運用についての仮定。確認できたら、本章を更新する（6 章）。

| 事項 | 仮定 |
|------|------|
| 更新の頻度 | センサーが、ファイルを、数分おきに更新する。本システムの取得間隔の既定は **5 分**（設備ごとに、1・5・10・15・30・60 分から選ぶ）。センサーの更新が取得間隔より遅いときは、新しい値がない周期は、何もしない。速いときは、ファイルに直近の記録を複数入れておくと、取りこぼさない |
| ファイルの配置 | 設備（センサー）ごとに 1 つのファイルを、ファイルサーバー（HTTP）の `/` で始まるパスに置く。本システムは、読み取り専用で取得する。設備ごとのパスは、設備の `sourceFilePath` に設定する |
| 1 つのファイルを随時更新する方式 | 更新のたびに全体を書き換える。書き換えの途中のファイルを読まないよう、更新日時が 1 秒以内のファイルは、次の周期に回す（一時ファイルに書いてから置き換える方式が望ましい） |
| 取り込まれ方 | 毎周期、ファイルを読み、**新しい計測日時の値、または、同じ計測日時で値が変わったものだけ**を保存する（同じ値は、触らない）。ファイルから消えた記録は、反映しない。履歴は、取得を繰り返して積み上がる |
| 設備の識別子との対応 | ファイルの `sensorId` は、設備（センサー）の `externalId` と同じ値にする。登録のない `sensorId` の記録は、読み取れなかった記録として数える（削除済みの設備の識別子は、別に数える） |
| 計測日時 | センサーの時計が正しい。タイムゾーンを書かない場合は、日本時間 |
| 接続・認証 | 設備ごとに設定する。本定義の対象外（取り込みの設定は、画面〔取り込み〕で行う） |

## 5. 欠損・異常値・遅延の扱い

評価での扱いの定義は、[ADR-0016](../adr/0016-ingestion-federation-rules.md) の D-10 に従う。環境センサーのファイルでは、次のように扱う。

| ファイルの内容 | 品質 | 評価での扱い |
|----------------|------|--------------|
| 値が範囲内の数値 | 有効 | 使う |
| 値が `null`（値がない項目） | 欠損 | 使わない（0 で代用しない）。取り込みの記録に、棄却として数える |
| 項目を書いていない | （保存しない） | その記録については、取り込まない |
| 値が範囲外（例: 温度 100.5、湿度 120） | 不正 | 使わない。元の値は残し、棄却として数える |
| 値が数値でない（例: `"abc"`・`"24.5"`） | 不正 | 同上 |
| 計測日時が、受信より 5 分を超えて未来 | 不正 | 同上 |
| 受信が、計測日時から 60 分を超えて遅れた | 遅延 | **使う**（棄却に数えない） |
| `timestamp` がない・読めない | （読み取れなかった記録） | 取り込まない。取り込みの記録に、読み取れなかった数として数える |
| JSON として読めない・`sensorId` または `records` がない | （形式違いのファイル） | そのファイルは取り込まず、失敗として記録・通知する |

## 6. 確認したい点

提供元（センサーの作り手・ファイルサーバーの管理者）に、確認したいこと。環境センサーの機種は、特定していない。

1. **機種・取得方式**: 使うセンサー（自作の機器を含む）と、データの取得方式。ファイルサーバーに置いたファイルを読む方式でよいか（センサーからの直接送信など、別の方式になる場合は、新しい入口を追加する）
2. **ファイルの形式・構造**: 本定義（JSON。`sensorId` と `records`。項目名は 2 章のとおり）に合わせられるか。異なる場合は、項目・型・単位・構造の違いを教えてほしい（差分を洗い出して、版を上げる）
3. **項目**: 温度・湿度・照度・CO2濃度の 4 項目の、単位・精度（小数点以下の桁数）・計測の位置・測定の範囲。ほかに出力される項目（追加したい項目）はあるか
4. **更新の頻度**: ファイルを更新する間隔。1 つのファイルに複数の記録を入れるか（最新の 1 件だけか、直近の少数か）
5. **配置方法**: ファイルを置く場所（パスの規則）。設備（センサー）ごとにファイルを分けられるか。書き換えの方法（一時ファイルに書いてから置き換えるか）
6. **識別子**: `sensorId` の付け方（1 台ごとに一意か）
7. **計測日時**: タイムゾーンの扱い（UTC か、オフセットつきか、日本時間のタイムゾーンなしか）。センサーの時計を合わせる方法
8. **欠損の表し方**: 計測できないときの出力（`null` にできるか。項目を省くか）。夜間の記録の有無

## 7. 変更の方針（版の上げ方）

- 提供元の定義が示されたら、(1) 本定義との差分を洗い出し（項目・型・単位・値の範囲・ファイルの形式・構造・計測日時・更新の頻度・配置方法）、(2) 影響（環境適応性の評価・画面・手動入力・連携）を確認し、(3) 形式定義（`environment-sensor-json`）の新しい版を追加（提供された形式が大きく違うときは、新しい形式定義を追加）して、(4) 本文書の版の履歴（8 章）と、[data-dictionary.md](./data-dictionary.md) 10.2 に、差分と影響を記録する。
- 版の付け方: 項目・構造が互換のままの補足・修正は、修正の版（1.0.x）。互換性を保った拡張（任意の項目の追加など）は、副の版（1.x.0）。互換性のない変更（項目名・構造・単位の変更）は、主の版（2.0.0）。
- 取り込んだ観測値には、解釈に使った版を残す。**保存済みの観測値・取り込みの記録の版の表記は、移行しない**（過去の表記は、そのまま残る）。
- 項目の追加・範囲の変更は、項目の定義・データ辞書・評価の観点・手動入力の見直しを伴う（別に設計する）。
