## 1. 共通事項

### 1.1 構成

- 画面は、React の SPA（PWA）。API は、REST（JSON）で、Hono を使った Lambda の関数として提供する（[ADR-0005](../adr/0005-tech-stack.md)）
- 画面は、日本語で表示する。PC・タブレット・スマートフォンで閲覧・入力できる（NFR-7.1、NFR-7.3。#142 の D-33 の決定）。狭い幅（900px 以下）では、表（SC-03 の判断基準・SC-05・SC-07・SC-08・SC-09・SC-11・SC-12・SC-14）を、1 行ごとのカード（項目名と値）で表示し、判断基準の編集（SC-13）は、保存・既定値へ戻すボタンを画面の下に固定する（#151）。設備管理（SC-10）は、表の枠の中で横にスクロールする
- 画面のデザイン（方向性・色・アイコン・共通のレイアウト）は、[ui-design-guidelines.md](./ui-design-guidelines.md) に従う
- 状態の更新は、画面が約10秒間隔で、保存済みの最新の評価結果を読み直す（タブの表示中のみ。FR-6.7）
- ロボット・ハウスを操作する機能はない（自動制御を行わない。goals.md）

### 1.2 共通のルール

| 項目 | 内容 |
|------|------|
| 認証 | ログインしたユーザーのみが、画面・APIを使える。未認証のアクセスは、ログイン画面へ誘導する（FR-9.1）。APIは、すべて認証トークンを検証する |
| 権限 | 要ログイン。操作ごとのロール制御は、管理者・一般の 2 ロール（ADR-0013 の表。実装済み〔#115〕。設備の割り当ては、実装済み〔#330〕。通知の絞り込みも、実装済み〔#331〕。ログは #332。FR-9.5） |
| 時刻 | APIは UTC（ISO 8601）で扱い、画面は日本時間（`Asia/Tokyo`）で表示する |
| 欠損・不明 | 欠損は「—」（ダッシュ）で表示する。評価できない観点は、ステータス「不明」で、理由と推奨アクションを表示する（FR-5.5） |
| ステータスの表示 | 正常／注意／異常／不明を、色・アイコン・文字で示す。色だけに頼らない（NFR-7.2） |
| 一覧 | ページ分割（既定 20件）。並べ替え・絞り込みの条件は、URLのクエリに反映し、再読み込みで保持する。**共通の部品（#152）**: 絞り込みの枠は、**適用中の条件の数**（初期値と違う条件の数。絞り込み・並べ替えを含む。「適用中の条件 3 件」）と、**条件のクリア**（条件をすべて初期値に戻す。URL のクエリから外す。適用中の条件がなければ選べない）を、項目の上に示す。**狭い幅（900px 以下）は、項目を折りたたみ**、開閉のボタン（「絞り込みを開く／閉じる」。`aria-expanded`）で開く（折りたたんでも、条件の数と条件のクリアは見える。広い幅は、常に開く）。ページ送りは、**表示範囲**（「21〜40 件目」）を示す。**総件数・総ページは示さない**（カーソル方式のため。1 年で約 63 万件の想定）。対象: SC-05・SC-07・SC-08・SC-09・SC-11（取り込みのログ。ページ送りの表示範囲は、連携の結果・ハウス別の記録も） |
| 入力の検証 | 画面とAPIの両方で検証する（画面は即時のフィードバック、APIが正）。不正な場合は、項目ごとにエラーを表示して、再入力を促す（FR-4.1.3） |
| 結果の通知 | 保存・修正・削除・接続の確認などの結果は、共通の部品（`ResultNotice`。データ入力の保存結果のパネルは、同じ規則の `useRevealOnChange`）で示す。`role="status"` でスクリーンリーダーに通知し、**表示されたとき（現れた・変わったとき）に、画面内になければスクロールする**（すでに見えていれば動かない。動きを減らす設定のときは、アニメーションしない）。**フォーカスは動かさない**（結果の通知は、操作できる要素を持たないため。押したボタンの位置を失わない）。成功は完了メッセージ（形のアイコン + 文字）、失敗は `form-error` の見た目。画面全体のエラー（`role="alert"`）は、この部品ではなく、従来どおり（#150） |
| 確認 | 削除などの取り消しにくい操作は、確認を求める。確認のダイアログには、対象（どのデータか）を、ラベルと値で示す。影響があるものは、影響の説明を添える（共通の部品 `ConfirmDialog`。対象の項目と影響の説明を、任意で示せる。#153） |
| 空の状態 | データがない場合は、その旨と、次の操作（例: データの入力）を表示する |
| ヘルプ | 判断基準（閾値・ステータスの意味）を画面から参照できる。主要な操作に、ツールチップを表示する（NFR-7.4）。**共通の部品（#154）**: 指標名・入力欄のラベルの横に、**ヘルプヒント**（「?」のボタン。ボタンの名前は「{対象}の説明」。押す・Enter・Space で、説明を開く。`aria-expanded`。もう一度押す・Esc〔ダイアログの中でも、ヒントだけを閉じる〕・外側を押す・フォーカスが外へ移る、で閉じる。同時に開くのは 1 つ。狭い幅でも、画面の幅に収める。`title` 属性だけには頼らない）を置く。状態の意味は、**折りたたみ式の凡例**（はじめは閉じている。ボタンで開閉）で示す。別のヘルプのページは設けない。指標の説明は、指標の定義（`shared/constants/metrics.ts` の `help`）、入力項目・カテゴリの説明は、`shared/constants/item-help.ts` に持ち、各画面は、そこから表示する（用語辞書）。説明は、設計の定義（viewpoint/・data-dictionary.md・用語集・ADR）から書き、定義のないものには付けない |

### 1.3 APIの共通仕様

| 項目 | 内容 |
|------|------|
| 形式 | `/api/v1/...`。リクエスト・レスポンスは JSON（UTF-8） |
| 認証 | `Authorization: Bearer <token>`（方式は設計で確定。FR-9.3） |
| 成功 | 200（取得・更新）、201（作成）、204（削除・既読化） |
| エラー | 4xx（入力不正 400、未認証 401、権限なし 403、存在なし 404、競合 409、版の確認が必要な更新に `If-Match` がない 428）、5xx。形式は `{ "error": { "code": "...", "message": "...", "fields": [{ "name": "...", "message": "..." }] } }`。`message` に内部情報（スタックトレース、パス、設定値）を含めない（security.md） |
| ページ分割 | `?limit=&cursor=`。応答に `nextCursor` を含める |
| 並べ替え・絞り込み | クエリ（例: `?from=&to=&category=&sort=`） |
| 冪等性 | 作成系は、重複を防ぐキーがある場合に、条件付き書き込みで 409 を返す |
| 版つき更新 | 判断基準の更新・既定値へ戻す操作は、`GET` の応答の `ETag`（内容のハッシュ）を、`If-Match` に付ける（同時編集の検出。SC-13-1）。`If-Match` がなければ 428、現在の版と一致しなければ 409（更新しない）。ワイルドカード（`*`）は受け付けない |
| ログ | 構造化ログ。リクエスト本文の全体・秘密情報を出力しない |

## 3. 画面仕様

### 3.1 SC-02 ダッシュボード（FR-6.1〜6.3、6.6、6.7 / UC-01）

| 項目 | 内容 |
|------|------|
| 目的 | ハウスの状態を、観点ごとに、一目で把握する（ダッシュボードは、ハウス単位。#355） |

### 3.15 SC-15 通知の設定（FR-7.2 / UC-23）

| 項目 | 内容 |
|------|------|
| 操作 | Web Push 通知の有効化（ブラウザの許可を求め、購読を登録）、解除、**テスト通知を送る**（有効なときだけ示す。宛先は、自分のこの端末〔この購読〕だけ。同じ端末へは、1 分に 1 回まで。1 分以内に押すと、「テスト通知は、1 分に 1 回までです。あと N 秒たってから、もう一度お試しください」と示す。通知の記録〔通知の一覧〕には、残さない。#159） |

| 関連API | `GET /api/v1/push-subscription`（状態の確認。端末の宛先を指定すると、その端末の購読の有無と、無効にされたか）、`PUT /api/v1/push-subscription`（`{ endpoint, keys? }`）、`DELETE /api/v1/push-subscription`、`POST /api/v1/push-subscription/test`（この端末へのテスト通知。`{ endpoint }`） |

| 入力 | `criteria[]`（`indicator`、`kind`、`thresholds`、`label`） |
| 応答 | 200。保存した判断基準（`version`、`isDefault=false`） |
| エラー | 428（`If-Match` がない。`PRECONDITION_REQUIRED`）、409（`If-Match` が現在の版と一致しない。他の管理者が先に変更した。`CONFLICT`。保存しない）、400（閾値の大小関係の逆転、数値でない、条件名が空欄または200文字超、20件超。`fields` に理由）、ステータス項目の指標は 400。確認の順序: 認証・権限・観点の存在（403・404）→ 428 → 409 → 入力の検証（400） |

**`POST /viewpoints/{viewpointId}/criteria/reset`**: 更新と同じ扱い。`If-Match` 必須（なければ 428、一致しなければ 409。既定値へ戻さない）。応答は 200（既定値の判断基準）。

**`GET /notifications`**

| 項目 | 内容 |
|------|------|
| クエリ | `kind`、`readState`（`UNREAD`／`READ`）、`limit`、`cursor` |
| 応答 | `items[]`（`notificationId`、`kind`、`viewpointId`、`equipmentId`、`status`、`message`、`createdAt`、`readState`、`memoCount`〔メモの件数。#239〕、`progress`〔状態変化の通知だけ。経過・回復日時。#238〕）、`nextCursor` |

**`PUT`・`DELETE /ingestion/equipment/{equipmentId}/connection`、`PUT /ingestion/equipment/{equipmentId}/credentials`、`POST /ingestion/equipment/{equipmentId}/test`**（Issue #367。[ADR-0026](../adr/0026-per-equipment-file-server-connection.md)）

| 項目 | 内容 |
|------|------|
| 入力 | `PUT …/connection` は `{ connection }`（プロトコル・ホスト・ポート・認証方式・API キーのヘッダー名。認証情報の値は含めない）。`PUT …/credentials`（Issue #207。D-47。[ADR-0022](../adr/0022-file-server-http-connection-provisional.md)）は、`authMethod`（保存済みの、設備ごとの接続の認証方式と同じ。`BASIC`／`BEARER`／`API_KEY`）と、認証方式ごとの値: `BASIC` は `username`（200 文字以内。`:` は不可）・`password`（1000 文字以内）、`BEARER` は `token`、`API_KEY` は `apiKey`（どちらも、表示できる ASCII で 2000 文字以内。空白・改行・日本語は不可）。`DELETE …/connection`・`POST …/test` は、本文なし |
| 応答 | `PUT`・`DELETE …/connection`: 200。接続の状態 `{ equipmentId, connection?, credentials }`（`connection` は、未設定なら省略）。`PUT …/credentials`: 200。状態 `{ state, updatedAt? }`（値は含めない。`state` は `CONFIGURED`）。設定の取得（`GET /ingestion/settings`）の、取り込み元ごとの設備の項目には、`credentials` として、状態（`NOT_REQUIRED`〔認証が不要〕・`NOT_CONFIGURED`〔未設定〕・`CONFIGURED`・`UNAVAILABLE`〔保管先から読み出せない〕）と更新日時を返す。`POST …/test`: 200。`ok`・`message`（理由だけ。接続先・パス・認証情報を含めない） |
| エラー | 400（入力不正、ハウスへの指定、内部のアドレス、接続が未設定・認証が不要・認証方式が保存済みの設定と違うときの認証情報の登録。**値を含めない**）、403（権限なし）、404（設備がない・削除済み）、503（認証情報を保管先に保存できない） |
| 記録 | 値は、画面・API の応答・ログ・エラー・変更履歴のどこにも残さない。変更履歴は、対象の種類 `ingestion-settings`・対象 ID `equipment-connections/<設備ID>`（接続先。認証情報の値は持たない）と、`credentials/equipment/<設備ID>`（更新した事実と認証方式だけ） |

**`POST /ingestion/{sourceId}/run`**

| 項目 | 内容 |
|------|------|
| 応答（run） | 202（同期して実行し、結果の概要を返す）。実行中の場合は 409（二重実行の防止）。結果は、取り込みログでも確認できる |

その他のAPIは、4.1 の概要と、data-dictionary.md の項目定義に従う。**入出力の詳細は、共有のスキーマ（`src/shared/schemas/`。Zod）が正**で、OpenAPI 等の API 定義ファイルは使わない（決定。[ADR-0021](../adr/0021-nonfunctional-ops-doc-rules.md)）。

## 5. 非同期・定期処理の仕様

| ID | 処理 | 契機 | 内容 | 失敗時 | 要件 |
|----|------|------|------|--------|------|
| JB-01 | 取り込み | スケジューラ（取得間隔）、即時取得 | 取り込み元ごとに独立して実行。新しいファイルの一覧の取得 → 取り込み済みの判定（識別子・ハッシュ）→ 読み込み → 解釈（FormatProfile）→ 検証 → 観測値の保存 → 取り込みログ。保存後に、評価を更新する | 再試行（回数・間隔の上限）。上限を超えたら、取り込み失敗の通知（JB-04）。他の取り込み元・機能は継続 | FR-1.1〜1.3、1.6〜1.10、FR-5.4 |
| JB-02 | 評価 | 取り込み・手動入力の後、定期（データ途絶の確認） | 設備・観点・視点ごとに、観測値を読み、メトリクスを算出し、判断基準でステータスを判定し、診断メッセージ・推奨アクションを付けて、評価結果を保存する。状態の変化を検知して、通知の作成（JB-04）を依頼する | 失敗は記録し、次の契機で再評価する。評価結果が古い場合は、画面で最終の評価日時を示す | FR-5、FR-7.1 |
| JB-03 | 連携 | スケジューラ、または連携キューへの追加 | 連携キューの「待機」「失敗」の項目を、農業情報基盤へ送る。結果（成功／失敗／保留／期限切れ）を記録する。破棄の期限を過ぎた項目は、送らずに破棄し、連携のログと通知に残す | 間隔を広げて再試行。基盤の停止中は「保留」。他の機能は影響を受けない | FR-8 |
| JB-04 | 通知の作成・配信 | 評価の状態変化、取り込みの失敗 | 「注意」「異常」へ変化したとき、または取り込みが失敗したときに、通知を作成（未読）する。状態変化の通知は、出来事で判定する（正常が 15 分以上続いたあとの悪化は新しい出来事。同じ出来事の中では、重くなるときだけ。改善・「不明」は通知しない。決定。ADR-0019）。取り込みの失敗・停止、連携の期限切れは、同じ取り込み元・状況は 60 分に 1 件。画面内の通知は、必ず保存し、Web Push を購読している利用者へ配信する | 配信の失敗は記録し、失敗した購読にだけ、1 分から倍々の間隔で、1 時間まで再送する（決定。[ADR-0019](../adr/0019-notification-rules.md)。実装済み。#237）。無効な購読は破棄 | FR-7 |

- 各処理は、同じイベントが重複して届いても結果が変わらない（冪等）ように実装する（coding-standards.md）
- 実行は、サーバーレスの関数（スケジューラ・ストリームを契機）。実行時間に収まる単位に分割する（ADR-0002）

## 6. 入力検証・業務ルールの一覧

| 対象 | ルール | 要件 |

| 設備 | 設備IDは一意。ロボット・センサーは、ハウスに属する | FR-2.4 |
