# UI デザイン方針

目的: 画面（Web UI）のデザインの方向性・デザイントークン・アイコンの使い方・共通のレイアウト・守ることを定め、デザインの刷新（Issue #170）と、以降の画面の追加・変更の拠り所にする。

画面ごとの振る舞いは [functional-specification.md](./functional-specification.md)、非機能要件（使いやすさ）は [non-functional-requirements.md](../requirements/non-functional-requirements.md) の NFR-7 を参照する。

## 1. 位置づけと範囲

- 決める事項は、Issue #169 で決めた。反映は #170（狭い幅（スマートフォン）の対応は、サブ Issue #151）で行う。
- 変えるのは、**見た目**と、**共通のレイアウトの配置**（メニュー・ヘッダーの組み替え、サマリーの見せ方、本文の見出しまわり）。
- **変えない**のは、メニューの項目・名前・数・遷移先・階層と、画面の構成・導線・情報設計。これらの見直しは、別の Issue（#155 画面名・メニュー・導線、#160 ダッシュボードの情報設計）で行う。
- 色・アイコン・レイアウトの値は、現時点の決定。実装で見直す場合は、本書を更新する。

## 2. 利用者と利用場面

| 項目 | 内容 |
|------|------|
| 利用者 | 施設園芸の農作業者（ロボット・ハウスの状態の確認と、復旧・調整を行う人）。ITの知識に依存しない（NFR-7.1） |
| 目的 | 異常に早く気づき、何をすべきかを判断する（HITL。goals.md）。ロボット・ハウスを操作する機能はない |
| 端末 | 実証実験は PC。実際の農場は、スマートフォン・タブレットも想定する（NFR-7.3。#142 の D-33） |
| 回線 | スマートハウスのローカル 5G が基本。スマートフォンは、キャリア回線もありうる |
| 場所・明るさ | ハウスの中・屋外。明るい場所でも読めること |
| 更新 | 画面は約 10 秒間隔で、最新の評価結果を読み直す（FR-6.7）。状態の変化に気づけること |

このシステムの画面は、**運用ダッシュボード**（頻繁に更新されるデータを、リアルタイムに監視する画面）に当たる。「一目で状態がわかる」ことを、最優先にする。

## 3. ダッシュボードの設計原則と、本システムへの適用

参考: [ダッシュボードデザインの原則（UXPin）](https://www.uxpin.com/studio/jp/blog-jp/dashboard-design-principles-ja/)。原則を、本システムに当てはめて、今回適用するものと、構成の見直し（#155・#160）に回すものに分ける。

| 原則 | 今回の適用（見た目・共通のレイアウト） | 構成の見直しに回すもの |
|------|----------------------------------------|------------------------|
| 1. 明確な視覚的階層 | 最も重要な「観点の状態」のサマリーを、本文の最上部に、大きな数のタイルで示す。**強い色は、異常に限る**（異常は塗りつぶし）。大きく太い文字は、見出しと主要メトリクスの値だけに使う。関連する情報は、カード・余白でまとめる | 観点の並び順の変更（悪い順など）、情報の優先順位の再設計（#160） |
| 2. 一貫性 | 色・文字・余白・角丸・アイコンを、トークンと部品で統一する。ステータスバッジ・カード・表・フォームを、全画面で同じ部品にする | - |
| 3. 認知的負荷の最小化 | 余白で区切り、色の種類を絞る（状態の色は、状態だけに使う）。詳細は、カードの「詳細」リンクと観点の詳細（SC-03）に任せる。ナビゲーションは、サイドメニューに集約する | 表示項目の削減、段階的な開示の追加（#160） |
| 4. データの分かりやすさ・読みやすさ | 文字と背景のコントラストを確保する（4.5:1 以上）。数値は等幅の数字（`tabular-nums`）にする。3D・不要な装飾を使わない | グラフの種類・表示方法の見直し（FR-6.10。TODO: 粒度・期間・表示方法） |
| 5. アクセシビリティ | 状態は、色・形・塗り方・文字で示す（色だけに頼らない）。色覚の違いでも区別できる配色にする（6 章）。キーボードだけで操作でき、ARIA の名前を持つ | - |

- ドリルダウン・フィルター・カスタムビューなどの、探索の機能の追加は、機能の変更のため、本書の範囲外（#160 など）。
- 「推奨アクション」の領域を、カードの中に、目立つ位置で残す（現状どおり。AI による推奨が増えても、置き場所を変えなくてよい）。

## 4. 方向性

| 項目 | 内容 |
|------|------|
| ライト | **クリーンな計器盤**。白と淡いグレーの面に、深い緑の枠組み（メニュー・主ボタン）。大きな数値。ブラウザの設定がライトのとき |
| ダーク | **運用モニター**。中立の暗いグレーの面に、明るい状態色。数値は等幅の数字。ブラウザの設定がダークのとき |
| 切り替え | ブラウザ（OS）の設定（`prefers-color-scheme`）に従う。**画面に手動の切り替えは設けない** |
| 緑 | 農業らしさは、**枠組み（メニュー・主ボタン・ロゴ）の緑**で出す。状態の「正常」の緑とは、役割も色も分ける |
| 色の意味 | 状態の色（正常・注意・異常・不明）は、**状態の表示だけ**に使う。観点の種類・装飾・リンクには、状態の色を使わない |
| イラスト | 空の状態・ログイン・404 だけ（イチゴとハウスのモチーフ）。業務の画面（ダッシュボードなど）には、使わない |
| フォント | システムフォントのみ（現状のフォントの指定を維持する）。外部フォント・外部の CDN は使わない |

| 項目 | 値 |

| 数字 | `font-variant-numeric: tabular-nums` |

| 影 | 使わない（面と枠で区切る） |
| アイコンの大きさ | 14・18・22・26・30px（線幅 1.8、角丸の線） |
| 操作の大きさ | 狭い幅（スマートフォン）で、操作できる部品の高さを 44px 以上にする |
| ブレークポイント | 900px 以下: メニューを引き出しにし、表をカードにする（現状どおり）。480px 以下: 余白・グラフを、さらに詰める |

## 6. 状態の表し方と、色覚への配慮（カラーユニバーサルデザイン）

状態（正常・注意・異常・不明）は、**色・形・塗り方・文字**の 4 つで示す。どれか 1 つが見えなくても、区別できる。

| 状態 | 色（主色） | アイコンの形 | 塗り方 | 文字 |
|------|------------|--------------|--------|------|
| 正常 | 青みのある緑 | 丸 + チェック | 実線の枠（淡い面） | 正常 |
| 注意 | 黄〜橙 | 三角 + 感嘆符 | 実線の枠（淡い面） | 注意 |
| 異常 | 赤 | 八角形 + 感嘆符 | **塗りつぶし** | 異常 |
| 不明 | 灰 | 破線の丸 + ? | **破線の枠・塗りなし** | 不明 |

- 配色は、色覚シミュレーション（Machado 2009。P 型・D 型・T 型）で、4 状態どうしの色の差を、**CIEDE2000 の ΔE 15 以上**にそろえた。旧案（暗い緑の背景）は、最小が 3 だった。

  | 配色 | 状態どうしの最小の差（通常・P 型・D 型・T 型のうち、最小） |
  |------|---------------------------------------------------------|
  | ライト | 17.9 |
  | ダーク | 18.3 |

- ダークの背景を、暗い緑にしない（正常の緑・不明の灰と、背景が似るため）。
- 正常は、赤と緑の組み合わせにならないよう、青みのある緑にする。
- 文字のコントラストは 4.5:1 以上、面・線・アイコンと背景は 3:1 以上（WCAG 1.4.3・1.4.11）。上の値は、この条件を満たすことを計算で確認した。
- 実装後に、色覚シミュレーションで、画面を確認する（#170 の完了条件）。

## 7. アイコンとイラスト

アイコンは、**自前の SVG**（インラインのコンポーネント）で作る。外部のアイコンライブラリ・アイコンのフォントは使わない（依存を増やさず、CSP でも壊れないようにするため）。

### 7.1 観点のアイコン

色は、中立の 1 色（緑がかったグレー。状態の色と混ぜない）。

| 観点 | アイコン |
|------|----------|
| 収穫精度 | 的 |
| 収穫速度 | ストップウォッチ |
| 操作性 | 調整パネル（スライダー） |
| メンテナンス性 | スパナ |
| コスト効率 | コイン（円） |
| 安全性 | 盾 + チェック |
| 耐久性 | バッテリー |
| 環境適応性 | 温度計 + 葉 |
| データ活用度合い | 棒グラフ |
| 満足度 | 笑顔 |

### 7.2 メニュー・設備・操作のアイコン

| 種類 | アイコン |
|------|----------|
| メニュー | ダッシュボード（4 つの四角）、データ入力（鉛筆）、通知（ベル。件数の印）、取り込み済みデータ（リスト）、設定（歯車） |
| 設定の中 | 設備（ハウス）、取り込み（プラグ）、ステータスコード（タグ）、ユーザー（人々）、通知の設定（ベル） |
| 設備の種類 | ハウス、ロボット、センサー（電波） |
| 操作・情報 | 更新、保存（チェック）、修正（鉛筆）、削除（ごみ箱。確認つき）、検索、詳細へ（矢印）、期間（カレンダー）、最終取得（時計）、推奨アクション（電球）、判断基準（本） |

### 7.3 決まり

- アイコンは、**文字と一緒に使う**。意味を、アイコンだけで伝えない（NFR-7.2）。アイコンだけのボタンには、読み上げ用の名前（`aria-label`）とツールチップをつける。
- 装飾のアイコンは、読み上げの対象から外す（`aria-hidden`）。文字が、同じ意味を持つ。
- アイコンの線幅・角丸・大きさは、統一する（5.3）。
- 観点のアイコンは、状態の色にしない（状態は、バッジ・タイルの色と形で示す）。

## 8. 共通のレイアウト

| 領域 | 内容 |
|------|------|
| サイドメニュー（左） | アプリ名、メニュー（アイコン + 文字）。現在の項目を強調し、通知には未読の件数の印をつける。「設定」は開閉できるまとまりにし、中に 5 項目（設備・取り込み・ステータスコード・ユーザー・通知の設定）を入れる（functional-specification.md 2.3） |
| 上部のバー | メニューの開閉、設備の選択、最終のデータ取得（古い・未取得の表示を含む）、通知（件数）、ユーザー（ログアウト） |
| 本文の見出し | 画面のタイトル、パンくず、対象の設備・評価の日時などの補足 |
| 本文 | サマリー（大きな数のタイル: アイコン + 数 + 状態名）→ 観点のカード。カードは、観点のアイコン・名前・状態のバッジ・主要メトリクスの値・診断・推奨アクション |

- 900px 以下では、サイドメニューを、☰ で開閉する引き出しにする。上部は 1 行にまとめる（現状は、ヘッダーとメニューが 4 行になる。#151）。
- メニューを開いたときは、フォーカスを中に移し、閉じたら ☰ に戻す。Esc で閉じる。キーボードだけで開閉できる。
- メニューのナビゲーションの名前（「メニュー」）と、リンクの名前は、変えない（既存の E2E が参照している）。
- 通知の件数・最終のデータ取得・設備の選択は、上部のバーに残す（今と同じ情報）。

## 9. 守ること

- 変えるのは、見た目と、共通のレイアウトの配置。メニューの項目・名前・数・遷移先・階層、画面の構成・導線・情報設計は変えない（#155・#160）。
- CSS を中心にする。DOM・aria の変更は、共通のレイアウト（サイドメニュー化）と、狭い幅（スマートフォン）の対応（#151。表のカード化など）に必要な範囲に限る。
- 依存パッケージを追加しない（CSS・トークン・自前の SVG のみ）。外部のフォント・CDN を使わない（CSP の設定（#127）で壊れないようにする）。
- 既存テストの期待値を、通すためだけに書き換えない。変更が要る場合は、理由を示して確認する。
- 状態は、色だけに頼らず、形・塗り方・文字で示す。色の意味を混ぜない（状態の色は、状態だけに使う）。
- ライト・ダークの手動の切り替えは設けない（ブラウザの設定に従う）。

## 10. 確認の方法

- 画面を、ライト・ダークの両方で、PC・タブレット・スマートフォンの幅（1280px・768px・375px）で確認する（スクリーンショット）。
- 色覚シミュレーション（P 型・D 型・T 型）で、4 状態が区別できることを確認する。
- 文字のコントラストを確認する（4.5:1 以上。面・線・アイコンは 3:1 以上）。
- 既存のテスト（単体・E2E）が、すべて成功することを確認する。
- キーボードだけで、メニューの開閉・主要な操作ができることを確認する。
