# UI デザイン方針

目的: 画面（Web UI）のデザインの方向性・デザイントークン・アイコンの使い方・共通のレイアウト・守ることを定め、デザインの刷新（Issue #170）と、以降の画面の追加・変更の拠り所にする。

画面ごとの振る舞いは [functional-specification.md](./functional-specification.md)、非機能要件（使いやすさ）は [non-functional-requirements.md](../requirements/non-functional-requirements.md) の NFR-7 を参照する。

## 1. 位置づけと範囲

- 決める事項は、Issue #169 で決めた。反映は #170（狭い幅（スマートフォン）の対応は、サブ Issue #151）で行う。
- 変えるのは、**見た目**と、**共通のレイアウトの配置**（メニュー・ヘッダーの組み替え、サマリーの見せ方、本文の見出しまわり）。
- **変えない**のは、メニューの項目・名前・数・遷移先・階層と、画面の構成・導線・情報設計。これらの見直しは、別の Issue（#155 画面名・メニュー・導線、#160 ダッシュボードの情報設計）で行う。
- 色・アイコン・レイアウトの値は、現時点の決定。実装で見直す場合は、本書を更新する。

## 2. 利用者と利用場面

| 項目 | 内容 |
|------|------|
| 利用者 | 施設園芸の農作業者（ロボット・ハウスの状態の確認と、復旧・調整を行う人）。ITの知識に依存しない（NFR-7.1） |
| 目的 | 異常に早く気づき、何をすべきかを判断する（HITL。goals.md）。ロボット・ハウスを操作する機能はない |
| 端末 | 実証実験は PC。実際の農場は、スマートフォン・タブレットも想定する（NFR-7.3。#142 の D-33） |
| 回線 | スマートハウスのローカル 5G が基本。スマートフォンは、キャリア回線もありうる |
| 場所・明るさ | ハウスの中・屋外。明るい場所でも読めること |
| 更新 | 画面は約 10 秒間隔で、最新の評価結果を読み直す（FR-6.7）。状態の変化に気づけること |

このシステムの画面は、**運用ダッシュボード**（頻繁に更新されるデータを、リアルタイムに監視する画面）に当たる。「一目で状態がわかる」ことを、最優先にする。

## 3. ダッシュボードの設計原則と、本システムへの適用

参考: [ダッシュボードデザインの原則（UXPin）](https://www.uxpin.com/studio/jp/blog-jp/dashboard-design-principles-ja/)。原則を、本システムに当てはめて、今回適用するものと、構成の見直し（#155・#160）に回すものに分ける。

| 原則 | 今回の適用（見た目・共通のレイアウト） | 構成の見直しに回すもの |
|------|----------------------------------------|------------------------|
| 1. 明確な視覚的階層 | 最も重要な「観点の状態」のサマリーを、本文の最上部に、大きな数のタイルで示す。**強い色は、異常に限る**（異常は塗りつぶし）。大きく太い文字は、見出しと主要メトリクスの値だけに使う。関連する情報は、カード・余白でまとめる | 観点の並び順の変更（悪い順など）、情報の優先順位の再設計（#160） |
| 2. 一貫性 | 色・文字・余白・角丸・アイコンを、トークンと部品で統一する。ステータスバッジ・カード・表・フォームを、全画面で同じ部品にする | - |
| 3. 認知的負荷の最小化 | 余白で区切り、色の種類を絞る（状態の色は、状態だけに使う）。詳細は、カードの題名のリンク（詳細へのリンクは、題名の 1 つだけ）と観点の詳細（SC-03）に任せる。ナビゲーションは、サイドメニューに集約する | 表示項目の削減、段階的な開示の追加（#160） |
| 4. データの分かりやすさ・読みやすさ | 文字と背景のコントラストを確保する（4.5:1 以上）。数値は等幅の数字（`tabular-nums`）にする。3D・不要な装飾を使わない | グラフの種類・表示方法の見直し（FR-6.10。TODO: 粒度・期間・表示方法） |
| 5. アクセシビリティ | 状態は、色・形・塗り方・文字で示す（色だけに頼らない）。色覚の違いでも区別できる配色にする（6 章）。キーボードだけで操作でき、ARIA の名前を持つ | - |

- ドリルダウン・フィルター・カスタムビューなどの、探索の機能の追加は、機能の変更のため、本書の範囲外（#160 など）。
- 「推奨アクション」の領域を、カードの中に、目立つ位置で残す（現状どおり。AI による推奨が増えても、置き場所を変えなくてよい）。

## 4. 方向性

| 項目 | 内容 |
|------|------|
| ライト | **クリーンな計器盤**。白と淡いグレーの面に、深い緑の枠組み（メニュー・主ボタン）。大きな数値。ブラウザの設定がライト（または、メニューでライトを選んだ）とき |
| ダーク | **運用モニター**。中立の暗いグレーの面に、明るい状態色。数値は等幅の数字。ブラウザの設定がダーク（または、メニューでダークを選んだ）とき |
| 切り替え | 既定（システム）は、ブラウザ（OS）の設定（`prefers-color-scheme`）に従う。ヘッダーのユーザーメニューの中の「テーマ」で、ライト・ダークを手動でも選べる（#352・#353）。設定は、この端末のブラウザ（`localStorage`）に保存する（端末ごと。サーバーには送らない） |
| 緑 | 農業らしさは、**枠組み（メニュー・主ボタン・ロゴ）の緑**で出す。状態の「正常」の緑とは、役割も色も分ける |
| 色の意味 | 状態の色（正常・注意・異常・不明）は、**状態の表示だけ**に使う。観点の種類・装飾・リンクには、状態の色を使わない |
| イラスト | 空の状態・ログイン・404 だけ（イチゴとハウスのモチーフ）。業務の画面（ダッシュボードなど）には、使わない |
| フォント | システムフォントのみ（現状のフォントの指定を維持する）。外部フォント・外部の CDN は使わない |

## 6. 状態の表し方と、色覚への配慮（カラーユニバーサルデザイン）

状態（正常・注意・異常・不明）は、**色・形・塗り方・文字**の 4 つで示す。どれか 1 つが見えなくても、区別できる。

| 状態 | 色（主色） | アイコンの形 | 塗り方 | 文字 |
|------|------------|--------------|--------|------|
| 正常 | 青みのある緑 | 丸 + チェック | 実線の枠（淡い面） | 正常 |
| 注意 | 黄〜橙 | 三角 + 感嘆符 | 実線の枠（淡い面） | 注意 |
| 異常 | 赤 | 八角形 + 感嘆符 | **塗りつぶし** | 異常 |
| 不明 | 灰 | 破線の丸 + ? | **破線の枠・塗りなし** | 不明 |

- 配色は、色覚シミュレーション（Machado 2009。P 型・D 型・T 型）で、4 状態どうしの色の差を、**CIEDE2000 の ΔE 15 以上**にそろえた。旧案（暗い緑の背景）は、最小が 3 だった。

  | 配色 | 状態どうしの最小の差（通常・P 型・D 型・T 型のうち、最小） |
  |------|---------------------------------------------------------|
  | ライト | 17.9 |
  | ダーク | 18.3 |

- ダークの背景を、暗い緑にしない（正常の緑・不明の灰と、背景が似るため）。
- 正常は、赤と緑の組み合わせにならないよう、青みのある緑にする。
- 文字のコントラストは 4.5:1 以上、面・線・アイコンと背景は 3:1 以上（WCAG 1.4.3・1.4.11）。上の値は、この条件を満たすことを計算で確認した。
- 実装後に、色覚シミュレーションで、画面を確認する（#170 の完了条件）。

## 7. アイコンとイラスト

アイコンは、**自前の SVG**（インラインのコンポーネント）で作る。外部のアイコンライブラリ・アイコンのフォントは使わない（依存を増やさず、CSP でも壊れないようにするため）。

### 7.1 観点のアイコン

色は、中立の 1 色（緑がかったグレー。状態の色と混ぜない）。

| 観点 | アイコン |
|------|----------|
| 収穫精度 | 的 |
| 収穫速度 | ストップウォッチ |
| 操作性 | 調整パネル（スライダー） |
| メンテナンス性 | スパナ |
| コスト効率 | コイン（円） |
| 安全性 | 盾 + チェック |
| 耐久性 | バッテリー |
| 環境適応性 | 温度計 + 葉 |
| データ活用度合い | 棒グラフ |
| 満足度 | 笑顔 |

### 7.2 メニュー・設備・操作のアイコン

| 種類 | アイコン |
|------|----------|
| メニュー | ダッシュボード（4 つの四角）、データ入力（鉛筆）、計測データ（リスト）、設定（歯車。太陽に似た絵柄から変えた。テーマの「ライト」の太陽と、区別するため）。通知は、メニューでなく、上部のバーのベルのアイコン（件数のバッジ）から開く（#351） |
| ユーザーメニュー | ユーザー（人）のアイコンのボタン。中の「テーマ」の項目に、システム（モニター）、ライト（太陽）、ダーク（月）。選択中の項目には、チェックの印（#352・#353） |
| 設定の中 | 設備（ハウス）、取り込み（プラグ）、ステータスコード（タグ）、ユーザー（人々） |
| 設備の種類 | ハウス、ロボット、センサー（電波） |
| 操作・情報 | 更新、保存（チェック）、修正（鉛筆）、削除（ごみ箱。確認つき）、検索、詳細へ（矢印）、期間（カレンダー）、最終取得（時計）、推奨アクション（電球）、判断基準（本）、パスワードの表示切替（目。表示中は斜線つきの目。アイコンだけのボタンで、名前は `aria-label`。8 章） |

### 7.3 決まり

- アイコンは、**文字と一緒に使う**。意味を、アイコンだけで伝えない（NFR-7.2）。アイコンだけのボタンには、読み上げ用の名前（`aria-label`）とツールチップをつける。
- 装飾のアイコンは、読み上げの対象から外す（`aria-hidden`）。文字が、同じ意味を持つ。
- アイコンの線幅・角丸・大きさは、統一する（5.3）。
- 観点のアイコンは、状態の色にしない（状態は、バッジ・タイルの色と形で示す）。

### 7.4 イラスト（イチゴとハウス）

- 自前の SVG（`components/illustration.tsx` の `HouseAndStrawberry`）。線の色は、文字の色に合わせ、ライト・ダークで切り替わる。装飾のため、読み上げの対象から外す。
- 使う場面は、**ログイン**（ブランドのブロック）・**空の状態**・**404** だけ。
- 空の状態は、共通の部品 `EmptyState`（`components/state-views.tsx`）で示す。イラストの下に、何が起きているか（文）と、次の操作（リンク）を置く。対象は、データの一覧（入力済みデータ・変更履歴・計測データ・通知・設備・ステータスコード）。画面の一部の小さな欄（元データ・取り込みのログなど）には、使わない。
- 404 は、イラスト・見出し・原因の文（URL が違っているか、ページが移動した可能性）・ダッシュボードへ戻るリンク。

### 7.5 アプリのアイコン（#326）

- ブラウザのタブ（`icon.svg`・`favicon.ico`）・ホーム画面（`apple-touch-icon.png`・マニフェストの `icons` の `icon-192.png`・`icon-512.png`）・Web Push の通知（`icon-192.png`・バッジ `badge-72.png`）で、同じ絵柄を使う。ファイルは、`src/frontend/public/` に置く（`public/` のファイルは、サイトのルートで配信される。CSP の `img-src`・`manifest-src` は `'self'` のまま通る）。
- **絵柄は仮**（主色 `#1d5c40` の角丸の四角と、白いハウスのシルエット）。ロゴ・ブランドの画像が決まったら、同じファイル名・大きさで差し替える（大きさは、単体テストが確認する）。仮の絵柄は、`scripts/generate-app-icons.ts` で再生成できる。
- バッジ（`badge-72.png`）は、透明の地に白だけで描く（Android の状態バーが、色を白に塗り替えるため）。

## 8. 共通のレイアウト

| 領域 | 内容 |
|------|------|
| サイドメニュー（左） | メニュー（アイコン + 文字。アプリ名は、ヘッダーの左のタイトルへ移した）。現在の項目を強調する（通知は、上部のバーから開くため、メニューにない）。「設定」は開閉できるまとまりにし、中に 4 項目（設備・取り込み・ステータスコード・ユーザー）を入れる（「通知の設定」は、ユーザーメニューへ移した）（functional-specification.md 2.3） |

- **観点の詳細のドロワー（#357）**: ダッシュボードのカード・観点別の状態の表から開く観点の詳細（満足度の詳細を含む）は、右からのドロワー（幅 `min(880px, 100vw)`。900px 以下は全画面。高さは画面いっぱい〔`100dvh`〕）。ダッシュボードの上に重ね（背面は、描画したまま）、スクリーンを敷く。✕・Esc・背面・戻るで閉じる。開いている間は、本文のスクロールを固定し、フォーカスを中に閉じ込め、閉じたら、開いたカードに戻す。URL は `/?viewpoint=…`。見出しは h2、パンくずは出さず、「ページで開く」を置く。重なりは、サイドメニューの引き出し・ポップアップより前面（z-index 40・41）。

- **ログイン画面の文言（#157。SC-01-1・01-2・01-5）**: ブランド（イラスト・アプリ名）の下に、システムの目的を、1 行で示す。セッションが切れて戻されたときの理由は、フォームの上に、お知らせ（`role="status"`。エラーの色は使わない）で示す。パスワードを忘れたときの案内は、ログインのボタンの下に、補足の文字で示す（連絡先は、具体的な名前を書かず、「管理者」とする）。
- **パスワード欄（#157。SC-01-4）**: パスワードの入力は、共通の部品 `PasswordInput`（`components/password-input.tsx`）で示す。ログイン・パスワードの変更・ユーザーの登録／再設定の 3 画面に使う。**表示切替**は、入力欄の右の、目のアイコンのボタン（`type="button"`。既定は非表示。`aria-pressed` で状態を伝え、名前〔`aria-label`・ツールチップ〕は、状態によらず「入力した文字を表示」で固定する。名前に「パスワード」を含めない〔欄のラベルでの検索が、欄とボタンの 2 件にならないように〕）。表示にしても、スペルチェック・自動の大文字化は切る。**Caps Lock の注意**は、欄の下に、アイコンと文字（「Caps Lock がオンです。大文字で入力されます」）で示す（状態の色は使わない）。キーの入力（押す・離す）と、欄のクリックで、`getModifierState('CapsLock')` を確かめ、欄から離れると消す（ブラウザは、フォーカスの時点では、状態を教えない）。読み上げ用の領域（`aria-live="polite"`）は、注意が出る前から置く。狭い幅（900px 以下）は、欄とボタンを、44px 以上にする。**ログイン画面は、開いたとき、ユーザーIDの欄にフォーカスを置く**（`useEffect` で 1 回。`autoFocus` 属性は、jsx-a11y の `no-autofocus` で禁じている）。
- **フォームを入れるダイアログ（#364〜#366）**: 設定の登録・修正・割り当ては、画面の中ではなく、ダイアログ（`role="dialog"` `aria-modal`。見出し h2 が名前）で行う。表の上に、登録のボタンを置く。開いたら最初の入力欄にフォーカスを移し、Tab はダイアログの中で循環し、Esc・✕・キャンセルで閉じる。閉じたら、開いたボタンへフォーカスを戻す。開いている間は、背面のスクロールを止める。**背面を押しても閉じない**（入力の途中を失わないため）。幅は 640px（表を入れるものは 880px）。確認のダイアログ（削除など。キャンセルが先にフォーカスを受ける）とは、別の部品。
- **結果の通知（#150）**: 保存・修正・削除・接続の確認などの結果は、共通の部品 `ResultNotice`（`components/result-notice.tsx`）で示す。`role="status"`（`aria-live` は、これが暗黙に持つ）で読み上げ、表示されたとき（現れた・メッセージが変わったとき）に、`scrollIntoView({ block: 'nearest' })` で、画面内になければスクロールする（フック `useRevealOnChange`。`prefers-reduced-motion: reduce` のときは、アニメーションしない。`scrollIntoView` のない環境では、何もしない）。**フォーカスは動かさない**（操作できる要素を持たないため。ダイアログ・編集欄のように、操作を受ける要素とは、別の扱い）。見た目は、成功が `form-success`（先頭に「正常」の形のアイコン）、失敗が `form-error`（「異常」の形のアイコン）。データ入力の保存結果のパネル（見出し・関連観点のステータス・リンクを含む）は、`ResultNotice` ではなく、同じフックと `role="status"` で、同じ規則にする。画面全体のエラー（`FormError`・`ErrorView`。`role="alert"`）は、この部品を使わない。
- **一覧の共通部品（#152）**: 一覧の絞り込みは、共通の部品 `FilterPanel`（`components/filter-controls.tsx`）に、項目を入れる。枠の上に、**適用中の条件の数**（`filter-count`。「適用中の条件 N 件」。初期値と違う条件〔絞り込み・並べ替え〕の数。0 件のときは出さない）と、**条件のクリア**（初期値に戻す。URL のクエリから外す。`QueryParams.clear`。0 件のときは無効）を置く。**狭い幅（900px 以下）は、項目を折りたたみ**、開閉のボタン（`aria-expanded`・`aria-controls`。名前は「絞り込みを開く／閉じる」）で開く。折りたたんでも、条件の数とクリアは見える。広い幅は、開閉のボタンを出さず、常に開く（CSS の `@media (max-width: 900px)`。`data-open` で状態を示す）。**操作（通知の「既読にする」など）は、絞り込みの枠に入れず**、折りたたみで隠さない。ページ送り（`Pager`）は、ページの大きさとこのページの件数を渡すと、**表示範囲**（「21〜40 件目」。`pager-range`）を行の左に示す。総件数・総ページは示さない（カーソル方式のため）。設備の選択肢は、`equipmentOptionLabel`（ハウスの下にロボット・センサーを字下げし、種別を付ける）で示す。
- **確認のダイアログの対象と影響（#153）**: 削除などの確認（`ConfirmDialog`）は、固定の文言だけにせず、対象を、ラベルと値の並び（定義リスト）で示し、影響があるものは、箇条書きの注記で添える（どちらも任意）。対象は、名前で示す（ID だけにしない）。元に戻せない操作は、その旨を、説明文に明記する。フォームのダイアログ（`Modal`。z-index 30）の中の操作の確認（親のハウスの付け替えなど。#163）は、フォームの中に `ConfirmDialog` を置く（確認のダイアログの z-index は 20 だが、`Modal` の重なりの中に入るため、フォームの前面に出る）。キャンセル・Esc は、確認だけを閉じ、フォームは閉じない（入力を残す）。確定は、削除のような赤い確認の見た目のまま、確認の動詞を、ボタンの名前にする（例: 「親のハウスを変更して保存」）。
- **ヘルプヒントと凡例（#154）**: 指標名・入力欄のラベルの横に、共通の部品 `HelpHint`（`components/help-hint.tsx`）を置く。見た目は「?」の小さな丸（22px）。押す範囲は、狭い幅（900px 以下）で 44px 四方（負の余白で、周りの並びを変えない。操作の大きさ〔5.3〕を満たす）。ボタンの名前は、表示の「?」ではなく、読み上げ用の文字「{対象}の説明」（`aria-label` にはしない。ラベルで入力欄を探す操作に、混ざらないため）。`aria-expanded`・`aria-controls` で開閉を示す。開くと、ボタンの下に説明（`role="note"`。意味・入力例・用語の組）を出す。閉じるのは、もう一度押す・**Esc**（ボタンにフォーカスを残す。ダイアログ・ドロワーの中でも、ヒントだけを閉じ、ダイアログは閉じない。閉じているときの Esc は、外側へ任せる）・**外側を押す**（`pointerdown`。iOS の Safari でも届く）・フォーカスが外へ移る。同時に開くのは 1 つ。画面の幅（余白 8px）からはみ出す分は、`left` でずらす（`transform` では、ページの横スクロールが残るため）。`title` 属性（ホバーだけ）には頼らない。**凡例**は、共通の部品 `Legend`（`components/legend.tsx`）。ボタン（`aria-expanded`・`aria-controls`）で開閉する折りたたみ式で、はじめは閉じている。状態の凡例（ダッシュボード。状態のバッジと意味）・データの状態の凡例（計測データ。状態と、意味・評価での扱い）・カテゴリの凡例（ステータスコード。`StatusCodeLegend`。正常・注意・異常のバッジと、意味・対応の目安〔状態の凡例と同じ定義〕、判定への使われ方の注記。SC-12-6）がある。色は、既存のトークンだけを使う
- **ダッシュボードの鮮度の表示（#158）**: 「データが古い」の警告は、文（先頭 3 件の設備名と「ほか N 件」）を `role="alert"` にし、警告の中に、開閉できる一覧（`<details>`。「古い設備の一覧（N 件）」。閉じた状態から始まる。設備名・最終の受信日時・基準〔分〕の表。狭い幅では、表だけ横にスクロールする）を置く（一覧は、`alert` に含めない。読み上げの対象を、文に限る）。「評価が更新されていません」の警告（最終の評価から 15 分以上）は、別の警告（`role="alert"`）にする。「最終の評価」「最終のデータ取得」（手動のみの運用は「最終の手動入力」）の日時の横に、ヘルプヒントを置き、更新の仕組み（評価は 5 分ごと・画面は 10 秒ごと・取得間隔）を説明する。
- **観点の詳細の構成と折りたたみ（#160。SC-03）**: 上から、診断（状態・メッセージ・推奨アクション。視点ごとの判定を含む。同じ内容は 1 箇所だけ）、根拠の指標、推移、元データ、判断基準。推移・元データは、共通の部品 `CollapsiblePanel`（`components/collapsible-panel.tsx`。`<details>`。見出し h2 を `summary` に入れる）で、既定は閉じる（ドロワー・全画面のページで同じ）。開閉の状態は、観点の詳細が持つ（期間・設備を切り替えて、欄が作り直されても、開いたままにする）。
- **グラフの点の選択（#160。SC-03-2）**: `LineChart` の点は、押す（タップ・クリック）・フォーカスで選べ、日時・値・状態を、グラフの下（`chart-readout`。`aria-live="polite"`）に示す。押しやすいよう、見えない大きな当たり（半径 12）を重ねる。Tab で止まるのは 1 点（選んだ点、なければ最後の点）で、矢印キー・Home・End で前後の点へ移る。値の表は、見える折りたたみ（「値の表」）。`title` 属性だけに頼らない。
- **データ入力の数値（#361）**: 数値の項目は、数値の欄とスライダーを連動させ、スライダーの範囲の目安・単位を、入力の下に示す（判断基準の閾値の入力と同じ見た目）。スライダーの名前は、「（項目名）のスライダー」で、数値の欄のラベル（項目名＋単位）と別にする。満足度の 9 観点（スター）は、広い幅で 3 列、狭い幅で 1 列。
- **1 回の計測ごとの表（#363）**: 項目と値は、計測の行の中に、項目ごとに 1 行で並べる（有効でない項目は、横に状態）。狭い幅（900px 以下）は、計測 1 件ごとのカード。
- **閾値の入力（#358）**: 判断基準の閾値は、スライダーと数値の欄を連動させ、目安の範囲・単位・既定値・現在値・変更後の値を、入力の下に示す（この順。既定値は「既定: xx」。保存されている値が既定値と違うときは、色でなく、太字・情報のアイコン（丸 + i）・「（変更済み）」の文字で強調する。#165）。スライダーの名前は、数値の欄のラベルと別にする（「注意下限のスライダー」。同じラベルが 2 つにならないように）。指標ごとに、正常・注意・異常の帯を、現在と変更後で並べる。区分は、色（`--status-*-soft`）と文字（正常・注意・異常）で示し、帯全体に条件の文章（`aria-label`）を付ける。幅の狭い区分は、文字を出さない。狭い幅（900px 以下）でも、入力・目安は、縦に並べて、幅に収める。スライダーは、押せる大きさ（高さ 44px）にする。

## 9. 守ること

- 変えるのは、見た目と、共通のレイアウトの配置。メニューの項目・名前・数・遷移先・階層、画面の構成・導線・情報設計は変えない（#155・#160）。
- CSS を中心にする。DOM・aria の変更は、共通のレイアウト（サイドメニュー化）と、狭い幅（スマートフォン）の対応（#151。表のカード化など）に必要な範囲に限る。
- 依存パッケージを追加しない（CSS・トークン・自前の SVG のみ）。外部のフォント・CDN を使わない（CSP の設定（#127）で壊れないようにする）。
- 既存テストの期待値を、通すためだけに書き換えない。変更が要る場合は、理由を示して確認する。
- 状態は、色だけに頼らず、形・塗り方・文字で示す。色の意味を混ぜない（状態の色は、状態だけに使う）。
- ライト・ダークは、既定ではブラウザの設定に従い、ヘッダーのユーザーメニューの中の「テーマ」で、手動でも選べる（#352・#353）。描画の前の最初の適用は、外部のスクリプト `public/theme-init.js` で行う（CSP は、インラインのスクリプトを許さない）。

## 10. 確認の方法

- 画面を、ライト・ダークの両方で、PC・タブレット・スマートフォンの幅（1280px・768px・375px）で確認する（スクリーンショット）。
- 色覚シミュレーション（P 型・D 型・T 型）で、4 状態が区別できることを確認する。
- 文字のコントラストを確認する（4.5:1 以上。面・線・アイコンは 3:1 以上）。
- 既存のテスト（単体・E2E）が、すべて成功することを確認する。
- キーボードだけで、メニューの開閉・主要な操作ができることを確認する。
