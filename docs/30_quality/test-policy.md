# テスト方針

目的: テストのフレームワーク・種類・配置・カバレッジ目標・書き方、およびAIエージェントへの指示を定める。

## テストフレームワーク

| 対象 | フレームワーク |
|------|----------------|
| バックエンド（`src/backend/`） | Vitest（単体・結合） |
| フロントエンド（`src/frontend/`） | Vitest（単体）。コンポーネントのテストのライブラリは TODO: 実装の開始時に決める |
| 共通コード（`src/shared/`） | Vitest（単体） |
| E2E | Playwright |

## テストの種類と役割

テストピラミッドに沿い、単体テストを最も多く、E2Eテストは主要シナリオに絞る。

| 種類 | 対象・目的 | 外部依存 | 実行タイミング |
|------|------------|----------|----------------|
| 単体テスト | 関数・クラス単位のロジック（閾値判定、データ変換、状態判定など） | すべてモック・スタブに置き換える | ローカルで随時、PRごとのCI |
| 結合テスト | API・DB・メッセージ連携など、複数コンポーネントの組み合わせ。**Repository の契約テストは、ローカルの実装（メモリ・ファイル）と DynamoDB のアダプタに、同じテストを適用する** | テスト用DB・コンテナ等を使う（DynamoDB は、DynamoDB Local。手順は commands.md。Cognito は、偽の Cognito（`tests/support/fake-cognito.ts`）。実際の AWS には接続しない）。外部サービスはモック | PRごとのCI（CI は、DynamoDB Local を service container で起動する） |
| E2Eテスト | ユースケース（`docs/10_design/requirements/use-cases.md`）に沿った利用者の操作フロー | テスト環境一式 | `main` 宛ての PR（`release/*`・`hotfix/*`）のCI。`develop` 宛ての PR は、ラベル `ci:full` を付けたとき |
| 負荷テスト | 大量データの状態で、全ユースケースの操作の応答時間を、許容時間（NFR-3.x）で判定する | テスト環境一式（合成データ） | E2E と同じ（`main` 宛ての PR のCI、またはラベル `ci:full`） |

## テストの配置場所・命名

テストは `tests/` 配下に、種類ごと・`src/` と同じ構成で配置する。

```text
tests/
├── unit/          # 単体テスト（src/ と同じ階層構成にする）
│   ├── backend/
│   ├── frontend/
│   └── shared/
├── integration/   # 結合テスト
├── e2e/           # E2Eテスト
└── fixtures/      # テストデータ（匿名化データ・合成データのみ）
```

IaC（`infra/`。AWS CDK）のテストは、CDK が `infra/` の依存のため、`infra/test/` に置く（Vitest の `infra` プロジェクト。CDK の assertions で、合成したテンプレートを検証する。AWS には接続しない）。

- テストファイル名は対象ファイル名に合わせる（接尾辞は `.test.ts`。例: `sensor-alert.test.ts`）
- テストケース名は「条件と期待結果」がわかる日本語で書く（例: `土壌水分が閾値を下回ったらアラートを発行する`）
- 1テストケースでは1つの振る舞いを検証する。構成は Arrange（準備）/ Act（実行）/ Assert（検証）に分ける

## カバレッジ目標

- **行カバレッジ・分岐カバレッジともに 90% 以上** を目指す
- CIでカバレッジを計測し、90% を下回る、または変更によって低下する場合はPRで理由を説明する
- 数値の達成だけを目的にしない。アサーションのないテストや、実装をなぞるだけのテストは書かない
- 次の部分は特に重点的にテストする（分岐をすべて網羅する）
  - アラート・異常検知の判定ロジック（閾値の境界値を含む）
  - HITL（人の確認・承認）フロー、承認・却下・タイムアウト時の振る舞い
  - ロボット・ハウス設備への操作指示と、その認可チェック
  - センサー値の欠損・異常値・遅延データの扱い
- 自動生成コード・設定ファイル・型定義のみのファイルなどは計測対象から除外してよい（除外する場合は設定ファイルに明記する）

## テストの書き方

- テストは互いに独立させ、実行順序に依存させない
- 現在時刻・乱数・外部API・センサー・ロボットとの通信など、結果が変わる要素は差し替え可能にしてテストで固定する
- 正常系だけでなく、異常系・境界値（閾値ちょうど、最小・最大、空、null、欠損）を必ず含める
- テストデータに実データ・個人情報を使わない（[security.md](../20_development/security.md) 参照）。`tests/fixtures/` には匿名化データか合成データのみ置く
- 不安定なテスト（実行ごとに結果が変わるテスト）は放置せず、原因を調べて修正する。一時的にスキップする場合は理由とIssueをコメントで残す
  - 修正は、期待値・許容を緩めるのではなく、原因（画面の更新を待たない・処理の競合など）を直す。CI（遅い環境）でだけ起きるものは、ラベル `ci:full` を付けた PR で E2E を複数回実行して、再発しないことを確認し、PR に記録する
- E2E（Playwright）は、画面の更新を待ってから、次の操作・検証へ進む（Issue #62 で、遅い CI でだけ失敗した 2 種類を直した）
  - 登録・保存などの操作は、完了（行の表示・通知）を待ってから、次の入力に進む。完了で入力欄が空に戻る画面では、待たないと、次の入力が消える
  - 表の内容など、再描画のあとに決まる値の検証は、1 回だけ読む `expect(await 読み取り(...))` ではなく、再試行する `await expect.poll(() => 読み取り(...))` や、要素の検証（`toHaveCount`・`toHaveText`）を使う

## 実装時の進め方

- 変更前に既存テストを実行し、成功している状態を確認してから作業を始める
- 機能追加・変更では、実装と同じPR内でテストを追加・更新する
- バグ修正では、先にバグを再現するテストを書き、失敗を確認してから修正する
- 変更後は関連するテストと全体のテストを実行し、すべて成功することを確認する
- CIのテストがすべて成功していることをマージ条件とする（[git-workflow.md](../40_operations/git-workflow.md) 参照）
