# UC-09 環境センサーデータを自動で取り込む: 整合性チェックレポート

- 確認日: 2026-10-10 / ブランチ: feature/app-foundation
- 対象: use-cases.md UC-09、functional-specification.md 3.8（SC-09）・3.10（SC-11）・4.2（`POST /ingestion/{sourceId}/run`）・5章（JB-01）、FR-1.2・1.3・1.6・1.9〜1.12、dev_spec.md 4章 No.17・29（暫定仕様）、5.1（UI のないユースケースの E2E の方針）、UC-08 のレポート（同じ取り込みの仕組み）
- 結論: 基本フロー（1〜4）と代替フロー（読めない・形式違い、接続できない、ログ、重複）は、実装済みで、E2E で通っている。**実装の不足はなかった**（UC-08 と同じ `ingestion-service.ts` を、取り込み元の種別 `SENSOR`・環境センサー CSV の FormatProfile で動かす構成）。**テストの不足が6点あり、E2E を8件追加した**（センサーの複数ハウスへの対応づけと評価、追加の取り込みによる評価の更新、遅延、ロボットの機体 ID の混入、BOM つき・CRLF の CSV、失敗の通知と復旧、センサーの形式違いでもロボットの取り込みは実行される、停止中も他の画面が使える）。基本フローのログの確認も強化した。UI を持たない UC の検証方針（SC-11 の即時取得・開発用 API・モックの操作 → SC-02・SC-09・SC-11 で確認）は、use-cases.md のシナリオを適切に検証している（3.3）。

### 3.3 UI を持たない UC の検証方針（dev_spec.md 5.1）の妥当性

use-cases.md の UC-09 のアクターは「ファイルサーバー（センサーデータの提供元）」で、システムが自動で取り込む。基本フロー・代替フローは「UC-08 と同様」。方針（ファイルサーバーのモックに CSV を置く → SC-11 の即時取得、または開発用 API のジョブ起動・時計の操作 → SC-09・SC-02・SC-11 で確認）を、シナリオの各手順と照らして確認した。

- 手順1〜4 とも、「入口（ファイルの配置・取り込みの起動）」と「結果（保存・評価・ログ）」が、画面で確認できる。起動は、即時取得（利用者の操作）と JB-01（開発用 API）の 2 経路を通る。システム主体の定期の取り込みは、時計の固定・進行（取得間隔 15 分の判定）で、確定的に再現している。実時間で待つ必要はない。スケジューラの `tick` 経由は、UC-08 の E2E と `scenario-scheduled-ingestion.ts` が通る。
- 即時取得は、定期の取り込みと同じ `runSource` を呼ぶ。取得間隔の判定だけが `runDueSources` に固有で、JB-01 の E2E と結合テストで確認している。
- 接続できない・遅延は、モックの停止・遅延（開発用 API）で再現する。
- UC-09 固有の確認（CSV の形式・センサーへの対応づけ・環境適応性の評価）は、UC-08 の仕組みの共通部分と分けて、UC-09 の E2E に持たせている。
- 限界: 読めないファイル（一覧にあるが読めない）は、E2E では再現できない。結合テストで確認している。実ファイルサーバー（Q-002）・実センサーの CSV（Q-004）は、仮決めの形式とモックのみのため、確認できない。

以上から、方針は、シナリオを適切に検証している。
