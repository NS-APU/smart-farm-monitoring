### 気づき（コードは、確認なしに変更していない。必要なら、方針を決めて対応する）

1. **接続元の偽装（本番で要対応。dev_spec.md 4章 No.3 に TODO を追記済み）**: 接続元は、クライアントが付けた `X-Forwarded-For` の先頭を、そのまま信頼する（`middleware.ts:73-85`）。ローカルの E2E は、この仕組みで接続元を分けている（仕様の挙動）。しかし、本番で、クライアントが直接このヘッダーを付けられると、毎回違う値にして、接続元ごとの制限を回避できる。また、API Gateway・ALB などは、実際の接続元を、ヘッダーの末尾に追加するため、先頭を使うのは不適切な場合がある。本番のインフラが確定したら、信頼できるプロキシが付与した値だけを使う、または、ユーザーID単位の制限を併用する（Q-017）。
2. **パスワードの変更・再設定で、既存のセッションが残る**: ユーザー管理（UC-14）で、パスワードを再設定しても、そのユーザーの発行済みのトークン（アクセス 30 分・リフレッシュ 7 日）は、有効なまま（`user-service.ts` の `update`）。ユーザーの削除は、次のリクエストから効く（仕様）。パスワードの再設定（漏えいの疑いなど）で、既存のセッションを失効させるのが望ましいが、仕様（dev_spec.md 4章 No.27）に記載がなく、`AuthPort` の変更を伴うため、確認のうえで対応する。
3. **メモリの増加（ローカル実装のみ）**: セッションと失敗の記録は、メモリ上の Map で、期限切れのものは、そのキーが使われたときにしか消えない（`local-auth.ts`）。接続元を偽装して失敗を繰り返すと、メモリが増える。本番は Cognito へ移行する前提（ローカル実装は、再起動で消える）であるため、対応は見送った。
4. **ログインの入力に、長さの上限がない**: パスワードの検証は、1MB（リクエスト本文の上限）までの入力に対して行われる（scrypt）。実害は小さいが、必要なら、`LoginRequestSchema` に上限を設ける。

## 9. 初期ユーザーでのログイン手順（commands.md に追記済み）

1. `.env.example` を `.env` にコピーする（`.env` は Git 管理外。値はダミー）。`INITIAL_USER_ID`・`INITIAL_USER_NAME`・`INITIAL_USER_PASSWORD` の 3 つがそろっていること。`.env.example` のダミー値は、ユーザーID `local-user`・パスワード `Dummy-Passw0rd-local`（パスワードは、8 文字以上で英大文字・英小文字・数字を含むこと。満たさないとバックエンドが起動しない）。
2. `pnpm dev:backend` と `pnpm dev:frontend` を別のターミナルで起動する（バックエンドは、起動時に、ユーザーが 1 人もいなければ、初期ユーザーを作る）。
3. ブラウザで `http://127.0.0.1:5173` を開き、ユーザーIDとパスワードでログインする。利用後は、ヘッダーの「ログアウト」。
4. 注意: 初期ユーザーは、ユーザーが 1 人もいないときだけ作られる。`PERSISTENCE=file`（既定）では、`.local-data/store.json` に保存されるため、後から `.env` を変えても反映されない（ログイン後にユーザー管理でパスワードを再設定するか、`.local-data/store.json` を削除して作り直す）。`INITIAL_USER_*` を指定しないと、ログインできない。失敗が 5 回続くと、15 分ログインできない（バックエンドの再起動でも解ける）。
