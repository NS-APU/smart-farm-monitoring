### 3.3 UI を持たない UC の検証方針（dev_spec.md 5.1）の妥当性

use-cases.md の UC-10 は、アクターが「システム」で、取り込んだデータ・評価結果の判定、通知の作成・配信が主である。画面は、結果を受け取る SC-05・ヘッダーのみで、UC-05（通知を受けて確認）・UC-22（一覧・既読）が、受け手の操作を担う。

- 入口（トリガー）は、use-cases.md の事前条件（UC-08・UC-09・UC-07 で取り込まれたデータ、または評価結果）に対応する3経路（手動入力、取り込み、定期の評価）。dev_spec.md 5.1 の表は、手動入力と定期の2つを書いていたが、取り込みは UC-24（失敗）にしか使っておらず、**取り込んだ値の判定の E2E が不足していた**。今回追加し、dev_spec.md 5.1 の UC-10 の行に追記した。
- 結果の確認は、SC-05（通知の一覧）・ヘッダーの未読の件数・SC-02（ダッシュボード）・SC-03（ステータスの推移）で行え、「通知に含める内容」「未読として記録」「発生の記録」を画面で確認できる。
- 配信（Web Push）は、ダミーの記録（`GET /dev/mocks/web-push/delivered`）で確認する。実ブラウザへの配信は、E2E の対象外（dev_spec.md 3.5。UC-23 でスタブ化）。
- 限界: 通知の配信の記録（`deliveries` の失敗・試行回数）は、API では公開していない。E2E では、配信の有無（ダミーの記録）で間接的に確認し、記録の中身は結合テスト（`evaluation-notification.test.ts`）で確認している。

以上から、方針は、追加した入口（取り込み）を含めて、シナリオを適切に検証している。

- 収穫精度の同値分割（正常は通知なし。注意 89.6%・異常 78.3% はロボットの通知を SC-05 で確認。メッセージは「【異常】収穫精度（収穫ロボット1）」）。
- ロボットの異常と栽培環境の異常が同時にあるときの通知（5件）。

### (4) 取り込んだデータの判定（基本フロー1・2。UC-08・UC-09）

- 環境センサーの CSV（温度 40℃）を取り込むと、ハウスとセンサーの通知を作り、同じ異常を含む次のファイルでは増えない。
- 正常な CSV → 通知なし → 注意の CSV で、ハウスとセンサー（登録済みの設備 ID に対応づけ）の通知を作る。
- ロボットの JSON（1果実あたり 144 秒）を取り込むと、収穫速度の通知をロボットとハウスに作り、ダッシュボードのステータス（異常）と一致する。

### (5) 事後条件: 異常・注意の発生の記録

- 注意（12:00）→ 異常（12:30）の時刻・ステータスが、SC-03 のステータスの推移の帯と一覧に記録されることを確認。作成中に、期待値の誤りが1件あった（変更前の状態として「不明」の帯があると想定したが、記録は最初の変化から始まる。期待値を、実際の仕様に合わせた）。

### (6) 定期の評価・スケジューラ・配信の再送（基本フロー1、代替フロー）

- 評価が行われなかったデータ（`evaluate: false` で保存）を、次の JB-02 で判定し通知する（続けて評価しても増えない）。
- データが途絶え、短期視点から外れても、長期視点が異常のままなら、通知は増えない。
- スケジューラの tick が、JB-02・JB-04 を実行し、購読している端末へ配信する。
- Web Push の配信が失敗しても、画面内の通知は未読のまま残る。復旧後の JB-04 で、すべての通知が購読へ届き、続けて JB-04 を実行しても、二重には配信しない。購読がなければ配信は完了し、あとで購読しても、過去の通知は配信されない。
