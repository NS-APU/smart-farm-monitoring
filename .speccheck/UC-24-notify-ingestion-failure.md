### 2.2 理由が「ファイルの一覧を取得できませんでした」の場合

接続エラー以外（想定外のエラー）の失敗は、モックのファイルサーバーでは再現できない（開発用 API に、その種類の故障がない）ため、E2E ではなく結合テストで確認している: `tests/integration/ingestion.test.ts:586-604`（理由・試行 3 回・`notifyIngestionFailure` の引数）。判断: 十分（E2E で再現する手段がないことは、仕様どおり）。

### 2.3 UI を持たない UC の検証方針の評価（use-cases.md のシナリオとの対応）

dev_spec.md 5.1 の方針（`PUT /dev/mocks/file-server` の DOWN → SC-11 の即時取得、または JB-01 → JB-04 → 結果を SC-05・SC-11 で確認）は、use-cases.md の次の点を満たす。

- システム主体のシナリオを、システムの入口（取り込みの実行 = 即時取得・JB-01・スケジューラ tick）から起動し、**利用者が見る結果**（SC-05 の通知・ヘッダーの未読件数・SC-11 のログ）で検証している（手順 1〜3、事後条件）。
- 代替フロー（重複の抑制 60 分・境界、通知の再送）と、事後条件の「他の機能を妨げない」を、時計の固定・進行（`POST /dev/clock/advance`）で確定的に検証している。
- 事前条件（UC-08・UC-09 の失敗）のうち、「接続の失敗」は通知し、「形式違い」は通知しない（ログのみ）区別も検証している。
- 再試行の待ち時間は、固定した時計で待たずに進める（実際の待ち時間 1 秒 → 2 秒は、結合テストで 1000ms + 2000ms を確認）。

判断: **方針は適切**。今回、不足していた「取り込み失敗の通知の Web Push の再送」（代替フロー）と「画面の幅」を追加した。dev_spec.md 4.1 No.28（失敗の通知の `sourceName` が取り込み元の表示名）は、`ingestion-service.ts:303`・`ingestion-settings.ts:17-26`・`notifications-page.tsx:34-45`（対象の列）・E2E（メッセージと対象の列の両方）・結合テスト・単体テストで一致している。
