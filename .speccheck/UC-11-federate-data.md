### 3.3 UI を持たない UC の検証方針について

UC-11 のシナリオの主体は「システム」（農業情報基盤をアクターとする）で、農作業者の画面操作がない。dev_spec.md 5.1 の方針は、次のとおりで、use-cases.md のシナリオを適切に検証している。

- 事前条件（連携対象の保存）: 取り込み（ファイルサーバーのモックへ置いて即時取得）・手動入力（API）という、本物の入口を通す。連携キューへの直接の投入はしない
- 基本フロー 1（システムが送る）: 実際の起動は、スケジューラ（5分ごとの JB-03）。E2E では、開発用 API の `POST /dev/jobs/JB-03/run`（任意の時点で決定的に起動）と、`POST /dev/scheduler/tick`（スケジューラの経路）の両方を使う
- 基本フロー 2・3（送る内容・結果の記録）: 農業情報基盤の側（モックの `received`）で、受け取った内容を確認し、本システムの側（SC-11 の連携の状況）で、結果の記録を確認する。「連携されたこと」と「記録されたこと」を、別々の観点で確認している
- 代替フロー（停止・拒否・遅延・復旧）: `PUT /dev/mocks/federation`（`DOWN`／`REJECT`／`SLOW`／`UP`）と、時計の操作（`/dev/clock/advance`）で再現する。他の UC（ダッシュボード・通知・手動入力・取り込み済みデータ）が動くことは、同じテストの中で画面を開いて確認する
- 限界: 農業情報基盤の実際の API・データモデル・頻度は未確定（Q-005）のため、確認できるのは、本システムの側の振る舞い（キュー・保留・再試行・記録）と、モックが受け取った内容まで。方式が確定したら、アダプタの E2E を追加する必要がある
- 動画: 画面（`page`）を開くテスト（SC-11 の確認を含むテスト）は動画つき。API だけで確認するテスト（`request` のみ）は、画面を開かないため、動画は出ない（playwright の `video: on` は、ページを開いたテストに適用される）。これは、他の UC の E2E と同様
