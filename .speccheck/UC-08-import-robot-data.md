# UC-08 ロボットデータを自動で取り込む: 整合性チェックレポート

- 確認日: 2026-10-10 / ブランチ: feature/app-foundation
- 対象: use-cases.md UC-08、functional-specification.md 3.8（SC-09）・3.10（SC-11）・4.2（`POST /ingestion/{sourceId}/run`）・5章（JB-01）、FR-1.1・1.3・1.6・1.9〜1.12、dev_spec.md 4章 No.17・29、5.1（UI のないユースケースの E2E の方針）
- 結論: 基本フロー（1〜4）と代替フロー（読めない・形式違い、接続できない、ログ、重複）は実装され、E2E で通っている。実装の不足が1点あり、修正した（定期の取り込み `runDueSources` で、1つの取り込み元が想定外のエラーで失敗すると、後続の取り込み元が実行されなかった。取り込み元ごとの独立（dev_spec.md 2.2・FR-1.9）に反する）。再現テストを先に書いて失敗を確認してから修正した。テストの不足が4点あり、E2E を4件追加した（ハウスへの対応づけ、未来の計測日時、失敗の通知と復旧、定期の取り込みでの取り込み元ごとの独立）。UI を持たない UC の検証方針（SC-11 の即時取得・開発用 API・モックの操作 → SC-02・SC-09・SC-11 で確認）は、use-cases.md のシナリオ（システム主体の取り込み）を適切に検証している（3.3 に判断を記載）。

### 3.3 UI を持たない UC の検証方針（dev_spec.md 5.1）の妥当性

use-cases.md の UC-08 のアクターは「ファイルサーバー（提供元）」で、システムが自動で取り込む。方針（ファイルサーバーのモックにファイルを置く → SC-11 の即時取得、または開発用 API のジョブ起動・時計の操作 → SC-09・SC-02・SC-11 で確認）を、シナリオの各手順と照らして確認した。

- 手順1〜4 とも、「入口（ファイルの配置・取り込みの起動）」と「結果（保存・評価・ログ）」が、画面で確認できる。起動は、即時取得（利用者の操作）、JB-01 の実行、スケジューラの `tick` の3経路を、すべて通る（`:82`・`:220`・`:243`）。システム主体の定期の取り込みは、時計の固定・進行（取得間隔の 15 分の判定）で、確定的に再現している。実時間で待つ必要はない。
- 即時取得は、利用者が実行する経路だが、定期の取り込みと同じ `runSource`（同じコード）を呼ぶ。判定（取得間隔・無効な取り込み元）だけが `runDueSources` に固有で、これは、JB-01 と `tick` の E2E と結合テストで確認している。
- 接続できない・遅延は、モックの停止・遅延（開発用 API）で再現し、再試行の待ち時間は、固定した時計で待たずに進める。
- 限界: 読めないファイル（一覧にあるが読めない）と、想定外のエラーの伝搬は、E2E では再現できない。結合テストで確認している。実ファイルサーバー（Q-002）への接続は、モックのみのため、確認できない（アダプタに同じ契約テストを適用する方針。dev_spec.md）。

以上から、方針は、シナリオを適切に検証している。

## 4. 本調査で見つけた不足と、変更内容

### (1) 定期の取り込みで、取り込み元ごとに独立して実行する（実装の修正）
